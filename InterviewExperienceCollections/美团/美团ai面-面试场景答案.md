## 计网

### 1. 请介绍 OSI 七层模型，各层的作用是什么？

**面试回答：**

我一般会先说，OSI 七层模型更多是帮助我们分层理解网络问题，实际工作里更常用 TCP/IP 四层，但七层模型对排障很有用。
从下到上分别是：

- 物理层：负责比特流传输，比如网线、光纤、电信号。
- 数据链路层：负责成帧、MAC 寻址、差错检测，典型协议是以太网。
- 网络层：负责 IP 编址和路由转发，核心是让数据从源主机到目标主机。
- 传输层：负责端到端通信，典型协议是 TCP 和 UDP。
- 会话层：负责会话建立、维护和断开。
- 表示层：负责数据格式转换、加解密、压缩。
- 应用层：直接面向业务，比如 HTTP、DNS、RPC。

如果线上排障，我通常会按这个思路逐层看，先看链路是否通，再看 IP、端口、协议报文，最后再看应用层逻辑。

### 1.1 传输层是如何保障可靠性的？

**面试回答：**

如果说 TCP 如何保证可靠性，我会抓几个核心机制：

- 序列号：每个字节都有序号，接收方可以知道数据是否完整、是否乱序。
- 确认应答：接收方会返回 ACK，发送方知道哪些数据已经被成功接收。
- 超时重传：如果 ACK 没按时回来，会触发重传。
- 校验和：用于发现传输过程中的数据损坏。
- 滑动窗口：提高吞吐量，避免每发一个包都停下来等确认。
- 流量控制：通过接收窗口避免把对方打爆。
- 拥塞控制：通过慢启动、拥塞避免等机制防止把网络打爆。

所以 TCP 的可靠不是靠单一机制实现的，而是“确认 + 重传 + 有序 + 控制速率”组合起来实现的。

### 1.2 TCP 的可靠性机制会带来哪些性能影响？

**面试回答：**

TCP 的可靠性是有代价的，主要体现在几个方面：

- 建连和挥手有额外时延，三次握手本身就比 UDP 重。
- ACK、重传、窗口管理都会增加协议开销。
- 丢包时会触发重传，直接拉高延迟。
- 拥塞控制会主动降速，在弱网环境下吞吐下降明显。
- TCP 是字节流，而且存在队头阻塞，前面的包没到，后面的数据也可能不能及时交付。
- 内核需要维护连接状态、缓冲区和定时器，并发连接多时会吃更多内存和 CPU。

所以 TCP 更适合“正确性优先”的场景，不一定适合“极低延迟优先”的场景。

### 2. TCP 和 UDP 的区别是什么？各自的应用场景有哪些？

**面试回答：**

我通常会从四点来答：

- 连接方式：TCP 面向连接，UDP 无连接。
- 可靠性：TCP 可靠、有序；UDP 尽力而为，不保证到达、不保证顺序。
- 传输方式：TCP 是字节流；UDP 面向报文。
- 性能特点：UDP 更轻量，时延更低；TCP 更稳定，通用性更强。

应用上：

- TCP 适合对可靠性要求高的场景，比如 HTTP/HTTPS、数据库连接、订单支付、文件传输。
- UDP 适合更看重实时性的场景，比如音视频通话、实时游戏、DNS、日志采集、监控探测。

一句话概括就是：TCP 重可靠，UDP 重实时。

### 3. 设计一个游戏网络通信协议时，你会选择 UDP 还是 TCP？为什么？

**面试回答：**

如果是实时对战类游戏，我会优先选 UDP 传输核心实时数据，比如位置、朝向、动作状态。原因有三个：

- 第一，游戏更怕“延迟大”，有时比“偶尔丢一点数据”更致命。
- 第二，很多状态是高频刷新数据，旧数据即使补发回来也没意义。
- 第三，UDP 没有 TCP 那种明显的队头阻塞，更适合实时同步。

但我不会说整个游戏都只用 UDP。我的做法一般是分通道：

- 登录、鉴权、支付、背包结算这类强一致数据走 TCP 或基于可靠消息机制。
- 实时战斗状态走 UDP。

也就是说，协议设计上不是“二选一”，而是按业务语义分层处理。

### 3.1 在使用 UDP 的情况下，如何处理丢包问题？

**面试回答：**

UDP 本身不可靠，所以业务层要自己补：

- 给消息加序列号，知道丢了哪一段。
- 对关键消息做 ACK 和选择性重传，不关键的数据允许直接丢弃。
- 对状态同步类消息用“下一帧覆盖上一帧”的思路，避免无意义补发。
- 对特别关键但频率不高的消息，可以做冗余发送或者前向纠错。
- 定期发送关键帧，全量纠偏，避免长时间误差累积。

核心思想不是把 UDP 硬做成 TCP，而是只保证“关键数据可靠”，普通实时数据允许丢。

### 3.2 如何解决数据乱序问题？

**面试回答：**

乱序本质上还是靠序列号处理：

- 每条消息带序号或时间戳。
- 接收端维护一个短暂的重排序缓冲区，等后续包到齐后按序消费。
- 超过等待阈值还没到的包，就直接跳过，不能无限等。
- 对状态同步类消息，很多时候只保留最新状态，旧包即使晚到也直接丢弃。

所以解决乱序的关键不是“强行等待全部包到齐”，而是“在实时性和完整性之间做取舍”。

### 4. IPv4 和 IPv6 有哪些区别？

**面试回答：**

我会先从最核心的几点来答：

- 地址长度不同：IPv4 是 32 位，IPv6 是 128 位，地址空间大很多。
- 表达格式不同：IPv4 是点分十进制，IPv6 是冒号分隔的十六进制。
- IPv6 报文头更简化，路由转发效率更友好。
- IPv6 基本不依赖 NAT，而 IPv4 因为地址紧张大量依赖 NAT。
- IPv6 不再使用广播，更多依赖组播和任播。
- IPv6 支持自动配置能力更强。

从业务角度看，IPv6 的核心价值不是“地址更长”，而是更大的地址空间、更简洁的协议头和更自然的端到端通信能力。

### 4.1 IPv4 向 IPv6 过渡有哪些常见策略？

**面试回答：**

过渡一般不是一步切，而是分阶段：

- 双栈：同时支持 IPv4 和 IPv6，这是最常见也最稳妥的方案。
- 隧道：把 IPv6 流量封装在 IPv4 网络里传输。
- 协议转换：比如 NAT64、DNS64，让 IPv6 侧去访问 IPv4 服务。
- 应用网关或代理：在接入层做协议兼容。

如果是企业落地，我通常会优先推荐双栈，因为改造风险最低，兼容性最好。

### 4.2 在实际过渡过程中，IPv4 和 IPv6 互通的关键问题是什么？

**面试回答：**

关键问题其实不是“地址能不能写出来”，而是整条链路是否都支持：

- 网络设备是否支持 IPv6 路由和安全策略。
- DNS 是否支持 AAAA 记录。
- 应用是否把 IP 写死，或者是否只按 IPv4 处理。
- 日志、监控、风控、白名单系统是否兼容 IPv6 地址格式。
- 访问控制、负载均衡、网关、WAF 是否都支持双协议。

所以 IPv6 改造往往不是网络团队单独能完成的，而是基础设施和应用一起改。

### 4.3 有哪些技术手段可以实现 IPv4 和 IPv6 的互通？

**面试回答：**

常见手段有四类：

- 双栈：同一套系统同时开 IPv4 和 IPv6。
- 隧道技术：在不支持 IPv6 的网络上承载 IPv6 流量。
- 协议转换：如 NAT64、DNS64、应用层代理。
- 网关中转：在 API 网关、边缘代理层做地址族转换。

如果是面向公网服务，我会优先双栈；如果是存量网络难改，才会更多考虑转换或代理方案。

### 5. HTTP 和 HTTPS 的区别是什么？

**面试回答：**

HTTP 和 HTTPS 的核心区别不是“多了个 S”，而是 HTTPS 在 HTTP 之下加了一层 TLS。

- HTTP 明文传输，容易被窃听和篡改。
- HTTPS 通过 TLS 提供加密、完整性校验和服务端身份认证。
- HTTP 默认端口是 80，HTTPS 默认是 443。
- HTTPS 建连阶段会多一次 TLS 握手，所以性能开销会稍高，但现在一般都能接受。

如果是生产系统，尤其是登录、支付、用户数据和管理后台，HTTPS 基本是默认要求，不是可选项。

## JVM

### 1. 请介绍 JVM 运行时数据区，各个区域的作用是什么？

**面试回答：**

JVM 运行时数据区我一般分成线程私有和线程共享两类来答：

- 程序计数器：线程私有，记录当前线程下一条要执行的字节码位置。
- Java 虚拟机栈：线程私有，存放栈帧，里面有局部变量、操作数栈、方法出口等。
- 本地方法栈：线程私有，给 Native 方法服务。
- 堆：线程共享，绝大多数对象实例都在这里，是 GC 的主要区域。
- 方法区：线程共享，存类信息、常量、静态变量、JIT 编译后的代码，HotSpot 里对应元空间。

如果面试官继续追问，我会补一句：直接内存虽然不属于 JVM 运行时数据区本身，但线上排查内存问题时也必须关注，比如 Netty、NIO 都会大量用到。

### 1.1 垃圾回收机制（GC）是如何工作的？

**面试回答：**

GC 的核心目标是自动识别“哪些对象已经没用了”，然后把内存回收掉。

- 第一步是判定对象是否存活，主流做法是可达性分析，从 GC Roots 出发，看对象是否还能被引用到。
- 第二步是回收，常见算法有标记清除、复制、标记整理。
- 第三步是按代处理，通常年轻代对象朝生夕灭，老年代对象存活更久，所以不同区域用不同策略。
- 回收过程中通常会有 Stop-The-World，也就是业务线程短暂停顿。

所以 GC 本质是“找垃圾 + 回收垃圾 + 控制停顿和吞吐的平衡”。

### 1.2 GC 对系统性能有哪些影响？如何进行优化？

**面试回答：**

GC 对性能的影响主要有四类：

- 停顿时间：STW 会直接影响接口响应时间。
- 吞吐量：频繁 GC 会抢 CPU，业务线程可用时间下降。
- 内存占用：堆设置不合理会导致 GC 过于频繁或过晚。
- 抖动：大对象、晋升失败、碎片问题都可能带来延迟尖刺。

优化时我一般这样做：

- 先看 GC 日志和监控，不凭感觉调参数。
- 根据目标选择收集器，低延迟优先 G1、ZGC，高吞吐可以看 Parallel。
- 合理设置堆大小和各代比例，避免过小导致频繁回收。
- 从代码层减少对象创建，尤其是短生命周期的大量临时对象。
- 避免长事务、超大缓存、一次性加载太多数据。

我的原则是先定位问题出在哪一代、哪一类对象，再决定调 JVM 还是改代码。

### 2. JMM 的主要作用是什么？它是如何影响线程之间通信的？

**面试回答：**

JMM，也就是 Java 内存模型，核心作用是定义多线程下共享变量的可见性、有序性和部分原子性规则。

- 线程工作时不是每次都直接读主内存，很多值会先放到工作内存或者 CPU 缓存。
- 如果没有同步手段，一个线程改了变量，另一个线程不一定立刻看到。
- JMM 通过 `volatile`、`synchronized`、`final`、`Lock` 这些机制建立 happens-before 关系，保证线程间可见性和顺序性。

所以线程之间的通信本质上不是“你写了我就一定看见”，而是必须通过 JMM 认可的同步手段来建立约束。

### 3. 请解释 Java 中的垃圾回收机制（GC），以及常见的垃圾收集器有哪些？

**面试回答：**

GC 机制前面讲的是原理，这里如果问收集器，我会重点说常见方案和适用场景：

- Serial：单线程回收，简单但停顿明显，适合小内存或单核环境。
- Parallel：关注吞吐量，适合后台计算类场景。
- CMS：以低停顿为目标，但会有碎片和并发模式失败问题，现在基本退出主流。
- G1：面向服务端较常用，按 Region 管理堆，能兼顾吞吐和停顿。
- ZGC、Shenandoah：更偏超低停顿，适合超大堆和低延迟要求场景。

如果是 Java 11 之后的新项目，我一般优先考虑 G1，低延迟要求特别高再看 ZGC。

### 3.1 在实际开发场景中，什么情况下你会选择使用 G1 垃圾收集器，而不是 CMS 或其他收集器？

**面试回答：**

我选择 G1，一般是基于这几个判断：

- 堆比较大，已经到几个 G 甚至几十个 G。
- 服务是在线业务，对停顿时间比较敏感。
- 对吞吐有要求，但更不能接受长时间 Full GC。
- 不希望像 CMS 那样面对碎片问题和较高的调优成本。

G1 适合大多数中大型 Java 服务，是因为它不是单纯追求吞吐，也不是单纯追求极致低延迟，而是更均衡。

### 3.2 G1 垃圾收集器是如何优化停顿时间的？它在设计上有哪些特点，使其适合大内存应用？

**面试回答：**

G1 的关键设计不是简单分代，而是把整个堆切成很多 Region。

- 它会优先回收垃圾收益高的 Region，也就是 Garbage First。
- 它能根据用户设置的停顿目标，预测本次回收应该挑哪些 Region。
- 年轻代和老年代不再是物理上连续的大块区域，而是逻辑分代。
- 它通过 Remembered Set 追踪跨 Region 引用，减少全堆扫描。
- Mixed GC 会把年轻代和一部分老年代一起回收，降低老年代压力。

所以 G1 适合大内存应用的原因是：可控停顿比传统收集器更好，且碎片问题比 CMS 更可控。

## JUC

### 1. 线程的生命周期还有通信方式

**面试回答：**

Java 线程生命周期我通常按 `NEW -> RUNNABLE -> BLOCKED / WAITING / TIMED_WAITING -> TERMINATED` 来说。

- NEW：线程刚创建，还没启动。
- RUNNABLE：可运行，可能正在执行，也可能在等 CPU。
- BLOCKED：等待获取监视器锁。
- WAITING：无限等待，比如 `wait()`、`join()`。
- TIMED_WAITING：超时等待，比如 `sleep()`、`wait(timeout)`。
- TERMINATED：执行完成或异常退出。

线程通信方式我会分两类：

- 共享内存方式：`volatile`、`synchronized`、`Lock`、`Condition`、原子类。
- 协作工具方式：`wait/notify`、`CountDownLatch`、`CyclicBarrier`、`Semaphore`、`BlockingQueue`、`Future`。

实际开发里，我更推荐优先用并发工具类，而不是手写底层 wait/notify。

### 2. 多个线程对变量进行累加操作，会出现什么问题？

**面试回答：**

最典型的问题就是竞态条件，结果会比预期小，也就是“丢失更新”。

原因是 `count++` 不是原子操作，它至少包含读、改、写三个步骤。多个线程交叉执行时，就可能互相覆盖。

如果没有同步手段，还会有两个附加问题：

- 可见性问题：一个线程改了，另一个线程不一定立刻看到。
- 有序性问题：在复杂场景下可能出现指令重排带来的异常表现。

解决方式我一般按竞争强度选：

- 并发不高，用 `synchronized` 或 `ReentrantLock`。
- 只做计数，用 `AtomicInteger`、`AtomicLong`。
- 高并发热点计数，更适合 `LongAdder`，减少 CAS 冲突。

## Redis

### 1. Redis 的性能出现瓶颈怎么优化？如何保证多个应用实例之间一致性？

**面试回答：**

如果 Redis 出现瓶颈，我会先判断瓶颈属于哪一类，再做针对性优化：

- CPU 打满：看是不是有大 Key、热 Key、复杂 Lua、慢命令，尤其是 `keys`、大范围 `zrange` 这类操作。
- 网络打满：看请求是否过碎，能不能 pipeline、批量化、压缩返回。
- 内存压力大：看是否存在无 TTL 数据、淘汰策略不合理、碎片率高。
- 单实例压力大：考虑读写分离、分片集群、本地缓存兜底。

多个应用实例之间的一致性，我一般区分两种情况：

- 如果是“多个实例共享 Redis 缓存”，Redis 本身就是共享存储，一致性问题主要在缓存更新策略，通常用 `Cache-Aside + 删除缓存 + 重试`。
- 如果是“每个应用实例还有本地缓存”，那就需要在 Redis 更新后通过 MQ、Redis Pub/Sub 或订阅 binlog 的方式通知各实例失效本地缓存。

我的经验是，不要追求缓存的绝对强一致，而是要把最终一致性窗口控制到业务可接受范围内。

## MySQL

### 1. 请介绍常见的锁机制有哪些？

**面试回答：**

如果从 MySQL，尤其是 InnoDB 来看，我会这样分类：

- 按粒度分：全局锁、表锁、行锁。
- 按模式分：共享锁和排他锁。
- InnoDB 里还有意向锁，用来协调表锁和行锁。
- 为了解决幻读，InnoDB 还有间隙锁和 Next-Key Lock。
- 另外还有元数据锁，表结构变更时经常会碰到。

我一般会补一句：InnoDB 说是行锁，但本质上是“基于索引的锁”，如果没走索引，可能会扩大锁范围。

### 2. 请介绍你在项目中遇到过的慢查询场景

**面试回答：**

我遇到过比较典型的一类慢查询，是订单列表分页查询：

- 表数据量上来后，查询条件多，还带排序。
- 早期索引设计只覆盖了单字段，没有覆盖组合条件。
- 再加上深分页，导致扫描行数非常大。

后来排查发现，问题主要是三个点：

- 没命中最优联合索引。
- `order by` 和 `where` 没共用好索引。
- 深分页用 `limit offset` 越往后越慢。

最终我是通过补联合索引、改成基于游标的分页、减少回表，把响应时间压下来的。

### 2.1 慢 SQL 是如何排查的？

**面试回答：**

排查慢 SQL，我一般按这个顺序：

- 先看慢查询日志，确认到底是哪条 SQL 慢。
- 用 `EXPLAIN` 看执行计划，重点看 `type`、`rows`、`key`、`extra`。
- 看是否出现全表扫描、回表过多、Using filesort、Using temporary。
- 结合 `show processlist`、`performance_schema`、监控面板看是否有锁等待。
- 如果是线上偶发慢，还会看是否跟大事务、主从延迟、热点数据有关。

我的原则是，先拿到执行计划和扫描行数，再谈优化，不然很容易拍脑袋。

### 2.2 如何对慢 SQL 进行优化？

**面试回答：**

优化慢 SQL，我会从四个方向入手：

- 索引层：补联合索引、覆盖索引，尽量让查询少扫描、少回表。
- SQL 层：避免 `select *`，避免函数操作索引列，避免隐式类型转换。
- 业务层：深分页改游标分页，大查询拆小，冷热数据分离。
- 架构层：缓存、读写分离、分库分表。

我一般会强调一个原则：不是加了索引就一定快，而是要让索引和查询条件、排序、分页方式一起匹配。

### 3. MySQL 的事务隔离级别有哪些？分别是如何实现的？

**面试回答：**

MySQL 常见四个事务隔离级别是：

- 读未提交：可能读到未提交数据，会有脏读。
- 读已提交：只能读到已提交数据，解决脏读，但可能不可重复读。
- 可重复读：同一事务里多次读同一数据，结果一致。
- 串行化：最严格，基本把并发读写串起来执行。

实现上：

- 读已提交和可重复读主要依赖 MVCC。
- 可重复读在 InnoDB 下还会配合间隙锁、Next-Key Lock 解决幻读问题。
- 串行化则更多依赖锁，把并发能力换成一致性。

### 3.1 可重复读隔离级别可能会遇到哪些问题？

**面试回答：**

可重复读不是没有代价，它常见的问题有：

- 读到的是事务开始时的快照，业务上可能觉得“数据不是最新的”。
- 锁定读场景下，间隙锁可能扩大锁范围，导致并发下降。
- 长事务会导致 undo 版本链变长，影响性能和回收。
- 复杂更新并发下仍然需要小心写冲突和死锁。

所以可重复读在一致性和并发之间是个平衡点，不是放之四海而皆准的最优解。

### 3.2 请再整体说明数据库的事务隔离级别

**面试回答：**

如果面试官让我整体再说一遍，我会用“问题和代价”来总结：

- 读未提交：并发高，但会脏读，基本不用。
- 读已提交：解决脏读，很多数据库默认这个级别。
- 可重复读：进一步保证同一事务内读取一致，MySQL 默认是这个。
- 串行化：一致性最强，但吞吐最低。

我做业务系统时，默认接受数据库的可重复读；如果是报表类或者某些并发冲突较少的场景，也会结合业务看是否选择读已提交。

### 4. 请具体讲一下 MVCC（多版本并发控制）的原理

**面试回答：**

MVCC 的核心思想是：读不一定要加锁，而是去读“适合当前事务看到的那个版本”。

在 InnoDB 里，每行记录会带一些隐藏字段，比如：

- 事务 ID，表示这行数据是哪个事务最后改的。
- 回滚指针，指向 undo log，可以找到旧版本。

查询时会结合 Read View 判断当前事务能看到哪个版本：

- 如果版本对当前事务可见，就直接读。
- 如果不可见，就顺着 undo log 找更早的版本。

这样做的好处是，普通读和写可以并发，减少锁冲突。
所以 MVCC 的本质就是“通过多版本换并发能力”。

### 5. 索引失效中，如果出现隐式类型转换导致的索引失效，在不修改表结构、不迁移数据的情况下如何解决？

**面试回答：**

这个问题我会先给结论：不要去转换索引列，而要让查询参数的类型和列类型保持一致。

比如：

- 如果字段是 `varchar`，那查询参数就按字符串传，不要拿数字去比。
- 如果字段是 `bigint`，那应用层参数就按数值类型绑定，不要传字符串。
- 在 SQL 里如果必须转型，应该尽量转常量或参数，不要写成 `cast(column as ...)`，因为那样通常会让索引失效。

实战里我优先做两件事：

- 改应用层参数绑定类型。
- 改 SQL 字面量写法，让 MySQL 不需要对列做隐式转换。

这类问题经常不是数据库本身设计错了，而是调用方传参不规范。

### 6. 高并发场景下如何进行分库分表？有哪些常见策略？分库分表的优点是什么？

**面试回答：**

高并发下做分库分表，核心目的是把单机的存储和并发压力拆开。

常见策略有：

- 垂直分库：按业务域拆，比如用户库、订单库、营销库。
- 垂直分表：把宽表拆成基础信息表和扩展信息表。
- 水平分表：同一张表按用户 ID、订单 ID、时间维度做 hash 或 range 拆分。
- 水平分库：把不同分片放到不同数据库实例。

优点主要有：

- 降低单表数据量和索引体积。
- 提升并发能力和扩展能力。
- 可以做业务隔离，降低故障影响面。

但我也会主动补一句：分库分表是架构升级，不是银弹，后面会引入跨分片查询、分布式事务、全局 ID 等复杂度。

### 6.1 请谈谈分库分表的常见策略及其在并发场景下的应用

**面试回答：**

我会按业务特点选策略：

- 用户中心这类天然按用户聚合的数据，适合按 `user_id hash`。
- 订单、日志这类时间增长明显的数据，适合按时间范围分表，再结合冷热分离。
- 不同业务边界明显的系统，先做垂直分库。

如果并发热点集中在少数商家、少数用户，还要重点考虑热点分片问题，不能只看平均分布。

### 6.2 在高并发场景下，如何选择合适的分库分表策略？会考虑哪些因素来决定使用垂直还是水平分库分表？

**面试回答：**

我选择策略时主要看五件事：

- 数据增长速度。
- 查询维度是否稳定。
- 事务边界是否清晰。
- 是否存在明显热点。
- 后续扩容是否方便。

如果问题是“业务耦合太重、单库职责太杂”，我先做垂直拆分。  
如果问题是“单表太大、QPS 太高、索引太重”，我优先做水平拆分。

一句话就是：垂直拆的是业务边界，水平拆的是数据规模。

### 6.3 实际应用中，垂直分库和水平分库可能会遇到哪些挑战？你会如何应对这些挑战？

**面试回答：**

挑战主要有这些：

- 跨库事务变复杂。
- 跨分片查询和聚合变难。
- 全局唯一 ID 需要单独设计。
- 数据迁移和扩容成本高。
- 热点分片可能把单点再次打爆。

应对上我一般这么做：

- 事务上优先做业务解耦和最终一致性，少做强一致分布式事务。
- 查询上通过中间件聚合、ES、离线数仓来承接复杂检索。
- ID 采用雪花算法或号段模式。
- 分片策略预留扩容空间，避免一开始就写死。

## Java 基础

### 1. 链表和数组的区别是什么？

**面试回答：**

我一般从存储结构和访问代价来回答：

- 数组是连续内存，支持按下标 O(1) 访问，缓存友好。
- 链表是节点通过指针串起来，插入删除某个已知节点很方便，但访问某个位置要顺着找。

所以：

- 数组查找快，随机访问强。
- 链表插删灵活，但遍历开销大，内存额外开销也更大。

在 Java 里，很多人理论上会说链表插入删除快，但实际工程里因为对象分散、缓存不友好，`LinkedList` 往往没想象中那么香。

### 1.1 分别适用于哪些场景？

**面试回答：**

数组或者 `ArrayList` 更适合：

- 读多写少。
- 高频随机访问。
- 数据量较稳定，或者允许扩容复制成本。

链表更适合：

- 已经拿到节点引用，且需要频繁在中间插入删除。
- 对随机访问几乎没要求。

不过在 Java 业务开发里，我通常优先考虑 `ArrayList` 或 `ArrayDeque`，真正用 `LinkedList` 的场景并不多。

### 1.2 如何优化 LinkedList，避免内存消耗过大？

**面试回答：**

这个问题我会比较务实地答：很多时候最好的优化不是“优化 LinkedList”，而是“不要用 LinkedList”。

原因是它每个节点都要额外保存前后指针和对象头，内存开销比较大，CPU 缓存命中也差。

优化思路一般有：

- 如果是队列或双端队列场景，用 `ArrayDeque` 替代。
- 如果只是顺序存储，用 `ArrayList`。
- 如果必须链式结构，尽量减少节点包装层级，避免一个节点再挂很多小对象。
- 对基础类型大量场景，考虑专用集合或自定义结构，避免装箱。

所以这题我不会只从理论答，会明确说 Java 工程实践里更重要的是选对容器。

### 2. volatile 和 synchronized 的区别是什么？

**面试回答：**

我会用三句话区分：

- `volatile` 保证可见性和有序性，不保证复合操作原子性。
- `synchronized` 同时能保证可见性、有序性和临界区内的原子性。
- `volatile` 更轻量，`synchronized` 更强但成本更高。

比如：

- 一个开关位、状态位，用 `volatile` 很合适。
- 多线程对共享对象做复合读写，就应该用 `synchronized` 或 `Lock`。

### 2.1 分别适用于哪些场景？

**面试回答：**

`volatile` 适合：

- 状态标记。
- 单次写、多次读。
- 不依赖当前值参与计算的场景。

`synchronized` 适合：

- 需要保护临界区。
- 读改写一体的复合操作。
- 多个共享变量需要一起保持一致性。

面试里我通常会补一句：`count++` 这种场景只加 `volatile` 没用，因为它不是原子操作。

### 2.2 notify 和 await 的区别是什么？

**面试回答：**

`notify` 是 `Object` 提供的，配套 `wait/notify/notifyAll`，必须和对象监视器一起使用。  
`await` 是 `Condition` 提供的，配套 `Lock` 使用，通常和 `ReentrantLock` 搭配。

两者核心区别我会总结成三点：

- `await`/`signal` 语义更清晰，和显式锁绑定，更适合复杂并发控制。
- 一个 `Lock` 可以创建多个 `Condition`，做到“不同条件队列分开等待”，`wait/notify` 做不到这么细。
- `Condition` 在可中断、超时等待、工程可读性上通常更好。

所以简单场景可以说 `wait/notify`，复杂场景我更倾向 `Lock + Condition`。

### 3. 请讲一下快速排序的原理

**面试回答：**

快速排序的核心思想是分治：

- 先选一个基准值 pivot。
- 把数组重新划分成两部分，一边都比 pivot 小，一边都比 pivot 大。
- 然后对左右两部分递归做同样的事。

它的关键不是“先排序完再分”，而是“先分区，再递归处理子问题”。  
如果分区做得好，整体效率会非常高。

### 3.1 在不同场景下，快速排序的时间复杂度是多少？

**面试回答：**

我会直接给结论：

- 平均时间复杂度是 `O(n log n)`。
- 最好情况下也是 `O(n log n)`，因为每次都能比较均匀地分成两半。
- 最坏情况下是 `O(n^2)`，比如每次都选到极端基准，分区极不均衡。

空间复杂度主要来自递归栈，平均是 `O(log n)`，最坏是 `O(n)`。

### 3.2 如何对快速排序进行优化？

**面试回答：**

常见优化点有这些：

- 基准随机化，避免总选到最差 pivot。
- 三数取中，让分区更均衡。
- 小区间改插入排序，减少递归开销。
- 大量重复元素时用三路快排，减少重复比较。
- 递归过深时切到堆排，也就是做成 Introsort。

所以快排优化的核心就是两件事：让分区更均衡，控制递归成本。

### 1. 如何设计系统以避免恶意刷好评或差评？

**面试回答：**

这个问题我会从“身份、行为、内容、处置”四层来答：

- 身份层：评价必须和真实交易绑定，未下单、未核销、异常账号不能评价。
- 行为层：限制同设备、同 IP、同账号族、同时间窗口内的高频评价行为。
- 内容层：做文本相似度、情感倾向、模板化识别，识别机器刷评。
- 关系层：结合账号、设备、收货地址、支付方式做图谱风控，识别团伙行为。
- 处置层：风险分级，低风险放行，高风险延迟展示或人工审核，严重的直接拦截并处罚。

如果是平台型业务，我还会补一句：不能只靠规则，最好是“规则 + 模型 + 人工审核”闭环。

### 2. 如何对大语言模型进行全链路耗时观测（如检索、工具调用、生成等阶段）？

**面试回答：**

我会把这件事当成一次分布式链路追踪来做：

- 给每次调用生成统一的 `traceId`、`requestId`、`sessionId`。
- 把一次请求拆成多个 span，比如网关、鉴权、检索、重排、工具调用、模型首 token、完整生成、后处理。
- 每个 span 记录开始时间、结束时间、状态、重试次数、输入输出规模。
- 指标上至少看 `p50/p95/p99`、超时率、错误率、首 token 时延、总生成时延。
- 日志里补齐模型名、版本、prompt 模板、token 用量、工具耗时。

这样做的价值是，出了问题能快速知道瓶颈到底在检索、工具、模型还是网络，而不是只看到“整体慢”。

### 3. 请设计一个权限管理模块

**面试回答：**

我一般按“认证和授权分离”来设计。  
认证解决“你是谁”，授权解决“你能做什么”。

如果设计一个标准权限模块，我会包含这些核心对象：

- 用户。
- 角色。
- 权限。
- 资源。
- 用户角色关系。
- 角色权限关系。

权限粒度我会分为：

- 菜单权限。
- 按钮权限。
- 接口权限。
- 数据权限。

落地时我会让接口层做统一鉴权，避免把权限判断散落到业务代码里。  
如果是多租户系统，还要把租户维度带进去，防止越权访问。

### 3.1 在使用 RBAC 和 Spring Security 的情况下，权限如何进行动态变更？

**面试回答：**

动态变更的关键不是“数据库能不能改”，而是“改完后在线用户如何及时生效”。

我的做法通常是：

- 权限数据存在数据库里，Spring Security 认证后把权限加载到用户上下文。
- 为了性能，一般会加 Redis 缓存。
- 当角色或权限发生变化时，更新数据库后删除相关缓存，并通过 MQ 或 Redis Pub/Sub 通知各节点失效本地缓存。
- 如果系统用了 JWT，我会引入权限版本号或强制重新登录机制，否则 token 已签发出去后很难立刻失效。

也就是说，动态权限本质上是“数据库变更 + 缓存失效 + 会话刷新”三件事一起做。

### 3.2 如何保证权限系统的安全性和一致性？

**面试回答：**

我会从这几个方面保证：

- 最小权限原则，默认不给权限。
- 所有权限校验都在服务端完成，前端隐藏按钮不能当成真正安全。
- 权限变更必须走事务，避免角色表和权限表只改一半。
- 多节点场景做好缓存失效广播，避免不同节点看到的权限不一致。
- 敏感操作必须有审计日志，谁在什么时候给谁加了什么权限都要可追溯。
- 对超管权限做二次校验和更严格审批。

### 4. 设计一个大模型文本生成 HTTP 接口

**面试回答：**

我会把接口分成四部分设计：请求体、参数控制、响应体、可观测信息。

一个典型接口可以是：

- `POST /api/llm/generate`

请求体我会包含：

- 业务身份，如 `appId`、`userId`、`sessionId`。
- 上下文，如 `messages`、系统提示词、历史轮次。
- 模型参数，如 `model`、`temperature`、`top_p`、`max_tokens`。
- 行为参数，如 `stream`、`timeout_ms`、`tools`、`response_format`。

响应里我会返回：

- `code`、`message`。
- `requestId`、`callId`、`traceId`。
- 模型输出内容。
- `finish_reason`。
- `usage`，包括 prompt token、completion token、总 token。

这样后面做计费、审计、重试和排障都比较方便。

### 4.1 从输入参数、模型参数，到返回结构、错误码、调用 ID，应如何设计？

**面试回答：**

我会强调两点：结构化和可追踪。

输入参数建议分层：

- 业务层参数：`bizCode`、`userId`、`sessionId`、`scene`。
- 内容层参数：`messages`、附件、工具上下文、知识库引用。
- 模型层参数：`model`、`temperature`、`top_p`、`max_tokens`、`stop`。
- 控制层参数：`stream`、`timeout_ms`、`retry_policy`、`idempotency_key`。

返回结构建议统一：

- 成功时返回 `answer`、`usage`、`model`、`finish_reason`、`callId`。
- 失败时返回分层错误码和明确错误信息。
- `requestId` 用于网关级排障，`callId` 用于具体模型调用链路，`traceId` 用于全链路追踪。

### 4.2 该接口如何支持流式返回（Streaming）？

**面试回答：**

流式返回我一般优先用 SSE，因为对前端接入比较友好。

设计时我会注意几个点：

- 响应头明确为流式输出。
- 每次返回一个增量片段，而不是等完整文本生成完。
- 事件类型要区分清楚，比如 `delta`、`tool_call`、`usage`、`done`、`error`。
- 客户端断开后，服务端要能及时感知并停止下游调用，避免资源浪费。
- 最后一帧要带上结束原因和完整统计信息。

如果面试官继续追问，我会补一句：流式场景下首 token 时延是关键指标，不只是总耗时。

### 4.3 错误码体系如何设计？如何判断具体错误？

**面试回答：**

错误码我会按层级设计，而不是只返回一个 500：

- 4xx：请求问题，比如参数错误、鉴权失败、配额不足、内容违规。
- 5xx：系统问题，比如模型服务超时、网关异常、工具调用失败、内部依赖故障。

再往下还可以细分：

- `MODEL_TIMEOUT`
- `MODEL_RATE_LIMIT`
- `TOOL_CALL_FAILED`
- `PROMPT_TOO_LARGE`
- `CONTENT_BLOCKED`
- `UPSTREAM_UNAVAILABLE`

判断具体错误时，我会看错误来源在哪一层，再结合 `traceId`、上游状态码、超时点和重试信息来定位，而不是只看最终报错文案。

### 5. 在项目开发中，你是否遇到过问题？请举例说明

**面试回答：**

这个题我建议用 STAR 结构答。  
比如我会举一个大模型接口超时的问题：

- 背景：一个 AI 生成功能上线后，晚高峰接口响应抖动明显，p95 从 3 秒涨到 12 秒。
- 问题：最初大家怀疑是模型慢，但排查后发现是检索、工具调用和重试叠加放大了时延。
- 动作：我补了全链路 trace，把每次调用拆成检索、重排、工具、模型生成几个阶段；然后限制工具超时时间，引入降级策略，并把部分同步操作改异步。
- 结果：最终 p95 降到 4 秒以内，超时率显著下降。

这个回答的重点不是“我遇到过问题”，而是“我怎么定位、怎么收敛、结果怎样”。

### 5.1 请描述一个“分享系统”的设计场景

**面试回答：**

如果让我设计一个分享系统，我会先明确目标：用户把内容分享给别人，别人能通过链接或口令访问，同时平台能统计传播效果。

核心设计我会包含：

- 分享对象：内容 ID、分享人、分享渠道、有效期。
- 分享凭证：长链接、短链接或分享口令。
- 权限控制：公开分享、指定人可见、过期失效、次数限制。
- 统计分析：点击次数、去重 UV、转化率、来源渠道。
- 风控：防刷点击、防恶意传播、敏感内容拦截。

如果流量大，我会把短链解析和点击统计拆开，解析走高性能链路，统计异步落库。

### 6. 设计一个简单的广告位系统，支持广告位的创建与广告投放

**面试回答：**

我会先拆成三部分：广告位、广告素材、投放关系。

核心对象有：

- 广告位：定义页面位置、尺寸、业务场景、可投放规则。
- 广告计划：预算、起止时间、状态、定向条件。
- 广告创意：图片、文案、跳转链接、素材审核状态。
- 投放记录：谁在什么时间投到哪个广告位，曝光和点击多少。

投放流程一般是：

- 先创建广告位。
- 再创建广告计划和创意。
- 审核通过后建立投放关系。
- 请求到来时按广告位、时间、定向、人群、预算做筛选和排序。

如果面试官追问，我会继续说预算扣减、频控、A/B 实验和报表统计。

### 7. 设计一个简单的项目管理系统，请描述项目、任务、成员之间的关系以及主要的数据库表结构

**面试回答：**

我会按“项目是容器，成员是参与者，任务是执行单元”来设计。

关系上：

- 一个项目有多个成员。
- 一个项目有多个任务。
- 一个任务属于一个项目。
- 一个任务可以分配给一个或多个成员。

主要表我会设计成：

- `project`：项目基础信息。
- `project_member`：项目和成员关系，带角色字段。
- `task`：任务信息，包括创建人、负责人、优先级、状态、截止时间。
- `task_assignee`：任务和执行人关系。
- `task_comment`：任务评论和操作记录。
- `task_history`：状态流转审计。

这样后面做协作、权限、审计、统计都比较自然。

### 7.1 如何确保任务的创建人一定是项目成员？

**面试回答：**

这个问题我会从“应用层校验 + 数据库约束”两层回答。

- 应用层创建任务前，先校验 `project_member` 表里是否存在 `(project_id, creator_id)`。
- 数据库层可以把 `project_member(project_id, user_id)` 做唯一约束，再让任务表里的 `(project_id, creator_id)` 关联这组关系。

也就是说，不只是代码里 `if` 一下，最好在库里也留住约束，避免脏数据绕过服务层写进去。

### 7.2 如何实现项目成员的权限分级？

**面试回答：**

我会做“系统级 RBAC + 项目级角色”结合设计。  
项目内可以至少分四级：

- Owner：项目负责人，拥有最高权限。
- Admin：项目管理员，可管理成员和任务。
- Member：普通成员，可参与任务协作。
- Viewer：只读成员。

具体到操作层面，再把权限拆成：

- 项目配置权限。
- 成员管理权限。
- 任务创建权限。
- 任务分配权限。
- 数据查看权限。

这样做的好处是既容易理解，也方便后续扩展。

### 7.3 如何确保任务分配合理、成员工作负载均衡？

**面试回答：**

我不会把这题只答成“支持手动分配”，而是会补上调度思路：

- 给成员维护当前任务数、任务总工时、逾期任务数等负载指标。
- 分配任务时做推荐，比如优先给当前负载低、技能匹配高的人。
- 设置 WIP 限制，避免某个人被塞太多进行中任务。
- 对高优任务允许主管强制指派，但要有可见的负载提醒。

这类系统不一定要做自动调度，但至少要把“负载可视化”和“辅助决策”做出来。

### 7.4 如何处理任务的优先级与紧急情况？

**面试回答：**

我会把优先级和紧急程度拆开设计：

- 优先级反映业务价值，比如 P0、P1、P2。
- 紧急程度反映处理时效，比如是否阻塞线上、是否影响客户。

系统上可以这样做：

- 任务表有优先级字段和 SLA 字段。
- 紧急任务进入专门泳道或置顶队列。
- 自动提醒负责人和相关管理者。
- 重要变更保留审计，防止大家随意把任务都标成最高优先级。

### 8. 在大模型调用中，如何进行成本控制？

**面试回答：**

成本控制我会从“少调、短调、调对模型”三个方向答：

- 少调：能缓存就缓存，能命中历史结果就不重复调用。
- 短调：压缩 prompt，减少无效上下文，限制 `max_tokens`。
- 调对模型：简单任务走便宜模型，复杂任务再走贵模型，做模型路由。
- 控调用链：限制工具调用轮次和重试次数，避免链路失控。
- 做预算和配额：按业务线、租户、用户设置日限额和熔断。

一句话就是：把每一次模型调用都当成有成本的资源，不是无限免费函数。

### 8.1 如何统计 token 用量、工具调用次数、重试次数，并按业务方、模型版本进行聚合分析？

**面试回答：**

我会把采集和分析分开设计。

采集层：

- 每次请求记录 `bizCode`、`appId`、`model`、`modelVersion`、`requestId`。
- 记录 prompt token、completion token、总 token。
- 记录工具调用次数、每个工具耗时、重试次数、最终状态。

分析层：

- 明细数据先按调用粒度落库。
- 再按天、业务方、模型版本做聚合表。
- 监控面板重点看成本、成功率、平均 token、重试率和工具使用分布。

如果量很大，我会把分析类数据放到更适合 OLAP 的存储里，而不是只堆在 MySQL。

### 8.2 在设计相关数据库表时，如何兼顾扩展性与性能？

**面试回答：**

我会采用“明细表 + 聚合表”分层设计。

- 明细表负责完整记录一次调用的上下文和指标。
- 聚合表负责报表查询，按天或小时聚合。

表设计上会注意：

- 高频查询字段单独列出来，比如业务方、模型、时间、状态。
- 大字段和调试字段不要全放主表，可以拆扩展表。
- 按时间分区或分表，方便归档和查询。
- 对分析查询重的场景，及时把数据同步到 ClickHouse、Doris 这类系统。

### 9. 如何设计一个日历管理系统，并支持事件创建与提醒？

**面试回答：**

我会先定义核心能力：

- 事件创建、修改、删除。
- 参与人管理。
- 提醒设置。
- 重复事件。
- 日历视图展示。

主要表可以有：

- `calendar`：日历本身。
- `event`：事件信息，开始时间、结束时间、地点、备注、创建人。
- `event_attendee`：参与人关系。
- `event_reminder`：提醒方式和提醒时间。
- `event_rrule`：重复规则。

提醒实现上我会用异步任务扫描即将到期事件，再通过站内信、短信、邮件或 IM 推送。

### 9.1 如何结合大模型，为用户进行旅游规划（基于用户偏好推荐酒店、行程、餐厅等）？

**面试回答：**

我不会让大模型“凭空规划”，而是做“结构化数据 + 大模型生成”的组合。

流程一般是：

- 先收集用户约束，比如预算、城市、天数、同行人群、饮食偏好。
- 再从酒店、景点、餐厅库里检索候选数据。
- 结合评分、距离、营业时间、预算做规则排序。
- 最后让大模型把结构化候选结果组织成自然语言行程方案。

这样做的好处是：

- 结果更可控，不容易胡编。
- 可以明确约束预算和地理位置。
- 方便后续做解释和二次编辑。

### 10. 在项目开发过程中，你是如何排查和规避潜在风险的？

**面试回答：**

我一般把风险分成四类：需求风险、技术风险、进度风险、上线风险。

具体做法是：

- 需求阶段先把边界条件、异常流程、非功能要求讲清楚。
- 技术方案阶段识别高风险点，先做 PoC，比如性能瓶颈、第三方依赖、模型效果。
- 开发阶段补监控、压测、降级、幂等和审计，不把问题留到上线后。
- 上线前做灰度、回滚预案、告警阈值和负责人值守。

我自己比较看重的一点是：不要只在问题出现后救火，而是尽量在设计阶段把大坑提前挖出来。
