### 6. 请介绍 Go 的 GMP 调度模型

**建议时长：60 秒**

GMP 是 Go 运行时把大量 goroutine 调度到操作系统线程上的模型：

- **G（Goroutine）**表示一个待执行任务，保存栈、指令位置和调度状态。
- **M（Machine）**对应操作系统线程，真正执行机器指令。
- **P（Processor）**代表执行 Go 代码所需的调度资源，包含本地运行队列和部分运行时缓存。P 的数量由 `GOMAXPROCS` 决定。

M 必须绑定 P 才能执行用户 Go 代码。P 优先从本地队列获取 G，本地没有任务时会查看全局队列、网络轮询器，或者从其他 P 偷取任务。某个 G 因 Channel 等待而阻塞时，运行时可以让当前 M/P 执行其他 G；如果 M 因系统调用长时间阻塞，P 可以转交给其他 M。

这个模型的价值是用少量线程承载大量 goroutine，并通过本地队列和 work stealing 降低全局锁竞争。P 不是物理 CPU，也不是“负责把 goroutine 分给机器的控制器”。

### 7. Go 原生 `map` 是线程安全的吗

**建议时长：30 秒**

普通 `map` 不是并发安全的。多个 goroutine 在没有任何写操作时可以并发读取；只要存在写入，读写双方都需要同步，否则既会产生数据竞争，也可能触发 `concurrent map read and map write` 或 `concurrent map writes`。

常见方案是 `map + sync.RWMutex`。`sync.Map` 适合写入一次、多次读取，或者不同 goroutine 操作不相交 key 等特定场景；它不是所有并发 `map` 的默认替代品。是否报运行时错误也不能当成正确性保证，仍应使用 `go test -race` 检查数据竞争。

### 8. `defer` 的原理、场景和执行顺序

**建议时长：45-60 秒**

`defer` 用于把函数调用推迟到当前函数返回前执行。执行到 `defer f(x)` 时，函数值和参数 `x` 会立即求值并保存；真正的函数调用在外层函数正常返回、显式 `return`，或者发生普通 `panic` 并展开调用栈时执行。

同一个函数中多个 `defer` 按后注册、先执行，也就是 LIFO。`return` 时会先给返回值赋值，再执行 `defer`，最后真正返回，所以闭包形式的 `defer` 可以修改命名返回值。

它常用于解锁、关闭文件或网络连接、记录耗时和在服务入口配合 `recover` 做异常隔离。边界是：`os.Exit`、进程被强制终止等情况不会保证执行 `defer`；资源释放失败如果有业务意义，也不能直接忽略错误。

### 9. MySQL 单表多少行需要分表

**建议时长：60 秒**

我不会给出一个固定行数，因为“千万行必须分表”只是经验提醒，不是 MySQL 的硬限制。相同行数下，行宽、主键大小、二级索引数量、查询条件、冷热分布和硬件配置不同，性能可能差很多。索引设计合理的窄表，即使上千万行，点查仍可能很快。

我会从四类指标判断：

1. 业务 SLA：核心查询的 P95/P99 是否持续超标，写入是否出现热点或锁等待。
2. 容量：数据和索引是否明显超过 Buffer Pool 的承载能力，增长速度是否会很快触顶。
3. 执行计划：通过慢查询、`EXPLAIN ANALYZE` 检查扫描行数、回表和排序，而不是只看总行数。
4. 运维成本：DDL、备份恢复、归档、主从延迟是否已经难以接受。

通常先做索引和 SQL 优化、冷热归档、读写分离或合理分区。只有单机或单表边界确实无法满足未来容量和 SLA 时，才选择水平分片，并提前设计路由键、扩容、跨分片查询和全局 ID。可以把一千万行当作开始做容量评估的提醒，但不能把它当作自动分表线。

### 10. 实习中使用了什么 Redis 结构，解决了什么问题

**建议时长：45-60 秒**

我在支付风控黑名单到期解封任务中使用了 Redis ZSet。业务上，一部分玩家因为小额提现等支付风险被临时加入黑名单，到期后需要自动解封。如果每次都全表扫描 MySQL，轮询成本较高，也不方便快速定位已经到期的数据。

因此 MySQL 保存黑名单业务记录，Redis ZSet 作为按时间排序的调度索引。定时任务分批查询 `score <= now` 的成员，执行业务校验和解封，成功后再移除 ZSet 成员。多实例场景还需要互斥或竞争消费，但分布式锁不能代替业务幂等和数据库状态校验。

### 11. 为什么选择 ZSet，`member` 和 `score` 存什么

**建议时长：45 秒**

选择 ZSet 的核心原因不是“Redis 快”，而是它天然支持按 `score` 排序和范围查询。`score` 存预计解封时间戳，`member` 存能唯一定位黑名单记录的标识。定时任务可以使用 `ZRANGE key -inf now BYSCORE LIMIT 0 100` 分批读取到期数据；旧版客户端也可能封装为 `ZRANGEBYSCORE`。

当时的成员主要由玩家标识和游戏项目标识组成。更稳妥的设计还应包含黑名单类型或记录版本，或者取出后回查数据库版本，避免旧的到期任务错误解封之后新加的一次黑名单。查询复杂度大致是 `O(log N + M)`，其中 M 是本批返回数量。

### 14. 黑名单怎样持久化，MySQL 和 Redis 分别做什么

**建议时长：60 秒**

MySQL 应该是业务事实源，保存玩家、项目、黑名单类型、状态、创建时间、解封时间和版本等信息；Redis ZSet 只是为了快速找到“当前已经到期的任务”，不能成为唯一数据源。

一致性上，我会按下面几层处理：

1. 创建或修改黑名单时先提交数据库，再通过可靠重试、事务消息或 Outbox 更新 Redis 调度索引。
2. 定时任务取出成员后回查数据库状态和版本，保证旧任务不能解封新一轮封禁。
3. 解封接口保持幂等，只有解封成功后才移除 ZSet 成员；失败任务保留并重试。
4. 定期用数据库做对账和重建，Redis 丢数据后也能恢复。

这样即使 Redis 单节点故障或缓存丢失，最多影响调度时效，不会丢失黑名单事实。

### 17. 流失召回的背景、目标和设计原因

**建议时长：45 秒**

### 21. Redis Pipeline 的背景和工作方式

**建议时长：60 秒**

这里的 Pipeline 发生在 **Go 业务服务与 Redis 之间**。离线任务一次已经拿到一批待处理用户，如果逐个执行 100 次 Redis 命令，并且每条都等待响应，就会累积约 100 次网络 RTT。Pipeline 会让 Redis Client 连续写出多条命令，再批量读取按顺序返回的结果，从而减少往返和系统调用开销。

它不是把浏览器请求或用户操作积攒起来，也不是把多个命令变成一条命令。Redis 仍然逐条执行这些命令，Pipeline 本身不提供事务原子性。使用时要控制批大小、检查每条返回结果，并处理连接失败和部分命令失败。

### 22. Pipeline 是否增加用户请求延迟，怎样保证正确性

**建议时长：45-60 秒**

不会因为 Pipeline 故意等待用户请求。这个场景本来就是离线任务的一批数据，批次形成后立即在服务进程内调用 Redis Pipeline；客服 Web 端到 Go 服务仍然是正常的在线接口。

正确性要分层看：Pipeline 只优化传输，不保证整批原子。每个 `SET key token NX PX ttl` 的加锁命令本身是原子的，但要逐条读取结果，只处理加锁成功的用户；释放锁需要用 Lua 原子完成“校验 token + 删除”，防止误删别人的锁。即使有锁，数据库唯一约束、版本校验或幂等更新仍应作为最终兜底。

### 23. 使用 Go 合并 K 个有序链表

**建议讲解时长：90 秒，编码时间：15-20 分钟**

思路是维护一个最多包含 K 个节点的最小堆。先把每条非空链表的头节点放入堆；每次弹出最小节点接到结果链表，再把它的下一个节点放回堆，直到堆为空。

```go
package main

import "container/heap"

type ListNode struct {
	Val  int
	Next *ListNode
}

type nodeHeap []*ListNode

func (h nodeHeap) Len() int           { return len(h) }
func (h nodeHeap) Less(i, j int) bool { return h[i].Val < h[j].Val }
func (h nodeHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }

func (h *nodeHeap) Push(x any) {
	*h = append(*h, x.(*ListNode))
}

func (h *nodeHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	old[n-1] = nil
	*h = old[:n-1]
	return x
}

func mergeKLists(lists []*ListNode) *ListNode {
	h := make(nodeHeap, 0, len(lists))
	for _, head := range lists {
		if head != nil {
			h = append(h, head)
		}
	}
	heap.Init(&h)

	dummy := &ListNode{}
	tail := dummy

	for h.Len() > 0 {
		node := heap.Pop(&h).(*ListNode)
		next := node.Next
		node.Next = nil

		tail.Next = node
		tail = node

		if next != nil {
			heap.Push(&h, next)
		}
	}

	return dummy.Next
}
```

### 24. 请解释代码主流程

**建议时长：30-45 秒**

`nodeHeap` 通过 `Less` 按节点值建立最小堆。初始化时每条链表只放头节点，因为每条链表内部已经有序，当前全局最小值一定在这些头节点中。弹出一个节点后，它所在链表的下一个节点才可能成为新的候选，因此再将 `next` 放入堆。

结果链表使用哨兵节点 `dummy`，避免单独处理第一个节点。代码复用原节点，并在拼接前暂时断开 `Next`，让结果链路更清晰。

### 25. 初始化堆时是否需要判空，堆最大多大

**建议时长：20 秒**

需要判空。题目通常允许某条链表为空，如果把 `nil` 放进堆，`Less` 访问 `Val` 时会 panic。输入切片本身为 `nil` 或长度为 0 不需要特殊分支，初始化出的空堆会直接返回 `nil`。

堆的大小始终不超过 K。每弹出一个节点，最多只把同一条链表的一个后继放回去，所以每条链表在堆中最多贡献一个候选节点。

### 26. 时间和空间复杂度

**建议时长：15 秒**

设所有链表一共有 N 个节点、链表数量为 K。每个节点入堆和出堆各一次，堆大小最多为 K，因此时间复杂度是 `O(N log K)`；堆和少量指针的额外空间是 `O(K)`。返回链表复用原节点，不计输出本身的空间。
