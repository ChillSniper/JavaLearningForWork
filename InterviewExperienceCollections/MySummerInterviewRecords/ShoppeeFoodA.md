### 4. Binlog + RocketMQ 如何保证 MySQL 和 Redis 最终一致

**建议时长：75-90 秒**

**推荐回答：**

> 先给结论：binlog 和 MQ 本身不能自动等于最终一致性，完整方案必须包含可靠投递、消费幂等和数据修复三层，而且 MySQL 是最终事实源。
>
> 业务事务提交后，MySQL 产生 binlog。Canal 以类似从库的方式读取增量变更，把表、主键、操作类型和位点等信息转换成事件并发送到 RocketMQ。同步消费者收到事件后，按业务映射更新或删除对应 Redis Key；只有 Redis 操作和必要的业务校验成功后，才返回消费成功。
>
> 可靠性方面，生产端要检查发送结果并重试，Broker 要持久化并根据可靠性要求配置副本，消费失败则重试，超过阈值进入死信队列并告警。由于重试可能造成重复投递，消费者需要按业务主键、事件 ID 或版本号实现幂等；同一个 Key 的变更还要防止旧事件覆盖新值。
>
> 最后必须有兜底：监控消费延迟，并定期以 MySQL 为准做抽样或全量对账。发现不一致时，可以重放保留的 MQ/binlog，或者按主键和时间范围重新构建缓存。因此这里承诺的是“可监控、可重试、可修复的最终一致”，不是零延迟强一致。

### 5. 订阅 binlog 的完整链路是什么

**建议时长：45-60 秒**

**推荐回答：**

> 链路可以拆成四段：`MySQL 提交事务 -> binlog 记录变更 -> Canal 解析并投递 RocketMQ -> 消费者更新或失效 Redis`。
>
> Canal 侧要保存 binlog 文件名和 position/GTID 等消费位点，确认下游接收后再推进位点，这样重启后可以继续消费。RocketMQ 侧保存消息和消费进度；消费者侧在业务处理成功后提交消费结果。
>
> 这里要区分三种确认：Canal 对 MySQL 位点的确认、生产者对 Broker 写入结果的确认、消费者处理后的确认。现场把它们统称为 ACK，容易把责任方向讲反。

### 6. 消息积压怎么办

**建议时长：60-75 秒**

**推荐回答：**

> 我会先判断是短时流量峰值，还是消费者永久变慢。监控上看每个队列的堆积量、最老消息年龄、消费 TPS、失败率和下游 Redis/数据库耗时，先定位瓶颈。
>
> 如果消费逻辑本身正常，可以增加消费实例和线程数，但并行度上限受 MessageQueue 数量限制；必要时增加队列并重新分配。消费端还可以批量拉取、Pipeline 更新 Redis、减少重复反序列化，并隔离慢 SQL 或外部调用。扩容前要确认同一业务 Key 是否要求顺序，不能为了并发破坏顺序一致性。
>
> 正确性上不能通过“跳过消息”消除积压，也不能在业务完成前提前返回成功。只要消息仍在保留期内、消费位点没有错误推进，就可以慢慢追平；超过保留期或发生错误 ACK，则必须从 binlog/数据库重新回放和对账。

### 7. RocketMQ 到消费者是推还是拉

**建议时长：20-30 秒**

**推荐回答：**

> 从业务 API 看，`PushConsumer` 像是 Broker 主动回调消费者；但从实现机制看，客户端 SDK 内部通过长轮询主动从 Broker 拉取消息，再交给本地消费线程。因此更准确的说法是“对使用者表现为 Push，底层是 Pull/长轮询”，不是 Broker 无控制地把消息塞给消费者。

### 8. RocketMQ 消息会不会丢，如何保证可靠性

**建议时长：75-90 秒**

**推荐回答：**

> 不能只回答“有 ACK，所以不会丢”，需要按生产者、Broker、消费者三段说明。
>
> 生产者发送后必须检查结果，失败重试；如果“业务提交成功但消息是否发出未知”，需要事务消息或本地消息表/Outbox 解决双写窗口。Broker 侧通过持久化和副本降低单机故障风险，具体刷盘和复制策略要按可接受的数据损失窗口选择。消费者只有在缓存更新和业务校验真正完成后才能返回成功；失败或超时触发重试，达到上限进入 DLQ 并告警。
>
> 可靠配置通常带来的是至少一次投递，因此会重复，消费者仍要做幂等。跨 MySQL、MQ、Redis 的链路不能轻易承诺 exactly-once，最终还要依赖版本控制、状态机和对账修复。

### 9. 消费者错误 ACK 后，已经跳过的数据怎么办

**建议时长：60-75 秒**

**推荐回答：**

> 如果消费者在业务真正成功前就返回了成功，Broker 会认为消息已经提交，自动重试机制救不回来。这时处理思路是“停错、定界、重放、校验”。
>
> 先下线或关闭有 Bug 的消费者，修复并验证；然后根据发布时间、ConsumerGroup offset、消息 ID、binlog position 或受影响主键确定数据范围。如果 MQ 消息仍在保留期内，可以把消费位点重置到故障前重放；如果 MQ 已过期，则从对应 binlog 位点重放，或者以 MySQL 为准扫描受影响主键并重建 Redis。
>
> 重放时必须携带数据版本或更新时间，避免旧事件覆盖故障期间产生的新数据。修复完成后再做数量、版本或抽样内容对账。也就是说，ACK 只能减少正常故障下的丢失，真正应对“错误 ACK”的是可回放日志和对账修复链路。

### 10. Redis 应该存业务投影还是 MySQL 整行镜像

**建议时长：35-45 秒**

**推荐回答：**

> Redis 存的是读路径需要的业务投影，不应默认把 MySQL 所有列一比一复制过去。Key 按车次、日期、用户等业务维度设计，Value 只保留查询需要且适合缓存的字段。
>
> binlog 事件至少要能定位表、主键、操作类型和版本。字段映射简单时可以增量更新 Hash；映射复杂或容易遗漏时，我更倾向于删除缓存，让下一次读取从 MySQL 重建。无论哪种方式，都要处理删除事件、字段变更、乱序和 TTL。

### 11. CRM 流失召回为什么需要分布式锁

**建议时长：40-50 秒**

**推荐回答：**

> 流失判定是定时任务加并发 goroutine 的处理方式，每个项目还会分批扫描用户。在任务重跑或多实例部署时，同一用户可能同时被两个执行单元取到，造成重复计算、重复写入或中间状态竞争。
>
> 所以锁的粒度是“项目 + 用户”，目标是保证同一个用户同一时刻只由一个执行单元处理。它解决的是跨进程互斥，不是用来同步 Redis 主从节点的锁状态。数据库唯一约束和 Upsert 仍然作为最终幂等兜底。

### 12. 项目中的分布式锁具体怎么实现

**建议时长：60-75 秒**

**推荐回答：**

> 这个项目不是用 Redisson，而是 Go 服务基于 Redis 客户端自己组合了 `SetNX + TTL + Token + Lua`。
>
> 每个用户使用类似 `churn:lock:{projectId}:{uid}` 的锁 Key，Value 是本次任务生成的随机 Token，并设置 15 分钟 TTL。批量处理用户时用 Pipeline 一次发送多条独立的 SetNX，减少网络 RTT；Pipeline 本身不保证整批原子性，但每条带过期时间的 SetNX 是原子的。只处理返回加锁成功的用户。
>
> 释放锁放在 `defer/finally` 语义中，通过 Lua 原子执行“比较 Token，相同才删除”，防止旧任务误删已经由新任务获得的锁：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

> 这个锁不宣称支持可重入、公平和自动续期。固定 TTL 必须大于正常处理时长，并监控超时；最终写入仍依靠数据库唯一键/Upsert 保证幂等。

### 13. 是调用框架，还是自己实现

**建议时长：20-30 秒**

**推荐回答：**

> 协调逻辑是我们基于 Go Redis 客户端实现的，不是 Redisson。客户端提供 Pipeline、SetNX 和 Eval 等原子命令能力；锁 Key、Token、TTL、批量加锁、Lua 解锁以及异常降级是业务代码设计的。Redisson 是 Java 生态的成熟方案，可以作为对比，但不能说成这个 Go 项目的真实实现。

### 14. Redis 分布式锁的完整原理和设计点

**建议时长：75-90 秒**

**推荐回答：**

> 一个基本正确的 Redis 锁至少包含四点。第一，用一条原子命令完成“Key 不存在才写入 + 设置过期时间”，例如 `SET key token NX PX ttl`；第二，Value 保存唯一 owner Token，避免释放别人的锁；第三，用 Lua 原子比较 Token 后删除；第四，业务结束在 `finally` 中释放，进程宕机则依靠 TTL 兜底。
>
> 工程上还要考虑锁粒度、等待时间和重试退避，避免热点 Key；评估业务最长耗时，决定固定 TTL 还是续期；明确是否需要可重入、公平锁和可中断等待；监控加锁失败率、持锁时间和超时次数。
>
> 更重要的是边界：Redis 主从切换、长时间 GC/进程暂停、网络分区都可能让旧持有者在锁失效后继续执行，所以锁不是 exactly-once 保证。关键写操作还需要数据库唯一约束、幂等键、版本号/状态机，要求更强时使用 fencing token，让下游拒绝旧持有者的写入。

**如果追问 Redisson 看门狗：**`RLock` 在未显式指定固定 leaseTime 时，由看门狗在持锁客户端存活期间续期；客户端崩溃后不再续期，锁最终过期。Redisson 还提供可重入和 Pub/Sub 唤醒等待者。它降低了固定 TTL 过短的问题，但不能替代业务幂等和 fencing。

### 15. TCP 三次握手

**建议时长：40-50 秒**

**推荐回答：**

> 第一次，客户端从 `CLOSED` 进入 `SYN_SENT`，发送 `SYN=1, seq=x`。第二次，服务端收到后从 `LISTEN` 进入 `SYN_RECV`，返回 `SYN=1, ACK=1, seq=y, ack=x+1`。第三次，客户端确认服务端的初始序列号，发送 `ACK=1, seq=x+1, ack=y+1`，客户端进入 `ESTABLISHED`；服务端收到后也进入 `ESTABLISHED`。
>
> 三次握手的核心是双方交换并确认各自的初始序列号，同时验证双向收发能力，避免旧的重复连接请求被误认为新连接。它建立的是 TCP 连接，后续可能承载 HTTP；HTTP/3 使用 QUIC/UDP，不能把“三次握手”和所有 HTTP 都直接画等号。

### 16. 第二次握手的 SYN + ACK 丢失怎么办

**建议时长：25-35 秒**

**推荐回答：**

> 服务端发送 SYN+ACK 后会保留未确认状态并启动重传计时器，超时后重传 SYN+ACK；客户端没有收到响应，也可能超时重传 SYN。重复 SYN 不会建立两条连接，双方通过四元组和序列号识别。若达到操作系统规定的重传上限仍未成功，连接尝试才会超时失败；具体次数和时间属于实现参数，不要硬背成“只重试一次”。

### 17. 第三次握手的 ACK 丢失怎么办

**建议时长：30-40 秒**

**推荐回答：**

> 客户端发出第三次 ACK 后已经进入 `ESTABLISHED`，服务端仍停在 `SYN_RECV`。因为服务端的 SYN+ACK 没有被确认，它会超时重传 SYN+ACK；客户端收到重复 SYN+ACK 后会再次回复 ACK，服务端即可建立连接。
>
> 如果客户端紧接着发送了带正确 ACK 的业务数据，服务端也可以据此完成状态迁移。所以第三次 ACK 丢失并不意味着服务端立刻关闭，TCP 的重传和状态机可以恢复。

### 18. Linux 如何管理半连接和全连接队列

**建议时长：45-60 秒**

**推荐回答：**

> 对一个监听 Socket，可以从面试角度理解为两类队列。收到 SYN、发送 SYN+ACK、尚未收到最终 ACK 的请求处于 `SYN_RECV`，在半连接队列中；三次握手完成但应用还没有调用 `accept()` 取走的连接，在全连接，也叫 accept 队列中。
>
> Linux 中半连接上限主要受 `tcp_max_syn_backlog` 影响；`listen(fd, backlog)` 主要约束已经完成握手、等待 accept 的队列，并受 `somaxconn` 封顶。半连接压力大时可以使用 SYN Cookies 等机制缓解 SYN Flood；全连接队列持续满通常说明应用 accept 不及时、线程阻塞或处理能力不足。
>
> 排查时不能只调大参数，还要结合队列溢出计数、连接建立延迟、应用 accept 速率和 CPU/线程池情况判断瓶颈。

### 19. 常见缓存淘汰算法

**建议时长：35-45 秒**

**推荐回答：**

> 常见算法包括 FIFO、LRU、LFU、Random，以及结合过期时间的 TTL 淘汰。LRU 看“多久没访问”，适合近期访问能代表未来热点的场景；LFU 看访问频率，能保留长期热点，但需要处理计数老化，否则历史热点可能长期占位；FIFO 实现简单但不关心访问价值；Random 开销低但命中率不稳定。
>
> TTL 解决的是数据过期，不等于内存不足时的淘汰策略。工程选型要看访问局部性、扫描流量、实现开销和元数据成本。

### 20. LRU 用什么数据结构实现

**建议时长：40-50 秒**

**推荐回答：**

> 标准做法是 `HashMap + 双向链表`。HashMap 保存 `key -> node`，让查询定位是 O(1)；双向链表按访问新旧排序，头部是最近访问，尾部是最久未访问。
>
> `get` 命中后把节点移动到头部；`put` 已存在则更新并移到头部；新增时插入头部，如果超过容量就删除尾节点，同时从 HashMap 删除对应 Key。使用带哨兵的 dummy head/tail 可以统一删除头尾和中间节点的代码，所有核心操作都是 O(1)。仅有双向链表时查找仍是 O(n)，所以不能漏掉 HashMap。

### 21. 如何解决 LRU 的扫描污染

**建议时长：60-75 秒**

**推荐回答：**

> 这是典型的 scan pollution。纯 LRU 会把每个第一次访问的数据都放到 MRU 端，一次 1 万条顺序扫描就能把原来的 100 条热点全部挤走。
>
> 可以使用 2Q 或分段 LRU，并增加“准入”逻辑。新数据第一次访问只进入容量较小的 probation/冷队列，不直接进入主热点队列；同一个 Key 再次命中，才晋升到 protected/热 LRU。这样一次性扫描的数据只会在冷队列内部循环淘汰，已经被多次访问的热点仍保留在热队列。
>
> 两个队列都可以配合 HashMap 记录节点和所属队列，查找、移动和淘汰仍可做到 O(1)。经典 2Q 还可以保留一个只记录 Key 的 ghost 队列，帮助判断刚被淘汰的数据是否很快再次出现。这个方案靠访问历史自动识别热点，不需要业务侧提前打标。

### 22. InnoDB 如何避免全表扫描污染 Buffer Pool

**建议时长：45-60 秒**

**推荐回答：**

> InnoDB 不是把新读入的页直接放到严格 LRU 的最前端，而是把 LRU 列表划分成 young/new 和 old 两个区域。新页先插入 old 区域的头部，也就是整个列表的中间位置；只有它后续满足再次访问和时间条件，才晋升到 young 区域。
>
> 因此，全表扫描带入的大量一次性页面主要在 old 区域互相淘汰，不容易把 young 区域中的热点页全部冲掉。`innodb_old_blocks_pct` 控制 old 区域比例，`innodb_old_blocks_time` 控制页面过早晋升；调整参数前要结合真实 workload 压测，而不是机械修改默认值。

### 23. 共享屏幕中的表应该如何建索引

**建议时长：45-60 秒**

原始表结构和 SQL 未被录音捕获，只能给条件化回答。面试时应先复述 SQL，确认查询列、过滤条件、排序、返回行数和数据分布，再回答索引。

**推荐回答：**

> 如果 SQL 是 `WHERE id = ? AND component_id = ?`，并且 `id` 是主键，那么通过主键已经只能定位一行，通常不需要再建 `(id, component_id)` 联合索引来加速过滤；InnoDB 聚簇索引叶子节点已经包含整行，可以定位后直接判断 `component_id`。
>
> 如果存在只按 `component_id` 查询多行的场景，就应该为 `component_id` 建二级索引。二级索引叶子节点保存主键，查询其他非索引列时还需要回表；如果查询字段固定且回表成本明显，可以设计覆盖索引。如果实际 SQL 还有状态、时间范围或排序，则按“等值条件在前、范围/排序结合真实选择性”的原则设计联合索引，最后用 `EXPLAIN` 和数据量验证。

不要在题干不完整时直接说“联合索引一定有用”或“一定没用”。索引答案必须绑定具体 SQL 和数据分布。

### 24. 什么是 CDN，什么是 DNS

**建议时长：各 30-40 秒**

**CDN 推荐回答：**

> CDN 是内容分发网络。它把静态资源或可缓存内容分发到多个边缘节点，再通过 DNS 调度或 Anycast 等方式让用户访问更合适的节点。命中边缘缓存时不需要回源，可以降低网络 RTT、减轻源站压力，也能吸收一部分突发流量。
>
> CDN 的关键问题包括缓存 Key、TTL、回源、缓存失效和一致性。它不等于 DNS，也不只是防 DDoS；动态、个性化或强一致内容通常不能直接长期缓存。

**DNS 推荐回答：**

> DNS 是域名系统，把域名解析为 A/AAAA、CNAME、MX 等资源记录。客户端通常先查浏览器、系统和本地缓存，再向递归解析器查询；递归解析器在未命中缓存时，会从根、顶级域到权威 DNS 逐级获得答案，并按 TTL 缓存。
>
> DNS 查询常用 UDP，也支持 TCP。解析得到地址后，应用再按协议建立 TCP、TLS 或 QUIC 连接，所以不能固定说“DNS 后一定进行 TCP 三次握手”。

### 25. DNS 递归查询与迭代查询的区别

**建议时长：35-45 秒**

**推荐回答：**

> 递归查询要求被询问的 DNS 服务器替客户端查到底，最终返回完整答案或错误，不把“下一步问谁”交给客户端。迭代查询则是服务器如果没有最终答案，就返回一个更接近目标的 DNS 服务器地址，由查询方继续询问。
>
> 典型流程是：电脑上的 stub resolver 向本地递归解析器发递归请求；递归解析器再对根 DNS、顶级域 DNS、权威 DNS 做多次迭代查询。递归更方便客户端，但解析器承担更多工作；迭代把查询过程掌握在解析器手中，并可以结合缓存降低后续开销。

### 28. LRU 扫描污染推荐怎样设计

面试官给出的方向是双队列加晋升逻辑：新数据先在冷队列中停留，第二次访问后再晋升到主 LRU，避免一次性扫描污染热点。这个方向对应 2Q/分段 LRU。

更好的反问方式是先给自己的修正思路：

> 我刚才想到可以加一个小的准入队列，新数据第一次只进冷队列，二次命中再晋升到主 LRU。这样一万条单次扫描只会冲刷冷队列。请问您说的方案是否是类似 2Q 的思路？

## 五、本场最值得修正的回答

1. **不要把 MQ 的多个 ACK 混在一起。**生产者确认 Broker、消费者确认处理结果、Canal 保存 binlog 位点是三件不同的事。
2. **错误 ACK 后不能指望自动重试。**必须回答 offset/binlog 重放、数据库回填、版本控制和对账。
3. **RocketMQ PushConsumer 底层仍是客户端长轮询拉取。**现场回答“可以理解为推”不够准确。
4. **CRM 项目没有使用 Redisson。**真实实现是 Go Redis 客户端的 Pipeline + SetNX + Token + TTL + Lua；看门狗只能作为扩展知识。
5. **分布式锁的用途不是同步 Redis 多节点。**它解决的是多个进程对同一业务资源的互斥，Redis 主从切换反而是锁安全性的风险之一。
6. **第三次握手 ACK 丢失后不会立即失败。**服务端会重传 SYN+ACK，客户端再次 ACK，或者后续数据携带 ACK 完成建连。
7. **扫描污染的关键是准入策略。**不能依赖业务方提前标热点，应从访问历史自动晋升。
8. **遇到共享屏幕题先复述条件。**没有完整 SQL、索引和数据量时，不要急着给唯一答案。
