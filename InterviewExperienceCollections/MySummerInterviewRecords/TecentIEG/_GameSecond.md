## 一、这场面试的核心考察

这场二面没有算法题，主要围绕简历连续追问，考察点集中在四条主线：

1. 项目是否真正做过，能否说清个人贡献边界。
2. Redis 与 MySQL 的缓存一致性、并发回源、缓存穿透等系统设计问题。
3. Apollo 配置中心的实际改造内容，而不是只会说“热更新”。
4. HTTP、TCP/IP 分层、K8s 等基础知识和技术边界。

其中最需要复盘的是缓存一致性。正确主线应当是：**MySQL 是事实源，写请求优先更新数据库，提交成功后删除缓存；Binlog + MQ 用于异步失效、补偿和最终一致性。不要把“先更新缓存，再异步回写数据库”作为普通业务数据的默认方案。**

回答节奏建议：先用一句话给结论，再说明核心流程，最后主动补充失败场景和取舍。普通问题控制在 30～60 秒，系统设计题控制在 60～90 秒，等面试官追问后再展开。

### 4. 五分钟未支付自动回滚并释放库存，怎么实现

**建议时长：60～90 秒**

**参考回答：**

> 这类需求本质上是“延时触发 + 订单状态机 + 幂等补偿”。创建订单时，数据库先记录订单为 `UNPAID`，同时冻结或预扣库存，并发送一条以订单 ID 为业务键的延时消息，触发时间是创建时间加五分钟，具体时长应以项目配置为准。
>
> 消费者收到消息后不能直接取消，而要执行条件更新，例如 `UPDATE orders SET status = 'CANCELLED' WHERE id = ? AND status = 'UNPAID'`。只有更新成功，才说明取消逻辑赢得了与支付操作的竞争，随后释放库存。若影响行数为 0，说明订单已经支付或取消，消费者直接幂等返回。
>
> 还要考虑两类故障。第一，订单事务成功但消息没发出去，可以用 RocketMQ 事务消息或本地消息表 Outbox 保证最终发出；第二，消息重复或消费失败，要依赖状态机、唯一业务键、重试和死信处理保证幂等。最后再用定时扫描“已超时但仍未支付”的订单做兜底，避免单纯依赖 MQ。

**技术边界：**

- RocketMQ 5.x 支持按时间戳投递的定时/延时消息；较早版本常使用固定延迟级别。面试时应按项目实际版本回答。
- 支付和取消并发时，优先使用数据库条件更新或乐观锁决定唯一合法状态迁移，不要只依赖分布式锁。
- 库存释放必须幂等，否则重复消息可能造成库存重复增加。

### 5. Binlog 配合 RocketMQ 同步 MySQL 和 Redis，是什么意思

**建议时长：60～90 秒**

**参考回答：**

> 这条链路和“未支付订单延时取消”是两个不同场景。这里解决的是数据库变更后缓存如何最终失效。
>
> 写请求先提交 MySQL 事务。事务提交后，MySQL 会产生 Binlog；Canal 一类组件订阅行级变更，将包含表、主键和变更类型的事件发送到 RocketMQ。消费者按业务主键处理消息，删除对应 Redis Key，后续读请求缓存未命中，再从 MySQL 读取最新数据并重建缓存。我更倾向于“删除缓存”而不是直接更新缓存，因为删除能减少双写和乱序覆盖问题。
>
> 这个方案的优点是缓存同步和业务代码解耦，并且能覆盖其他程序直接修改数据库的场景；代价是只能做到最终一致性，还会引入消息延迟、重复、乱序和运维复杂度。因此需要保存 Binlog 位点或消费进度、保证 MQ 可靠投递、消费者幂等，并按主键保证同一条数据的事件有序。必要时还要做失败重试、死信告警和定期对账。

**追问边界：**

- 不要说“使用 MQ 就绝对不会丢消息”或“能保证强一致性”。
- 若业务只由单一服务写数据库，常规 Cache Aside 的“更新数据库后删除缓存”成本更低；Binlog + MQ 适合多写入口或需要统一异步失效的场景。
- 如果项目实际上只是阅读了已有实现，应说“项目采用该链路，我重点学习和验证了其流程”，不要说成自己从零搭建。

### 6. Redis 中的数据为什么一定要处理，不管它行不行

**建议时长：30～45 秒**

**参考回答：**

> 如果读路径是先查 Redis，缓存里存在旧值时，请求就不会再访问 MySQL，因此数据库虽然已经更新，用户仍会读到旧数据。所以可变业务数据更新后必须让缓存失效，或者明确接受一个有限的陈旧窗口。
>
> TTL 只能限制旧数据最长存在多久，不能替代一致性方案。对车次介绍等允许短暂陈旧的数据，可以用较短 TTL；对订单状态、余票等敏感数据，应在数据库提交成功后主动失效缓存，并配合重试或 Binlog 消息补偿。若要求严格强一致，关键读请求应直接读事实源或增加版本校验，而不是只依赖缓存。

### 7. Redis 中的数据有没有过期时间

**建议时长：20～30 秒**

**参考回答：**

> 有。写缓存时应根据业务设置 TTL，例如使用 `SET key value EX seconds` 或 `EXPIRE`。TTL 的主要作用是控制缓存生命周期、限制异常情况下的脏数据上界，并帮助淘汰冷数据。
>
> 但所有 Key 使用相同 TTL 可能造成同一时刻集中失效，引发缓存雪崩，所以通常会加随机抖动；热点数据还可以预热，或者采用逻辑过期配合异步重建。

### 8. 缓存不一致窗口有多长，怎么保证

**建议时长：60 秒**

**参考回答：**

> 先说结论：普通 MySQL + Redis 双写很难低成本做到严格强一致，通常保证最终一致性，并把不一致窗口控制在业务可接受范围内。
>
> 在“更新数据库，提交成功后删除缓存”的 Cache Aside 方案中，短暂窗口主要出现在数据库提交成功到缓存删除成功之间。如果删除成功，窗口通常只是一次网络调用的时间；如果删除失败，旧值可能一直保留到重试成功或 TTL 到期。因此我会把删除失败写入可靠重试链路，例如本地消息表或 Binlog + MQ，并配置最大重试、告警和对账。
>
> 还有一种低概率竞态：读线程缓存未命中并读到旧数据库值，写线程随后提交新值并删除缓存，最后读线程又把旧值回填。可以通过按 Key 的互斥重建、延迟二次删除、数据版本号或基于 Binlog 的再次失效降低风险。是否需要这些复杂度，要看业务对陈旧数据的容忍度。

### 9. TTL 是谁检查的

**建议时长：20 秒**

**参考回答：**

> 如果使用 Redis 原生 TTL，过期判断由 Redis 服务端维护，不需要业务请求自己解析一个时间字段。客户端读取已经过期的 Key 时会得到未命中，Redis 同时通过惰性删除和主动过期机制回收 Key。
>
> 只有采用“逻辑过期”方案时，业务 Value 里才会额外保存过期时间，由应用判断是否需要异步重建；这和 Redis 原生 TTL 是两套不同机制，不能混在一起回答。

### 10. TTL 是什么概念

**建议时长：15～20 秒**

**参考回答：**

> TTL 是 Time To Live，表示一个 Key 剩余的生存时间。可以用 `TTL` 查看秒级剩余时间，用 `PTTL` 查看毫秒级剩余时间。到期后，这个 Key 在读取语义上应当视为不存在。

**边界：** TTL 是缓存生命周期控制手段，不是数据库与缓存的版本号，也不能证明数据一定是新的。

### 11. Key 过期以后还在不在，Redis 怎么删除

**建议时长：30～45 秒**

**参考回答：**

> 从客户端语义看，Key 一旦过期就不可再读，会返回未命中；从内存回收时机看，它不一定在到期的那一毫秒立刻完成物理删除。
>
> Redis 主要结合两种方式：惰性删除是在客户端访问过期 Key 时发现并删除；主动过期是服务端周期性抽样检查带 TTL 的 Key 并清理。这样避免为了每个 Key 单独创建定时器，同时也避免永远不访问的过期 Key 长期占用内存。

**纠正原回答：** 不是由业务服务为每个缓存 Key 自己开线程扫描，也不是应用决定 Redis 永远不主动删除。

### 12. “检查过期”是单独开线程，还是请求到来时检查

**建议时长：30 秒**

**参考回答：**

> 原生 TTL 由 Redis 自己处理，业务层不需要额外开扫描线程。请求访问时会触发惰性检查，Redis 服务端还会进行主动过期抽样。
>
> 如果业务采用逻辑过期，则请求线程读到旧值后可以先返回旧数据，再提交一个异步重建任务；为了避免大量请求同时重建，需要用互斥锁或 singleflight 合并同一个 Key 的任务。逻辑过期适合允许短暂旧数据、但希望热点 Key 不直接失效的场景。

### 13. 缓存未命中时，完整读流程是什么

**建议时长：30～45 秒**

**参考回答：**

> 标准 Cache Aside 读流程是：先读取 Redis；命中就直接返回；未命中再查询 MySQL；数据库有值，就写入 Redis 并设置 TTL；数据库也没有，就缓存一个带较短 TTL 的空值，或者先经过布隆过滤器，再返回不存在。
>
> 对 Redis 原生过期 Key，不需要先执行一次 `DEL`，因为读取时已经按不存在处理。对热点 Key，还要在查询数据库前做双重检查：先抢重建锁，抢到后再次查缓存，仍未命中才访问数据库，避免重复回源。

### 14. 多个并发请求同时缓存未命中，会发生什么

**建议时长：45～60 秒**

**参考回答：**

> 如果不做保护，多个请求会同时查 MySQL，并分别回写 Redis。普通冷 Key 可能只是多几次查询，但热点 Key 过期时会形成缓存击穿，瞬间把压力打到数据库。
>
> 单实例内可以用 singleflight 或按 Key 的本地互斥锁合并请求；多实例下可以使用带超时和唯一标识的分布式锁。抢到锁的线程再次检查缓存，再回源并重建；其他线程可以短暂等待、快速失败，或者在逻辑过期方案下先返回旧值。
>
> 如果回源期间还可能发生写操作，仅靠重建锁不够，还应给数据携带版本号，或在数据库变更后再次发送缓存失效事件，防止旧查询结果覆盖新值。

### 15. 更新数据时，先更新 MySQL 还是 Redis

**建议时长：45～60 秒**

**参考回答：**

> 对普通 Cache Aside，我会把 MySQL 作为事实源，采用“先更新数据库，事务提交成功后删除缓存”，而不是同时更新两份数据。
>
> 先删缓存再更新数据库存在明显竞态：缓存刚删掉，另一个读请求可能从尚未更新的数据库读出旧值并重新写回缓存。先更新缓存再更新数据库也有问题：数据库更新失败时，缓存反而比事实源更新，后续恢复和审计都困难。
>
> 数据库更新成功但缓存删除失败时，要通过重试、Outbox 或 Binlog + MQ 再次删除，并用 TTL 作为最后兜底。这个方案追求的是可控的最终一致性，不是无条件强一致。

### 16. 先更新 Redis，随后更新 MySQL 失败，怎么办

**建议时长：30～45 秒**

**参考回答：**

> 这正是我不选择“先更新缓存、再更新数据库”的原因。此时 Redis 已经是新值，而 MySQL 仍是旧值，缓存变成了未经数据库提交确认的数据源。如果再异步把缓存内容写回数据库，还可能覆盖期间发生的合法更新。
>
> 更合理的处理是让数据库先完成事务提交，成功后只删除缓存；数据库失败就不动缓存。如果确实是 Write-Behind 这类以缓存为入口的专门架构，就必须有持久化日志、顺序写、版本控制、失败重放和数据恢复设计，不能临时开一个线程回写。

### 17. 异步补偿与新的更新请求如何协调

**建议时长：45～60 秒**

**参考回答：**

> 我不会让一个普通异步线程拿着 Redis 的值无版本地回写数据库。更稳妥的方式是让补偿任务处理“已经在数据库提交过的变更事件”，事件至少包含业务主键、操作类型和版本或 Binlog 顺序信息。
>
> 同一业务主键的事件应路由到同一有序队列，消费者做幂等处理；落库或更新缓存时使用版本比较，只允许新版本覆盖旧版本。这样即使消息重复或晚到，也不会把新数据回滚成旧数据。
>
> 对订单状态，直接使用数据库条件更新控制合法状态迁移；对缓存同步，通常删除缓存比回写具体值更不容易受到消息乱序影响。

### 18. 并发冲突依靠什么机制控制

**建议时长：45～60 秒**

**参考回答：**

> 要按冲突类型选择机制。订单支付和取消竞争时，优先用数据库状态机和条件更新，例如 `WHERE status = 'UNPAID' AND version = ?`，由影响行数判断谁成功；InnoDB 会对命中的索引记录加锁，但业务仍要通过状态条件保证迁移合法。
>
> 对缓存重建，可以按 Key 使用本地 singleflight 或分布式互斥锁，避免同时回源。分布式锁需要唯一 token、过期时间和比较 token 后再释放；任务可能超过租期时还要考虑续期或 fencing token。
>
> 对 MQ 重复和乱序，核心是业务幂等、唯一键、版本号和同 Key 有序，而不是给所有流程套一把大锁。锁解决互斥，不自动解决消息丢失、进程宕机和旧任务晚到。

### 19. 缓存的本质是不是降低数据库压力，还能保证一致性吗

**建议时长：30 秒**

**参考回答：**

> 缓存的主要价值是降低数据库读压力和访问延迟，也可以吸收热点流量；它本身不是用来“保证一致性”的，反而会引入第二份数据和一致性问题。
>
> 因此要先定义业务目标：哪些数据允许秒级陈旧，哪些必须读事实源，再决定 TTL、主动失效、消息补偿或版本校验。不能同时笼统承诺“高性能”和“强一致”。

### 20. 数据不存在却有大量请求查询，怎么办

**建议时长：45～60 秒**

**参考回答：**

> 这是缓存穿透：请求的 Key 在 Redis 和数据库里都不存在，导致每次缓存未命中后都访问数据库。
>
> 第一种方案是缓存空值，并设置较短 TTL，适合不存在 Key 数量有限、数据可能后来创建的场景。第二种方案是在入口使用布隆过滤器，先判断 ID 是否可能存在；它可能有假阳性，但不会有假阴性，仍要保留数据库和空值兜底。对于明显恶意的随机请求，还要配合参数校验、鉴权、限流和黑名单。
>
> 方案选择要看数据规模和更新频率。布隆过滤器本身也要考虑数据新增时同步更新，以及过滤器重建期间的一致性。

### 21. 缓存穿透主要对谁造成压力

**建议时长：20 秒**

**参考回答：**

> 请求首先会消耗 Redis 的 QPS 和网络资源，但真正危险的是每次 Redis 未命中后继续访问 MySQL，因此主要风险是数据库被大量无效查询打满。原回答只说“对 Redis 造成压力”不完整，应该把完整请求链路讲出来。

### 22. 缓存空值后，数据后来被创建怎么办

**建议时长：45 秒**

**参考回答：**

> 空值必须设置较短 TTL，不能永久缓存。创建数据时，先提交 MySQL 事务，成功后删除对应的空值缓存；下一次查询再从数据库加载真实数据。若系统采用 Binlog + MQ，也可以让 `INSERT` 事件触发该 Key 的失效。
>
> 不建议先把真实值写入 Redis 再写 MySQL，因为数据库失败会造成缓存里出现一条实际不存在的数据。如果担心删除缓存失败，应使用可靠重试和 TTL 兜底。并发场景下可以给事件携带版本，避免迟到的空值写入覆盖真实值。

### 23. “优化携程 Apollo 配置中心方案”具体做了什么

**建议时长：60～90 秒**

**参考回答：**

> 这里的“携程”指携程开源的 Apollo，不是优化 Go 协程，也不是修改 Apollo 或 gconf 的底层源码。公司已经有基于 Apollo Go 客户端封装的 gconf 组件，我负责的是客服系统业务侧的接入和热更新逻辑。
>
> 原来一些游戏 GM 域名、接口地址、业务参数和 Worker 配置分散在代码或本地配置中，修改后需要重新发布服务。我基于 gconf 的 `BindConfig` 接入多个 Namespace，把不同业务配置绑定到对应 Go 结构体，并实现相应的 `ChangeListener`。
>
> 配置在 Apollo 发布后，客户端通过 HTTP Long Polling 收到变更通知，再拉取新配置并触发 `OnChange`。监听器先解析和校验新值，成功后整体替换内存配置；对于 Worker 配置会触发 reload，对于 CRM/VIP 规则类配置会清理相关缓存。这样配置变更可以在不重启服务的情况下生效。
>
> 这里还要注意并发安全：不能简单说“普通全局指针赋值就绝对线程安全”。更严格的实现应使用不可变配置对象配合 `atomic.Pointer`，或者用 `RWMutex` 保护读写；新配置解析失败时保留旧配置，同时记录日志和告警。

**个人贡献边界：**

- Apollo 和 gconf 是已有基础设施。
- 可辩护的个人工作是多 Namespace 业务接入、配置绑定、OnChange 监听，以及配置变化后的缓存清理或 Worker reload。
- Namespace 的具体数量在现有记录中存在 7/8 不一致，面试时说“多 Namespace”，除非已回看真实 `init.go` 确认。

### 24. 项目用了哪些网络协议，最常用哪个

**建议时长：30～45 秒**

**参考回答：**

> 我会先区分层次。业务接口层面使用最多的是 HTTP/HTTPS，例如客服系统调用游戏 GM 后台接口；传输层通常是 TCP，HTTPS 还会在其上使用 TLS。项目使用 MySQL、Redis 等中间件时，客户端库还会通过各自的应用层协议与服务端通信。
>
> 所以不能把 HTTP 说成“网络层协议”。如果面试官问最常用的业务协议，我回答 HTTP/HTTPS；如果问底层传输，则需要结合具体连接回答 TCP，HTTP/3 场景则是 QUIC 运行在 UDP 之上。

### 25. TCP/IP 网络分层怎么划分

**建议时长：45 秒**

**参考回答：**

> 工程面试中我通常按五层模型回答：
>
> 第一层是应用层，例如 HTTP、DNS、Redis 协议；第二层是传输层，例如 TCP、UDP，负责端到端传输；第三层是网络层，核心协议是 IP，负责寻址和路由；第四层是数据链路层，例如以太网，负责同一链路上的帧传输；第五层是物理层，负责比特在介质上的传输。
>
> OSI 七层模型会把五层模型中的应用层进一步拆成应用层、表示层和会话层。实际排障时，我会沿着“域名解析、连接建立、TLS、HTTP、业务处理”逐层定位，而不是只背层数。

### 26. 项目使用哪个 HTTP 版本，怎么确认

**建议时长：30～45 秒**

**参考回答：**

> 这个问题不能只凭业务代码猜。应用代码调用的是 HTTP/HTTPS，但最终使用 HTTP/1.1、HTTP/2 还是其他版本，取决于客户端库、服务端、网关以及 TLS ALPN 协商结果，而且服务不同链路的版本可能不一样。
>
> 如果现场没有核实过，我会明确说“当时没有确认具体版本”，然后说明验证方法：查看客户端 Transport 和网关配置，检查响应中的协议字段，使用 `curl -v`，或者抓包观察 ALPN 和连接复用情况。面试里承认未验证，比随口说一个版本更可靠。

### 27. HTTP/1.0、1.1、2、3 的主要差异

**建议时长：60～90 秒**

**参考回答：**

> HTTP/1.0 和 1.1 的核心差异不只是“短连接和长连接”。HTTP/1.1 默认使用持久连接，多个请求可以复用同一条 TCP 连接；它要求 `Host` 头，支持同一 IP 上的虚拟主机；还标准化了分块传输等能力。HTTP/1.0 也可以通过扩展的 `Connection: keep-alive` 复用连接，所以不能绝对说 1.0 一定每次断开。
>
> HTTP/1.1 虽然可以复用连接，但同一连接上的请求响应仍容易受到队头阻塞影响。HTTP/2 引入二进制分帧、一个连接上的多路复用和 HPACK 头部压缩，但它仍运行在 TCP 上，丢包时可能影响同一连接的多个流。
>
> HTTP/3 把 HTTP 映射到 QUIC 上。QUIC 基于 UDP，在用户态实现可靠传输、加密和多路复用，不同流之间能减少 TCP 层面的队头阻塞，并改善连接迁移和握手延迟。它不是简单地把 HTTP 改成“不可靠 UDP”。

### 28. 是否接触过容器、K8s 和灰度发布

**建议时长：30～45 秒**

**参考回答：**

> 实习项目的部署环境使用了 K8s，也涉及灰度发布，但我当时是业务开发实习生，没有集群和发布平台权限，没有亲自编写生产环境的资源清单或操作集群。所以我会把边界说清楚：项目“使用了 K8s”，不等于我“负责了 K8s 运维”。
>
> 我目前理解 Pod 是最小调度单元，Deployment 管理副本和滚动更新，Service 提供稳定服务发现，Ingress 负责入口流量，ConfigMap/Secret 管理配置，readiness/liveness probe 参与流量接入和故障恢复。后续我会通过本地集群实际部署一个服务，把镜像构建、滚动发布、探针和回滚链路走通。

**不要硬答：** 若未真正操作过，就不要声称做过集群扩缩容、故障处理或生产灰度。

### 29. 反问：游戏中台岗位具体负责哪些业务

**面试官回答摘要：**

> 团队属于技术运营方向，为游戏业务工作室提供从开发、运营到运维的一整套平台能力，涉及底层数据、运营和监控等多个方面。当前岗位偏运维管控系统开发，主要包括资源管控、远程命令控制、节点控制等，是偏底层通道和控制面的服务。

**更好的追问方式：**

这样能继续问出实际业务场景、技术挑战和岗位预期，比只问“具体做什么”更有信息量。

### 30. 反问：AI、Agent 是否与岗位提效相关，是否值得深入学习

**面试官回答摘要：**

## 四、这场面试中原回答的关键问题

### 1. 把 Redis TTL 说成业务自己检查

Redis 原生 TTL 由服务端维护，并结合惰性删除和主动过期回收 Key。只有逻辑过期方案才需要应用读取过期时间并触发重建。两者必须分开。

### 2. 把“先更新缓存”当成一致性修复

普通 Cache Aside 应以 MySQL 为事实源，先提交数据库，再删除缓存。先更新缓存再更新数据库会在数据库失败时产生更难处理的不一致。

### 3. 用临时异步线程回写数据库

临时线程没有持久化、顺序、重试和幂等保障，进程重启后任务也会丢失。应使用可靠消息、Outbox、Binlog 事件或定时对账，并通过版本和状态机控制并发。

### 4. 说缓存穿透主要压 Redis

Redis 会消耗 QPS，但穿透的核心风险是每次未命中都继续查询 MySQL，最终把数据库打满。

### 5. 没有区分“使用”和“亲自负责”

项目部署在 K8s，不等于自己负责 K8s；公司已有 gconf，不等于自己开发 gconf；基于开源项目学习，不等于独立设计了完整 12306。二面很看重这种边界意识。

## 五、建议重点背熟的三段话

### 1. 缓存更新策略

> MySQL 是事实源，我采用 Cache Aside：读时先查缓存，未命中再查数据库并回填；写时先提交数据库，再删除缓存。删除失败通过可靠消息或 Binlog + MQ 重试，TTL 只做最后兜底。这个方案保证的是可控的最终一致性，不是无条件强一致。

### 2. 并发缓存重建

> 热点 Key 失效时，多个请求会同时回源形成缓存击穿。单实例可以用 singleflight，多实例可以按 Key 加分布式互斥锁；抢到锁后要再次检查缓存，再查询数据库并回填。若回源期间可能发生写入，还要通过版本号或后续失效事件防止旧值覆盖新值。

### 3. Apollo 个人贡献

> Apollo 和 gconf 是公司已有能力，我负责业务侧多 Namespace 接入和热更新处理：基于 BindConfig 绑定配置，实现 OnChange 监听，新配置校验成功后替换内存对象，并联动清理缓存或 reload Worker。严格并发场景应使用 atomic.Pointer 或 RWMutex，解析失败则保留旧配置。
