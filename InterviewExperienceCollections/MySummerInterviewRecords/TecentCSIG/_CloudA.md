## 二、本场面试暴露出的主要问题

1. **项目事实没有准备到监控口径。** 项目已经内部上线，但 QPS、ZSet 大小、单批耗时和积压量没有数据。不了解可以诚实说明，但至少要区分“接口 QPS”“待调度任务量”和“同时到期量”。
2. **扩容方案没有贴合定时任务的查询模式。** 现场直接回答一致性哈希和二分查找，但该任务首先需要按时间找出所有到期项。更合适的是“时间分桶 + 桶内哈希分片”，否则每轮仍要扫描全部分片。
3. **混淆了 Pipeline、Lua 和分布式锁。** Pipeline 只减少网络往返，不保证多条命令原子性；Lua 用于把“校验锁所有者 + 删除锁”合成原子操作。它们不是两种锁。
4. **红包题缺少正确性主线。** 网关不能为了降低并发随意丢弃合法抢红包请求。应该先讲限流防刷，再讲 Redis Lua 原子扣减，最后用数据库状态机、唯一约束、幂等和对账兜底。
5. **把三条消息链路混在了一起。** `binlog + Canal + MQ` 是缓存最终一致性链路；RocketMQ 事务消息解决“本地事务与发消息”的一致性；延迟消息用于未支付订单关闭。三者不能混答。
6. **Go 和容器基础准备不足。** `make/new`、`defer`、goroutine/channel、Go GC、镜像/容器均属于 Go 后端岗位的基础题，应该控制在 40 到 60 秒内答清结论、机制和边界。
7. **算法编码节奏偏慢。** N 叉树题开始按二叉树理解，LRU 指针操作边写边想。更稳妥的方式是先确认数据结构和接口，再口述不变量，最后编码。

### 3. 请展开介绍基于 Redis ZSet 的定时解封任务

**建议时长：90 到 120 秒**

> 这个需求的背景是，客服或风控人员会把存在支付风险的玩家临时加入黑名单。封禁有明确到期时间，因此系统需要自动解封，避免依赖人工操作。
>
> 我把解封时间戳作为 ZSet 的 `score`，把能够唯一标识玩家和项目的值作为 `member`。定时任务通过 `ZRANGEBYSCORE key -inf now LIMIT 0 100` 分批取出已经到期的记录。这里 ZSet 的价值不只是“Redis 快”，而是它把时间变成了可排序、可范围查询的索引，查询复杂度是 `O(log N + M)`，其中 `M` 是本批返回数量。
>
> 多实例部署下，多个任务实例可能同时扫描到同一条记录，所以实现中有调度协调和记录级互斥。真正的正确性还不能只依赖锁：解封接口本身应该幂等，成功后再确认任务完成，失败要能够重试或进入补偿队列。

**技术边界：** 当前代码复盘显示原实现存在“先 `ZREM`，再调用下游解封接口”的顺序。如果 `ZREM` 成功后进程崩溃，任务可能永久丢失。更稳妥的方式是原子地把任务从待处理集合移动到 `processing` 集合，业务成功后 ACK 删除；超出可见性超时的任务重新投递。

### 6. 百万条任务同时到期时有哪些瓶颈和异常风险

**建议时长：90 秒**

> 我会先把问题拆成“取任务、处理任务、失败恢复”三段。取任务阶段，一个大 ZSet 会成为单分片热点，单次取太多还会带来网络包和客户端内存压力；每次只取 100 条虽然保护了 Redis，但百万条会形成很长的积压。处理阶段真正的瓶颈往往是下游 API 和数据库，而不是 `ZRANGEBYSCORE` 本身。失败恢复阶段，如果先删任务再执行业务，实例崩溃会丢任务；如果先执行再删，又可能重复处理。
>
> 我的改造会是：第一，按批拉取并使用有界 Worker Pool，依据下游容量控制并发；第二，原子认领任务，使用 `pending -> processing -> done` 状态和可见性超时；第三，业务接口按业务键幂等，失败做指数退避、最大重试和死信补偿；第四，监控 backlog、最老任务延迟、成功率和重试量。
>
> 如果规模长期达到百万级同时到期，我会重新评估 ZSet 轮询是否还是合适，可能改为按时间分桶的多分片调度，或者使用支持延迟投递和消费扩展的消息队列，而不是只把一个大 Key 机械拆开。

### 7. 除了拆大 Key，还有哪些扩容和积压处理方案

**建议时长：60 到 90 秒**

> 一致性哈希并不是这个场景的第一答案，因为查询目标是“所有已经到期的任务”。如果只按用户哈希，调度器每轮仍然要扇出扫描全部分片。
>
> 更匹配查询模式的设计是“时间分桶 + 桶内哈希分片”。例如 Key 设计为 `unlock:{yyyyMMddHH}:{shard}`：调度器只扫描当前和历史未清空的时间桶，桶内再按 `hash(userId) % P` 分散热点。为了以后扩容，可以预先定义较多逻辑分片，再把逻辑分片映射到少量物理消费者，扩容时只调整映射，避免搬迁全部数据。
>
> 另外还要增加批处理、消费并行度、下游限流、重试和对账。拆 Key 只解决 Redis 热点，不能自动解决下游吞吐和任务可靠性。

### 8. Redis Pipeline 和 Lua 分别有什么作用，为什么一起使用

**建议时长：90 秒**

> 这里需要先澄清：Pipeline 和 Lua 不是两种分布式锁，而是同一套用户级锁方案中的性能组件和正确性组件。
>
> 加锁时，每个用户对应一个锁 Key，使用 `SET key token NX PX ttl`。一批用户需要加锁时用 Pipeline 一次发送多条命令，减少网络往返；但 Pipeline 不保证整批命令原子执行，每条 `SET NX` 只保证自己这一条命令原子。
>
> 释放锁时不能直接 `DEL`，因为实例 A 的锁可能已经过期，实例 B 又获得了同名锁。A 再执行 `DEL` 会误删 B 的锁。因此要用 Lua 把“`GET` 校验 token”和“`DEL`”合成一个不可被其他命令插入的原子操作：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

> Pipeline 的优点是降低 RTT，缺点是不提供事务语义且批次过大会占用客户端和服务端缓冲区；Lua 的优点是支持条件判断和原子读改写，缺点是长脚本会阻塞 Redis。Redis Cluster 下，脚本涉及的多个 Key 还必须位于同一个 hash slot。

**另一层口径：** 黑名单定时任务中还有“全局调度锁 + 单记录锁”。全局锁减少多实例重复扫描，记录锁防止同一玩家被重复处理。两层锁是性能优化和细粒度兜底，但最终仍要依赖幂等和补偿。

### 9. 除了 Redis 方案，还了解哪些分布式锁

**建议时长：60 秒**

> 常见方案有三类。第一类是 Redis 锁，性能高、接入简单，适合允许短暂重复并且业务有幂等兜底的场景；需要处理唯一 token、TTL、续期、主从切换和误删锁。Redisson 是 Redis 锁的成熟客户端实现，不是另一种共识系统。
>
> 第二类是 ZooKeeper 或 etcd。它们基于临时节点或 Lease、版本号和一致性协议，协调语义更强，还能用 revision 生成 fencing token；代价是延迟和运维复杂度更高。第三类是数据库行锁、唯一约束或条件更新，优点是和业务数据处于同一个事务边界，低并发时简单可靠，缺点是高竞争下容易把数据库变成瓶颈。
>
> 选型不能只看“哪把锁更强”，要看故障模型。涉及资金和库存时，我不会把 Redis 锁当成唯一正确性边界，还会使用数据库状态机、条件更新、唯一约束、业务幂等键和对账。

### 10. 红包系统适合使用什么方案

**建议时长：90 到 120 秒**

> 红包系统不应该只回答“用某一种锁”。我会按流量入口、资格与库存、最终账务三层设计。
>
> 入口层做用户级限流、防刷和请求幂等，但不会随机丢弃合法请求。Redis 层使用 Lua 在一个脚本内完成“校验活动、校验一人一次、判断剩余数量、扣减库存、记录领取结果”，或者预先拆分红包金额后原子弹出，这样一次请求不需要获取粗粒度分布式锁。成功结果再通过 MQ 异步写入领取记录和后续通知。
>
> 数据库保存最终账务事实，使用业务唯一键防止重复入账，并通过事务和条件更新维护状态。消费者必须幂等，异常消息重试后进入死信队列，还需要定时对账修正 Redis 与账务库的差异。

**边界：** Redis Lua 能保证同一 Redis 执行环境内脚本原子，但不能单独保证跨 Redis、数据库和 MQ 的全局原子性。资金正确性最终要落在账务事务、幂等和对账上。

### 11. 乐观锁具体怎样实现

**建议时长：60 秒**

> 乐观锁的核心是假设冲突不多，更新时再检查“我读到的数据是否仍然是最新版本”。例如红包表有 `remaining` 和 `version`：

```sql
UPDATE red_packet
SET remaining = remaining - 1,
    version = version + 1
WHERE id = ?
  AND remaining > 0
  AND version = ?;
```

> 受影响行数为 1 表示扣减成功；为 0 表示库存已不足或版本发生变化，需要重新读取后有限次重试。其实如果只做库存扣减，也可以直接使用 `UPDATE ... SET remaining = remaining - 1 WHERE remaining > 0`，让一条 SQL 原子完成校验和更新，不一定非要显式版本号。
>
> 乐观锁适合冲突概率不高的场景。红包尾部库存竞争非常激烈时，大量 CAS 重试会放大数据库压力，因此更常见的是 Redis 原子预扣减或按红包 ID 串行化消费，数据库负责最终落账。

>
> 需要特别区分三条链路：`binlog + Canal + MQ` 用于 CDC 和缓存同步；RocketMQ 事务消息用于协调“应用本地事务 + 发消息”；延迟消息用于订单超时关闭。订单十分钟未支付的处理应该是延迟消息到期后重新查询订单状态，再用条件更新把 `UNPAID` 改为 `CANCELLED`，而不是让延迟队列决定支付事务是否提交。

### 19. Go 中 `make` 和 `new` 有什么区别

**建议时长：40 秒**

> `new(T)` 可以用于任意类型，它分配一块零值内存并返回 `*T`。例如 `new(int)` 返回 `*int`，指向的值是 0。
>
> `make` 只用于 `slice`、`map` 和 `channel`，它会初始化这些类型所需的运行时结构，并直接返回 `T`，不是 `*T`。例如 `make(map[string]int)` 得到可以直接写入的 map；而 `new(map[string]int)` 得到的是指向 nil map 的指针，仍然不能直接写入，通常没有实际意义。

```go
p := new(int)             // *int，*p == 0
m := make(map[string]int) // map，可直接 m["a"] = 1
s := make([]int, 3, 8)    // len=3, cap=8
ch := make(chan int, 10)  // 容量为 10 的有缓冲 channel
```

### 20. Go 中 `defer` 的执行规则是什么

**建议时长：45 到 60 秒**

> `defer` 把一次函数调用延迟到当前函数返回前执行，正常 `return`、执行到函数末尾，或者当前 goroutine 发生 panic 展开栈时都会执行。多个 `defer` 按后注册先执行，也就是 LIFO。
>
> `defer` 语句执行时，函数值和实参就已经求值；如果函数有命名返回值，deferred function 可以在真正返回前修改它。常见用途是 `defer file.Close()`、`defer mu.Unlock()`。
>
> `recover` 只有在 deferred function 中、并且当前 goroutine 正处于 panic 展开过程中才有意义。普通业务错误仍然应该返回 `error`，不能把 `panic/recover` 当成日常异常处理。

### 21. 怎样理解 goroutine 和 channel

**建议时长：60 秒**

> goroutine 是由 Go runtime 调度的轻量级并发执行单元，多个 goroutine 会复用到多个 OS 线程上。它适合高并发 I/O，但“轻量”不等于可以无限创建，生产中仍要用 Worker Pool、Semaphore 或有界队列限制并发，并通过 `context` 处理超时和取消。
>
> channel 是带类型的通信与同步机制。无缓冲 channel 的发送和接收需要双方同时就绪，既传数据也完成同步；有缓冲 channel 在缓冲区未满或非空时可以暂时解耦生产者和消费者。关闭 channel 应由发送方负责，接收方使用 `v, ok := <-ch` 判断是否关闭。
>
> Go 鼓励“通过通信共享内存”，但不是所有共享状态都必须使用 channel。简单计数器或短临界区使用 `sync.Mutex`、原子变量往往更直接。

### 22. Go 的垃圾回收机制是什么

**建议时长：60 到 90 秒**

> Go 标准工具链使用并发、非移动的标记清扫 GC。GC 从全局变量、goroutine 栈等根对象出发，追踪可达对象并标记，之后回收不可达对象占用的堆空间。工程上常用三色标记来理解并发标记过程，写屏障用于保证应用线程修改指针时不会漏标活对象。
>
> GC 不是全程 Stop-The-World，但在某些阶段仍有短暂停顿。运行时的 pacer 会根据存活堆、分配速度、`GOGC` 和内存限制决定触发时机，并让应用 goroutine 分担一部分标记工作。
>
> 排查 GC 问题时我会先看分配速率、堆大小、GC CPU 占比和暂停时间，再用 pprof 找热点分配。优化重点通常是减少不必要的堆逃逸、临时对象和大对象生命周期，而不是一上来手动调低 GC 频率。

### 23. Docker 镜像和容器有什么区别

**建议时长：40 秒**

> 镜像是只读、分层的运行模板，包含应用、依赖、配置和文件系统内容；容器是镜像启动后的可运行实例，本质上是受 namespace、cgroup 等机制隔离和限制的进程，并在镜像层之上增加可写层。
>
> 一个镜像可以启动多个相互隔离的容器。删除容器不会删除镜像，但容器可写层中的数据会丢失，所以持久化数据应该放到 Volume 或外部存储中。镜像回答“拿什么启动”，容器回答“正在运行的实例是什么”。

### 24. MySQL 事务的 ACID 分别是什么，InnoDB 怎样支持

**建议时长：60 到 90 秒**

> `A` 是原子性，一组操作要么全部成功，要么全部失败。InnoDB 通过事务状态和 undo log 支持回滚，崩溃恢复还需要 redo/undo 协同。
>
> `C` 是一致性，事务前后数据必须满足主键、唯一键、外键和业务不变量。它不是由某一个日志单独实现，而是原子性、隔离性、持久性、数据库约束和正确业务逻辑共同保证的结果。
>
> `I` 是隔离性，并发事务之间的中间状态不应随意互相影响。InnoDB 通过 MVCC、行锁、间隙锁等机制实现不同隔离级别。`D` 是持久性，事务提交后结果在故障后仍可恢复，核心是 WAL 和 redo log；具体强度还受 `innodb_flush_log_at_trx_commit`、存储设备和 `fsync` 行为影响。如果启用 binlog，`sync_binlog` 也影响 binlog 的持久性。

### 25. InnoDB 使用什么数据结构作为索引

**建议时长：60 秒**

> InnoDB 的普通索引在面试中通常称为 B+ 树。非叶子页主要保存键和子页指针，叶子页保存索引记录；页是磁盘和缓冲池管理的基本单位，默认页大小通常是 16 KiB。叶子页按键有序并相互链接，因此既适合等值查询，也适合范围扫描。
>
> 聚簇索引的叶子页保存完整行数据，通常按主键组织；二级索引的叶子页保存二级索引列和主键值。使用二级索引查询其他列时，通常还要拿主键回到聚簇索引查一次，也就是回表；覆盖索引可以避免回表。
>
> B+ 树层数不是固定三层，取决于页大小、键宽、行大小和数据量。主键过长会放大所有二级索引，随机主键还更容易引起页分裂，因此通常倾向较短且趋势递增的主键。

### 27. Redis 为什么性能高，为什么适合做缓存

**建议时长：60 秒**

> 第一，Redis 的主要数据集在内存中，避免了数据库随机磁盘访问；第二，它为不同场景提供了经过优化的数据结构，大多数常用操作是 `O(1)` 或 `O(log N)`；第三，它采用事件驱动和 I/O 多路复用处理大量连接，命令执行大体串行，减少了共享数据结构上的锁竞争；第四，协议简单，并支持 Pipeline、批量命令和 Lua，能够减少网络往返。
>
> 它适合缓存还因为支持 TTL、过期删除、内存淘汰策略、主从和集群。但“命令串行”既是优点也是边界：大 Key、`O(N)` 慢命令和长 Lua 脚本都会阻塞其他请求。Redis 也不是因为有持久化就能替代所有数据库；作为缓存时，MySQL 等持久化数据库通常仍是事实源。

### 28. MySQL、Redis、MongoDB 的差异和适用场景

**建议时长：90 秒**

> MySQL 是关系型数据库，强调结构化 Schema、事务、约束、关联查询和可靠持久化，适合订单、账户、库存等需要 ACID 和复杂关系的数据。
>
> Redis 是内存数据结构存储，延迟低，适合缓存、计数、排行榜、限流、会话和临时协调数据。它可以持久化，但内存成本、淘汰策略和故障语义决定了它通常不应作为资金数据的唯一事实源。

### 29. 求一棵 N 叉树的最大深度

**建议讲解：60 秒；编码：5 到 8 分钟**

> 我先确认这是 N 叉树而不是二叉树。可以用 BFS 按层遍历：根节点入队，每轮先记录当前层节点数，只处理这一层，并把所有非空子节点加入队列；每处理完一层，深度加一。根节点为空返回 0。每个节点只入队出队一次，时间复杂度 `O(n)`，空间复杂度是 `O(w)`，`w` 为树的最大宽度。

```java
import java.util.ArrayDeque;
import java.util.List;
import java.util.Queue;

class Node {
    int val;
    List<Node> children;

    Node(int val, List<Node> children) {
        this.val = val;
        this.children = children;
    }
}

class Solution {
    public int maxDepth(Node root) {
        if (root == null) {
            return 0;
        }

        Queue<Node> queue = new ArrayDeque<>();
        queue.offer(root);
        int depth = 0;

        while (!queue.isEmpty()) {
            int levelSize = queue.size();
            for (int i = 0; i < levelSize; i++) {
                Node current = queue.poll();
                if (current.children == null) {
                    continue;
                }
                for (Node child : current.children) {
                    if (child != null) {
                        queue.offer(child);
                    }
                }
            }
            depth++;
        }
        return depth;
    }
}
```

**边界用例：** 空树、只有根节点、链状 N 叉树、某些节点的 `children` 为 `null`、子节点列表中含 `null`。

### 30. 实现 LRU Cache

**建议讲解：90 秒；编码：12 到 18 分钟**

> LRU 要同时满足“按 Key `O(1)` 查找”和“`O(1)` 调整最近使用顺序”，因此使用 HashMap 加双向链表。Map 从 Key 定位节点；链表头部表示最近使用，尾部表示最久未使用。`get` 命中后把节点移到头部；`put` 更新已有节点并移到头部，或者插入新节点；容量超限时删除 `tail.prev`，并同步从 Map 移除。头尾哨兵节点可以统一空链表和边界节点的指针操作。

```java
import java.util.HashMap;
import java.util.Map;

class LRUCache {
    private static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> cache = new HashMap<>();
    private final Node head = new Node(0, 0); // head.next 是 MRU
    private final Node tail = new Node(0, 0); // tail.prev 是 LRU

    public LRUCache(int capacity) {
        if (capacity < 0) {
            throw new IllegalArgumentException("capacity must be non-negative");
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = cache.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = cache.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }

        Node created = new Node(key, value);
        cache.put(key, created);
        addAfterHead(created);

        if (cache.size() > capacity) {
            Node removed = tail.prev;
            remove(removed);
            cache.remove(removed.key);
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}
```

> `get` 和 `put` 的平均时间复杂度都是 `O(1)`，空间复杂度 `O(capacity)`。这份实现不是线程安全的；生产并发场景需要额外同步，或者使用经过验证的缓存库。若题目允许直接使用 JDK，也可以说明 `LinkedHashMap(accessOrder=true)` 能实现 LRU，但手写题通常希望考察 Map 与双向链表。

**建议现场自测：**

```text
LRUCache(2)
put(1,1), put(2,2), get(1) -> 1
put(3,3), get(2) -> -1
put(4,4), get(1) -> -1, get(3) -> 3, get(4) -> 4
```
