### 6. Agent 项目的端到端流程是什么

**建议时长：75 秒。**

我按用户视角把它分成七步：

1. 用户先选择或配置 Agent，例如系统提示、模型参数、可用知识库和工具权限。
2. 用户提交自然语言任务，后端创建一次会话或任务，并完成鉴权和参数校验。
3. 如果任务需要私有知识，系统先对问题做检索，把命中的文档片段连同用户问题一起组装进模型上下文。
4. Host 把可用工具的名称、描述和参数 Schema 一并提供给模型。
5. 模型可以直接生成回答，也可以输出结构化的工具调用请求。
6. 应用校验工具名、参数和权限，再通过本地函数或 MCP 客户端调用外部服务；工具结果作为新的上下文返回给模型。
7. 模型基于工具结果生成最终回答。若工具失败，则按策略重试、降级或返回明确错误；发布文章等有副作用的操作还应要求用户确认。

需要强调：RAG、工具调用和循环次数不是所有请求都必经的固定步骤，要由任务和系统策略决定。

### 7. 大模型怎样知道并选择工具

**建议时长：60 秒。**

不是把工具信息写进向量数据库让模型搜索。通常由 Agent Host 或客户端先获得工具清单；在 MCP 中可以通过 `tools/list` 获取工具的 `name`、`description` 和 `inputSchema`。应用把这些定义作为工具上下文提供给模型，模型再根据用户意图和工具描述输出工具名及结构化参数。

应用收到调用请求后还要做三层校验：工具是否在白名单内、参数是否满足 Schema、当前用户是否有权限。校验通过后，MCP 客户端用 `tools/call` 调用 Server；结果再返回模型继续生成。

模型负责“建议调用哪个工具”，应用负责“能不能调、怎样调和是否需要人工确认”。模型选择可能出错，所以工具描述、权限、参数校验、超时、重试和副作用确认都不能省略。

### 9. Skills、MCP 和 Function Calling 的区别与关系

**建议时长：70 秒。**

先给结论：三者不在同一个抽象层次，也不是固定的上下级关系。

- **Function Calling** 是模型与应用之间的一种交互机制。模型输出“调用哪个函数、参数是什么”，应用真正执行函数，再把结果返回模型。模型本身通常不会直接执行代码。
- **MCP** 是连接 AI 应用与外部能力的标准协议。它规定客户端怎样发现 Server 暴露的 Tools、Resources、Prompts，以及怎样调用工具。Function Calling 可以调用本地函数，也可以由应用映射到 MCP 工具。
- **Skills** 通常是可复用的任务说明或工作流封装，里面可以包含提示词、步骤、脚本和资源。它可以调用本地工具，也可以调用 MCP 工具；不同产品对 Skill 的具体格式并不完全相同。

例如“发布公众号文章”可以被封装成一个 Skill；Skill 先检查文章和账号，再让模型通过 Function Calling 选择发布工具；该发布工具可能由 MCP Server 提供。

### 10. 这些 AI 概念分别解决什么问题

**建议时长：75 秒。**

这些概念的共同背景是：大模型擅长理解和生成文本，但它的训练知识有截止时间，不天然拥有企业私有数据，也不能可靠地直接操作外部系统。

- **RAG** 解决知识缺失和私有知识接入问题，但它不等于扩大模型上下文上限，也不能保证检索内容一定正确。
- **Function Calling** 解决“把自然语言意图转换为结构化动作”的问题。
- **MCP** 解决不同 AI 应用重复对接不同工具的集成成本，让工具发现和调用有统一协议。
- **Skills** 解决高频任务的步骤复用和执行规范问题。
- **Agent** 解决多步骤任务的规划、工具使用、状态推进和结果整合问题。

技术深度主要体现在边界：RAG 需要考虑召回率和证据质量；工具调用需要权限与参数校验；Agent 循环需要预算和终止条件；有副作用的操作需要幂等与人工确认。

### 12. 什么是责任链模式？项目怎样实现

**建议时长：60 秒。**

责任链模式是把多个处理器按顺序组织起来，让请求依次经过每个处理器，每个处理器只负责一个校验或处理步骤。它的核心价值是把原来集中在 Service 中的大段逻辑拆开，使每个节点可以独立修改、测试和扩展。

这个项目在框架层定义 `AbstractChainHandler`，统一 Handler 接口；`AbstractChainContext` 在启动时收集 Spring 容器中的 Handler，按 `order` 排序，并按业务 `mark` 组织成不同责任链。Service 只需要把请求和链标识交给 Context，就能依次执行整条链。

它的代价是调用链变长、排查需要更好的日志，而且共享 Context 或单例 Handler 不能保存请求级可变状态。

### 13. 购票校验链有哪些 Handler？为什么要拆

**建议时长：50 秒。**

我实际记录过的购票校验链有四个节点：必填参数非空校验、列车与站点合法性校验、余票库存校验、重复购票校验，分别通过 `order` 控制顺序。

拆分的原因不是单纯减少代码行数，而是让职责和变化原因分开。例如库存规则变化只修改库存 Handler；新增学生票资质校验时，新建一个 Handler 并插入合适顺序，不需要改动核心购票 Service，符合开闭原则。每个 Handler 也可以单独做单元测试。

### 14. 除了责任链，怎样让复杂代码更清晰

**建议时长：60 秒。**

要先判断复杂性的来源，再选手段：

- 同一业务有多种可替换算法，例如不同支付渠道，用策略模式配合工厂选择。
- 流程骨架相同、个别步骤不同，可以用模板方法。
- 状态迁移复杂，例如订单待支付、已支付、已取消，可以显式建模状态机并使用条件更新。
- 日志、鉴权、监控等横切逻辑可以用 AOP，但核心业务不应隐藏在切面里。
- 跨服务且允许异步的后续动作可以用领域事件或 MQ 解耦，但不能为了“代码优雅”强行引入最终一致性和运维成本。
- 方法本身过长时，优先按领域职责拆 Service、提取小函数、使用清晰的数据对象和统一异常处理。

设计模式是解决特定变化和依赖问题的工具，不是越多越好。

### 16. 铁路区间库存与多区间扣减是什么

**建议时长：70 秒。**

铁路库存与普通商品库存的区别是：一张座位可以分段售卖。假设线路是 A-B-C-D，用户购买 A-C 后，该座位在 A-B、B-C 两段不可再售，但 C-D 仍可能出售。因此一次购票会影响多个相邻区间以及多个起终点组合，这就是区间库存更新带来的写扩散。

一种通用建模方式是把每个相邻区间映射为一个 bit。请求 A-C 对应区间掩码 `0011`，如果座位占用位图与请求掩码按位与为 0，说明没有冲突；售出后再按位或更新。面向快速查票还可以维护起终点余票的派生计数，但派生数据越多，更新和一致性成本越高。

项目边界要诚实说明：我理解并验证了区间库存这个业务难点，但如果面试官问具体表名、事务 SQL 和缓存键，我需要先重新对照源码，不能根据通用方案冒充项目实现。

### 17. 缓存成功、数据库失败怎么办？完整购票流程怎样设计

**建议时长：90 秒。**

先给结论：如果系统只在 Redis 扣减成功就向用户返回“购票成功”，而数据库订单和库存还没有可靠落库，这个语义是不成立的。最多只能返回“排队中”或“已受理”。

更稳妥的流程是：

1. 网关完成鉴权、限流和基础参数校验。
2. 责任链完成车次、站点、库存和重复购票校验。
3. Redis Lua 原子完成令牌或预库存扣减，用于快速挡住明显无库存请求。
4. 在数据库本地事务中，通过条件更新扣减最终库存并创建待支付订单；条件更新或唯一约束作为最终防超卖边界。
5. 本地事务成功后才返回“下单成功、待支付”；若失败，则释放或补偿 Redis 预占。
6. 发送延时消息用于超时取消，消费者通过订单状态机和幂等条件完成取消及库存回补。
7. 缓存作为派生数据，可通过 Binlog/CDC 加 MQ 或可靠删除策略做最终一致性和定时对账。

如果采用 MQ 异步落库，则接口必须返回“处理中”，并设计可靠消息、消费幂等、失败重试、死信和对账补偿，不能假设“重试直到成功”就没有边界。

### 18. 为什么使用 RocketMQ？适合哪些场景

**建议时长：60 秒。**

RocketMQ 在这个场景主要解决四类问题：异步处理、服务解耦、流量削峰和延时触发。

例如创建订单后，短信、审计等非核心动作可以异步消费；抢票高峰可以先把可接受的任务写入 MQ，保护下游数据库；未支付订单可以用延时消息触发取消。需要纠正一个表述：数据库不是消费者，真正的消费者是业务服务，由它消费消息并更新数据库。

引入 MQ 后还要承担消息可能重复、短暂乱序、积压和最终一致性的成本，所以生产者要确认发送结果，Broker 要有可靠存储和副本，消费者要在业务成功后确认并保持幂等，同时建设重试、死信、监控和对账。

### 19. MQ 解耦的本质是什么

**建议时长：45 秒。**

解耦的本质是把同步的“直接调用某个下游服务”改成依赖稳定的消息契约。生产者只表达“某个业务事实已经发生”，不需要知道有多少消费者、消费者是否在线以及各自怎样处理；下游可以独立扩容、发布和重试。

但解耦不等于没有依赖，依赖从代码调用转移到了 Topic、消息 Schema、时序和投递语义上。因此消息版本兼容、幂等键、顺序范围、积压监控和可追踪性仍然是系统设计的一部分。

### 20. 延时消息怎样取消未支付订单

**建议时长：60 秒。**

创建待支付订单后发送一条携带 `orderId` 的延时消息。消息到期后，消费者不能直接取消，而应执行条件更新，例如：

```sql
UPDATE orders
SET status = 'CANCELLED', version = version + 1
WHERE id = ? AND status = 'UNPAID' AND version = ?;
```

只有受影响行数为 1 才说明本次取消成功，然后再幂等回补库存。若用户在第 9 分 59 秒支付，支付回调也必须用 `UNPAID -> PAID` 的条件更新与取消竞争，最终只能有一个状态迁移成功。重复投递时，已支付或已取消订单直接返回成功，不重复回补库存。

### 21. RocketMQ 延时时间可以任意设置吗

**建议时长：45 秒。**

要先问版本。RocketMQ 4.x 原生使用固定延时等级，官方默认有 18 个等级，例如 1 秒、5 秒、10 秒一直到 2 小时，不能为每条消息设置任意延时时长；10 分钟订单可以使用对应等级。

RocketMQ 5.x 支持按毫秒时间戳设置定时投递，表达上更灵活，但仍有允许时间范围，官方文档给出的默认最大范围是 24 小时，并不是无限任意时间。长周期任务更适合数据库任务表加调度系统，而不是长期占用延时消息。

### 22. RocketMQ 事务消息怎样工作

**建议时长：60 秒。**

事务消息主要保证“本地事务执行”和“消息发送”之间的最终一致性：

1. Producer 先向 Broker 发送半消息，此时下游不可见。
2. Broker 保存后返回确认，Producer 执行本地事务。
3. 本地事务成功则发送 Commit，失败则发送 Rollback。
4. 如果二次确认丢失或返回 Unknown，Broker 会回查 Producer 的本地事务状态。
5. Commit 后消息才对消费者可见。

它不保证下游消费与上游事务天然强一致。消费者仍可能重复收到消息，因此还需要业务幂等、重试、死信和补偿。

### 23. 黑名单是什么业务场景

**建议时长：55 秒。**

游戏中存在小额交易和提现场景，风控系统会识别薅羊毛、洗钱等高风险行为，再由客服或运营对相关玩家实施支付限制。黑名单既支持永久限制，也支持一段时间后的自动解封。

我参与的重点是到期解封能力：客服设置临时黑名单和解封时间后，系统需要可靠地找到到期记录并自动解除限制，同时记录操作日志。业务价值是减少人工遗漏和用户到期后仍被限制的问题。

### 24. 数据存在哪里？为什么使用 ZSet

**建议时长：70 秒。**

这里要先区分三类数据，不能笼统说“数据库和 Redis 各存一份”：

- 游戏服务中的 `black_limit` 等策略状态是实际生效状态。
- MySQL 保存策略操作记录和审计信息。
- Redis ZSet 是待解封任务的调度索引，不应被当作唯一事实源。

ZSet 的 `member` 使用能够唯一标识一条任务的 `userId + projectKey`，`score` 使用解封时间戳。定时任务通过 `ZRANGEBYSCORE -inf now LIMIT 0 100` 分批取出已经到期的任务。

选择 ZSet 的关键不是“Redis 快”，而是它天然按 score 排序并支持范围查询，可以主动分页扫描和控制批量大小。相比只依赖 Key TTL，它更容易观察待处理任务、批量消费和实现失败重试。

### 25. 为什么需要分布式锁？锁的是什么

**建议时长：65 秒。**

服务是多实例部署的，同一时刻可能有多个实例扫描到同一条到期任务。如果都执行解封，会重复调用下游并重复写操作日志。

这个链路可以分成两层协调：全局调度锁控制同一时刻只有一个实例扫描 ZSet，减少重复扫描；记录锁以 `userId + projectKey` 为粒度，避免同一任务被重复处理，同时允许不同玩家并行解封。

Redis 锁的基础写法应是 `SET key uniqueToken NX PX ttl`，显式释放时用 Lua 比较 token 后删除。TTL 防止持锁实例崩溃造成永久死锁，但 TTL 过短、长 GC、网络分区和主从切换仍可能出现两个执行者，因此业务状态校验和幂等不能只依赖锁。

### 26. 加黑名单和到期解封的完整流程

**建议时长：80 秒。**

加入黑名单时：先校验玩家、项目、策略类型和解封时间；调用业务服务把黑名单状态设置为生效；若是临时黑名单，把唯一任务标识写入 ZSet，score 为解封时间；最后记录操作人、原因和新旧策略，便于审计。

到期解封时：定时任务扫描 `score <= now` 的记录；对单条任务竞争记录锁；获取锁后重新读取当前业务状态，确认它仍是同一次封禁且已经到期；通过幂等接口或条件更新执行解封；成功后再移除 ZSet 任务并写系统操作日志。失败时保留或重新放回任务，按退避策略重试并告警。

现有学习记录中的实现是先 `ZREM` 再调用 `delBlackLimit()`，如果下游失败会丢任务。面试中应主动指出这个缺陷，并把“成功后删除、失败可重试”作为改进方案，而不是把现有实现说成完整可靠方案。

### 27. 锁单个玩家是否足够？怎样避免旧任务误解封新封禁

**建议时长：70 秒。**

只锁 `userId` 可能过粗，也不能单独解决时序问题。锁粒度至少要包含玩家、项目和黑名单类型；如果同一玩家可以多次被拉黑，还应为每次策略变更保存 `version` 或唯一 `blacklistRecordId`。

解封任务执行时不能只看“这个玩家现在在黑名单里”，而要校验“当前版本仍等于任务创建时的版本，并且当前解封时间已经到期”。可以使用条件更新：

```sql
UPDATE blacklist
SET status = 'RELEASED', version = version + 1
WHERE user_id = ?
  AND project_id = ?
  AND status = 'BLACK'
  AND version = ?
  AND release_at <= NOW();
```

这样即使旧任务晚到，因版本不匹配也不会误解封后来重新加入的黑名单。分布式锁减少并发，版本和状态机才是正确性的最终边界。

### 28. Redis 成功、数据库或下游失败会不会不一致

**建议时长：50 秒。**

会，而且原实现确实存在这个缺口。更准确地说，问题不是普通的“缓存与数据库双写”，而是“调度索引与业务动作之间缺少原子边界”。如果先从 ZSet 删除，再调用下游解封，而下游失败，这条任务就不会被再次扫描，用户可能长期无法解封。

反过来，如果业务状态已经变更但 ZSet 删除失败，任务会再次投递。只要解封接口和日志写入具备幂等性，这一方向通常比任务丢失更容易处理。因此顺序上应优先保证业务动作成功，再删除调度任务，并配合状态校验和重试。

### 29. 怎样系统解决黑名单链路的一致性

**建议时长：90 秒。**

我会把 MySQL 或实际策略服务作为事实源，把 Redis ZSet 定位为可重建的调度索引，并采用以下组合方案：

1. **写入侧可靠事件**：在数据库事务中同时写业务记录和 Outbox 事件；事务提交后由后台任务或 CDC 把事件投递到 MQ，再由消费者幂等更新 ZSet。若事实源在远程游戏服务，则至少要记录本地任务状态和调用结果，不能依赖一次双写。
2. **执行侧状态机**：解封前校验记录 ID、版本、状态和到期时间；通过条件更新或幂等下游接口完成 `BLACK -> RELEASED`。
3. **删除顺序**：业务动作和审计成功后再 `ZREM`。失败则保留任务或写入带下一次重试时间的任务集合。
4. **失败治理**：有限重试加指数退避，超过阈值进入死信表或补偿队列并告警，不能无限同步重试占住线程。
5. **对账重建**：定期扫描事实源中的“已到期但未解封”记录，补回 ZSet；Redis 故障恢复后也能从事实源重建。

MQ 解决的是可靠异步传播，不自动提供全链路 exactly-once。消费者仍需使用业务唯一键、条件更新和幂等日志。

### 30. Redis 常用数据结构与场景

**建议时长：75 秒。**

- `String`：缓存对象、计数器、分布式锁和简单状态；自增命令适合原子计数。
- `Hash`：保存字段较多且需要局部读写的对象，例如用户资料；是否优于序列化 String 要看访问方式和内存开销。
- `List`：有序序列、简单队列，但可靠消息通常更适合 Stream 或专业 MQ。
- `Set`：去重、集合交并差、共同关注。
- `Sorted Set`：排行榜、延时任务索引、按时间或分数做范围查询。
- `Stream`：追加日志、消费者组和事件流。
- `Bitmap`：签到、布尔状态统计；它是 String 上的位操作。
- `HyperLogLog`：用固定小内存近似统计 UV，存在误差，不保存完整成员集合。
- `GEO`：经纬度和附近位置查询，底层能力与 ZSet 相关。

需要纠正原回答：Bloom Filter 不是 Bitmap 的同义词。Bloom Filter 使用位数组和多个哈希函数判断“可能存在或一定不存在”，Redis 中通常由 RedisBloom 模块提供。

### 31. 数组和链表的区别

**建议时长：55 秒。**

数组使用连续的槽位保存同类型元素，支持通过下标 O(1) 随机访问；长度固定，若在中间插入或删除，通常需要移动后续元素，所以是 O(n)。

链表的节点通过引用连接，节点不要求连续。按下标查找需要从头或尾逐个遍历，通常是 O(n)；但如果已经拿到目标节点及其前驱，插入和删除只需要修改引用，可以是 O(1)。

在 Java 集合中还要区分 `ArrayList` 和数组：`ArrayList` 底层仍是动态数组，扩容时要分配更大的数组并复制元素；`LinkedList` 才是双向链表。实际业务中 `ArrayList` 通常因缓存局部性和更少对象开销而更常用。

### 32. 数组为什么可以 O(1) 随机访问

**建议时长：35 秒。**

因为数组中每个槽位的宽度固定，运行时知道数组首地址和元素槽位大小，所以访问第 `i` 个元素可以直接计算其槽位地址：`base + i * slotSize`。这个计算不随数组长度增长，因此时间复杂度是 O(1)。

O(1) 表示操作次数与数据规模无关，不代表绝对只执行一条 CPU 指令；还会有边界检查、地址计算和内存访问。

### 33. 对象大小不同，Java 对象数组为什么仍能 O(1) 访问

**建议时长：45 秒。**

Java 的 `Student[]` 不是把大小不同的 `Student` 对象本体连续塞进数组，而是连续保存固定宽度的对象引用。数组通过下标 O(1) 找到第 `i` 个引用，再由引用指向堆中的具体对象。

学生姓名是两个字还是三个字，只影响 `Student` 或它引用的 `String` 对象占用多少堆空间，不影响数组引用槽位的宽度。因此对象数组完全可以 O(1) 随机访问。基本类型数组则直接连续保存固定宽度的基本类型值。

### 34. 怎样理解封装、继承和多态

**建议时长：70 秒。**

- **封装**：把数据和操作数据的方法放在一起，并隐藏不该被外部直接修改的状态。它的价值是维护对象不变量，例如账户余额不能被任意赋值，只能通过经过校验的方法变更。
- **继承**：子类复用并扩展父类行为，表达 `is-a` 关系。继承会带来较强耦合，业务设计通常优先考虑组合，只有稳定的类型层次才适合继承。
- **多态**：父类或接口引用可以指向不同实现，调用重写方法时在运行期分派到真实对象。调用方依赖抽象，不需要写大量 `if-else` 判断具体类型。

三者不是“封装一个对象、继承方法、实现多个接口”这么简单。面试时应讲清各自解决的问题和边界。

### 35. 多态在实际开发中怎样使用

**建议时长：55 秒。**

以支付渠道为例，可以定义统一接口：

```java
public interface PayStrategy {
    PayResult pay(PayRequest request);
}
```

支付宝、微信支付分别实现该接口。业务层只持有 `PayStrategy`，由工厂或 Spring 注入的实现集合按渠道选择具体对象，再统一调用 `pay()`。调用方依赖接口，新增渠道时不需要改动核心支付流程。

12306 责任链本身也体现多态：多个校验 Handler 实现同一接口，Context 以统一方式遍历调用，但每个 Handler 执行不同校验。这里“接口引用指向不同实现，并触发各自的重写方法”才是多态的关键。

### 36. 算法题：无重复字符的最长子串

> 原转录没有记录屏幕上的完整题面，也没有嵌入题目截图。根据“左右指针、字符计数、出现重复就移动左指针”的讲解，可以可靠推断为 LeetCode 3「无重复字符的最长子串」。如果原题另有输入输出要求，应以当时屏幕题面为准。

**建议讲解时长：60 秒，编码 8 到 10 分钟。**

使用滑动窗口。`left` 表示当前无重复窗口的左边界，`right` 向右扫描；`last[c]` 记录字符 `c` 上一次出现的位置。如果 `c` 在当前窗口内出现过，就把 `left` 跳到 `last[c] + 1`，然后更新答案。

```java
import java.util.Arrays;

public class Solution {
    public int lengthOfLongestSubstring(String s) {
        int[] last = new int[128];
        Arrays.fill(last, -1);

        int left = 0;
        int answer = 0;

        for (int right = 0; right < s.length(); right++) {
            char c = s.charAt(right);
            left = Math.max(left, last[c] + 1);
            last[c] = right;
            answer = Math.max(answer, right - left + 1);
        }
        return answer;
    }
}
```

时间复杂度是 O(n)，因为每个字符只被扫描一次；空间复杂度是 O(|字符集|)。上面代码假设输入是 ASCII。若字符范围不确定，可以用 `HashMap<Character, Integer>`；若题目要求完整 Unicode 码点，则需要按 code point 遍历，而不是直接把 UTF-16 的 `char` 当作一个完整字符。

边界用例：空串返回 0；全相同字符返回 1；`abba` 在第二个 `a` 处必须使用 `Math.max`，避免左指针回退。

### 4. 一致性只说了 MQ，没有说事实源、幂等和补偿

MQ 只能可靠传播事件，不自动解决业务一致性。完整答案至少要包含：事实源、状态机或条件更新、幂等键、失败重试、死信、对账和人工补偿。

### 5. Java 基础概念缺乏准确例子

对象数组和多态是本场最明显的基础失分点。复习时不能只背定义，要准备一个内存模型解释和一个项目代码例子。
