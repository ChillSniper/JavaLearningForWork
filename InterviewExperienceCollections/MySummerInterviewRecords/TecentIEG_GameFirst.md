### 2. 支付风控黑名单模块的背景和实现

**建议时长：60 到 90 秒。**

**参考回答：**

这个需求解决的是微小额提现、红包激励等场景中的风险用户管控。风控或客服会为玩家设置黑名单和解封时间，系统需要在到期后自动发起解封，避免完全依赖人工操作。

实现上，游戏服的风控策略是权威状态，Redis 只承担待解封任务的调度。我使用一个 ZSet 保存任务，`score` 是解封时间戳，`member` 是能够唯一标识玩家和项目的组合值。定时任务每隔一段时间通过 `ZRANGEBYSCORE key -inf now LIMIT 0 100` 分批查询到期任务，再调用游戏服 SDK 解封，并写入操作日志。多实例执行时使用 Redis 锁减少同一玩家被重复处理。

这套方案在当时几千条任务的规模下足够简单，也便于观察任务积压。它的不足是 Redis 调度记录、远程解封和本地日志不在一个事务里，所以不能只靠 SetNX 宣称强一致。如果重新设计，我会增加任务状态、幂等操作号、失败重试和对账补偿，成功后再确认移除调度任务。

### 3. 为什么选择 ZSet，而不是 Redis TTL

**建议时长：45 到 60 秒。**

**参考回答：**

核心原因是 TTL 解决的是“键何时失效”，而不是“到期后可靠执行一次业务解封”。如果给每个玩家建立一个独立 key 并监听过期事件，会产生大量零散 key；更重要的是，过期通知依赖 Pub/Sub，断线期间的事件会丢失，而且事件触发时间也不保证与 TTL 归零时刻完全一致。即使 key 被删除，Redis 也不会自动调用游戏服的解封接口。

ZSet 更像一个可查询的时间索引。把解封时间放在 score 中，可以按时间范围批量拉取、限制单批数量、查看积压、失败后重新入队；同一个 member 再次 `ZADD` 还可以更新解封时间。因此它更适合这个轻量级定时任务场景。

**边界：**不能把答案说成“TTL 到点后 key 仍然可以被正常读取”。TTL 到期后 key 在逻辑上已经失效，真正不可靠的是把过期通知当成业务消息使用。

### 4. 权威封禁名单存在哪里？本模块负责什么

**建议时长：20 到 30 秒。**

**参考回答：**

权威状态在游戏服或上游风控策略服务中，我的模块不是黑名单的唯一数据源。客服系统接收黑名单操作，Redis ZSet 只保存待解封调度信息；到期后由客服系统调用游戏服接口发起解封，本地 MySQL 保存操作审计记录。因此判断用户是否真的被封禁，最终要以权威服务的状态为准，不能只看 ZSet 中是否存在 member。

### 5. Redis key 和 member 怎样设计

**建议时长：40 到 60 秒。**

**参考回答：**

当时的 ZSet key 类似 `customer-server:pay-risk:black`，由系统名、业务域和任务类型组成，便于定位和监控。member 使用 `userId + projectKey` 唯一标识某个项目下的玩家，score 保存绝对解封时间戳。同一个 member 再次写入时会更新 score，适合延长或缩短封禁时间。

设计时主要考虑四点：命名要有清晰命名空间；member 必须无歧义，生产上最好使用固定编码或结构化组合，避免简单分隔符碰撞；key 和 member 不能包含敏感信息；还要提前考虑 Cluster 下的分片方式和关联 key 的同槽要求。若并发更新比较复杂，我还会在权威状态中加入 `version`，定时任务执行时同时校验版本。

### 6. 为什么当前一个服务使用一个 ZSet key

**建议时长：30 到 45 秒。**

**参考回答：**

当时单个游戏的黑名单只有几千条，一个 ZSet 可以直接按时间排序和范围查询，运维、监控和代码实现都比较简单，所以没有为了不存在的规模问题提前分片。

但我会明确这个选择的边界：Redis Cluster 是按 key 分槽，不会把一个大 ZSet 的 member 自动拆到多个节点。一个 key 最终仍然落在一个槽和一个主节点上，数据量或访问量继续增长后会形成内存和 CPU 热点。因此需要监控 `ZCARD`、内存、扫描延迟和积压量，达到阈值后再做应用层分片。

### 7. 千万级记录下怎样扩展

**建议时长：60 到 90 秒。**

**参考回答：**

我会从单个大 ZSet 改为“固定虚拟分片 + 分片任务所有权”。例如预先定义 128 或 256 个逻辑桶，使用 `hash(projectId, userId) % 256` 得到桶号，key 可以设计为 `customer-server:pay-risk:unlock:{s042}`。每个桶是一个独立 ZSet，避免一个 key 成为热点；后台实例通过租约领取一组桶，只扫描自己负责的桶。

固定虚拟桶比直接按当前机器数量取模更稳定，因为扩容实例时不需要重新计算所有玩家的分片。Redis 仍只作为调度索引，MySQL 或游戏服保存权威状态；失败任务要有重试次数、下一次执行时间和死信状态，并通过定期对账重建漏掉的任务。容量上还需要结合单条 member 大小、总内存、到期峰值和下游接口吞吐做压测，不能只看 ZSet 查询复杂度。

### 8. 怎样把玩家映射到业务分片

**建议时长：30 到 45 秒。**

**参考回答：**

应用层先对稳定业务标识做哈希，例如 `CRC32(projectId + ':' + userId) % N`，得到固定虚拟桶号。写入、查询和解封都使用同一个函数，就能稳定找到对应 ZSet。哈希输入不能使用会变化的字段，桶数也不应频繁改变。

这里的业务分片和 Redis Cluster 的槽是两层概念：业务哈希负责把一个大集合拆成多个 key，Redis Cluster 再对每个完整 key 计算槽位。只做玩家哈希但仍写进同一个 ZSet，并不能把压力分散到多个节点。

### 9. 项目中的 Redis 是什么部署模式

**建议时长：15 到 25 秒。**

**参考回答：**

当时项目通过 Go Redis 客户端连接单实例 Redis，没有实际使用 Redis Cluster。因此我只能把单机方案描述为当前实现，不能说它已经具备分片和自动故障转移能力。Cluster 相关内容是面试官扩大规模后的设计讨论。

### 10. Redis Cluster 的原理和故障转移

**建议时长：60 秒。**

**参考回答：**

Redis Cluster 主要解决数据分片和节点故障后的可用性问题。整个 key 空间被划分为 16384 个 hash slot，每个主节点负责一部分槽；客户端根据 key 计算槽位并访问对应节点，路由变化时通过 `MOVED` 或 `ASK` 更新路由。

每个主节点可以配置副本。节点之间通过 Cluster Bus 和 gossip 传播状态，主节点被多数主节点判定失联后，其副本会参与故障转移并晋升为新主节点。这里不是 Raft 共识。Redis Cluster 的主从复制默认是异步的，所以主节点刚确认的写入还没复制就故障时，仍然存在数据丢失窗口，它不是强一致系统。

### 11. 怎样让分片 key 分散到不同槽和实例

**建议时长：45 到 60 秒。**

**参考回答：**

Redis Cluster 的基础规则是 `CRC16(key) % 16384`。应用拆出多个不同 key 后，Cluster 会把它们映射到不同槽；槽再由运维分配到不同主节点。若要控制同槽，可以使用 `{...}` hash tag，例如 `unlock:{s042}:zset` 和 `state:{s042}:hash` 会落在同一槽，便于执行多 key Lua 或事务。

反过来，如果所有分片 key 都写成相同的 `{pay-risk}`，它们会全部落到同一个槽，分片就失效了。不同 tag 也可能出现哈希碰撞，因此严格要求特定槽时需要用 `CLUSTER KEYSLOT` 验证；至于是否落到不同物理主节点，还要结合当前槽到节点的映射观察，应用不能只靠 key 名字绝对保证。

### 12. 红包激励黑白名单 SDK 做了什么

**建议时长：45 到 60 秒。**

**参考回答：**

这个 SDK 的作用是把客服系统调用激励服务的细节统一封装起来。它负责构造查询、加黑、加白、编辑和删除等 HTTP 请求，并统一处理鉴权、超时、错误码和响应解析。鉴权侧使用 Access-Id、Random、Timestamp 等字段按约定排序后拼接 SecretKey，再计算 SHA256 签名；Endpoint 等可变参数通过 Functional Options 配置，避免调用方依赖具体环境。

SDK 上层还接入了操作审计和批量导入导出。这里需要强调：SDK 只解决跨服务调用的一致接口和安全校验，审计可靠性、业务幂等和远程调用失败补偿仍然属于业务服务层，不能因为封装了 SDK 就认为这些问题已经解决。

### 13. 操作日志记录在哪里

**建议时长：20 到 30 秒。**

**参考回答：**

日志记录在客服系统自己的 MySQL 操作记录表中，而不是只打印到文件。记录维度包括项目或游戏标识、玩家、操作类型、操作人、操作时间、变更前后值、调用结果和操作流水号。按 CloudID、AppID、GameID 等业务维度路由，是为了支持审计查询和控制单表规模。

### 14. 怎样保证业务操作和异步审计日志一致

**建议时长：60 到 90 秒。**

**参考回答：**

先说结论：单纯启动一个异步 Goroutine，在远程操作成功后再插入日志，只能降低接口延迟，不能保证审计可靠。进程可能在远程调用成功、日志落库之前崩溃，日志就会永久丢失。录音中的当前实现没有彻底解决这个边界，面试时应该直接承认。

如果业务变更和审计表都在同一个 MySQL 中，最简单的方案是在一个本地事务里同时提交业务数据和审计数据。如果黑白名单实际由远程服务维护，我会先在本地事务中写入带唯一 `operationId` 的操作记录，状态为 `PENDING`，再调用远程服务；远程接口使用同一个 operationId 做幂等，成功后将记录更新为 `SUCCESS`，失败或结果未知则由后台任务重试和对账。数据库唯一索引防止同一操作重复建单。

这样实现的是可恢复的最终一致性，而不是跨系统原子提交。如果远程服务既不支持幂等键，也不支持按操作号查询结果，就无法低成本承诺严格的 exactly-once，只能增加对账或改造远程接口。

### 15. 不引入 MQ，怎样低复杂度保证最终一致性

**建议时长：45 到 60 秒。**

**参考回答：**

我会选择“本地任务表 + 状态机 + 定时补偿”，而不是先引入 MQ、TCC 或分布式事务框架。请求到达时先在本地事务中写一条操作任务，状态为 `PENDING`；后台 Worker 按主键范围或 `FOR UPDATE SKIP LOCKED` 领取任务，调用远程服务后更新为 `SUCCESS` 或记录下一次重试时间。每个请求携带唯一 operationId，数据库加唯一约束，远端也按该 ID 幂等。

这个方案只增加一张表和一个已有服务内的 Worker，复杂度可控，而且进程重启后任务仍然存在。对于长期失败的任务进入 `MANUAL_REVIEW`，通过告警和对账处理。只有当吞吐、解耦或跨团队订阅需求明显增加时，再把任务投递升级为 Outbox + MQ。

### 16. Canal 或 Binlog 能否解决审计一致性

**建议时长：30 到 45 秒。**

**参考回答：**

Canal 可以订阅 MySQL Binlog，把已经提交的数据库变更转换为后续事件，因此适合做异步审计、缓存更新或消息投递。它的价值是业务事务提交后，不必再依赖请求线程额外发送一次消息。

但它有前提：必须先有一份本地、持久化的业务事实可供监听。如果真正的黑白名单变更发生在远程服务，而本地数据库什么都没有提交，监听本地 Binlog 也无法推导远程调用结果。CDC 下游仍然要处理重复消费、断点续传、失败重试和幂等，所以 Canal 是后续解耦方案，不是对所有一致性问题的直接答案。

### 17. CRM 流失召回做了什么优化

**建议时长：60 到 90 秒。**

**参考回答：**

这个需求面向客服对高价值或长期未登录玩家的召回。原流程在多实例定时扫描时可能重复处理同一玩家，而且逐个请求 Redis 会产生大量网络往返。

我做的核心优化是按用户加细粒度锁，并使用 Redis Pipeline 批量发送多个 `SET key token NX PX ttl` 命令，把一批用户的多次网络往返压缩为一次。任务完成后通过 Lua 原子执行“校验 token 再删除”，避免旧任务误删新任务的锁。业务侧还把单一免打扰逻辑升级为标签过滤，并补充按客服、流失等级和月份的统计维度。

需要说明的是，Pipeline 只优化网络，不保证整批原子性；Redis 锁也只是减少并发重复。最终幂等仍要依靠数据库条件更新、唯一索引或 Upsert 等持久化约束。

### 18. Pipeline、SetNX 和 Lua 各自解决什么问题

**建议时长：45 到 60 秒。**

**参考回答：**

Pipeline 解决的是性能问题：客户端先缓存一批命令再一次发送，减少 RTT，但服务端仍然逐条执行，其他客户端的命令可能穿插，所以它不是事务。

`SET key token NX PX ttl` 解决的是单个锁 key 的原子抢占和自动过期。token 必须对每次加锁唯一，释放时使用 Lua 原子完成 `GET == token` 后 `DEL`，否则实例 A 的锁过期后，可能误删实例 B 新获得的锁。

这三者结合只能提供一个有时间边界的互斥机制，不能单独保证业务幂等、跨系统一致性或严格顺序。业务层还需要唯一 operationId、状态校验、数据库约束和失败补偿；对高一致性资源还应考虑 fencing token，防止已经失效的旧持有者继续写入。

### 19. 新增封禁与定时解封并发时怎样保证顺序

**建议时长：60 到 90 秒。**

**参考回答：**

只给解封任务加 SetNX 不够，因为它只能防止两个解封任务并发，不能协调“新增封禁”和“到期解封”这两个方向相反的操作。

我会为每个玩家维护一条权威状态，至少包含 `status`、`expireAt` 和单调递增的 `version`。新增或延长封禁时，在权威存储中原子地更新 expireAt 并增加 version；调度任务携带创建时的 expectedVersion。解封执行前必须再次读取权威状态，只有 `version == expectedVersion`、状态仍是封禁且 `expireAt <= now` 时，才通过 CAS 或条件更新完成状态迁移。只要期间出现了新封禁，version 已变化，旧解封任务就会失效。

如果状态和调度都在 Redis，同槽 key 可以用 Lua 完成校验和修改；如果权威状态在 MySQL，则使用带 version 条件的 `UPDATE`。远程副作用仍要带唯一 operationId 并保持幂等。

### 20. 不允许出现短暂解封时怎么办

**建议时长：60 到 90 秒。**

**参考回答：**

先说明一个关键边界：系统无法判断一个尚未到达任何权威节点的“在途请求”。如果 4:59:59.900 发出的延长请求在 5:00 之后才到达，而 5:00 的解封已经提交，仅靠本地锁无法知道未来还会来一条请求。

若业务要求绝不能短暂解封，就必须让两类命令经过同一个可线性化的排序点。例如让新增封禁和解封都进入按 userId 分区的单线程队列，或者由同一个权威状态服务使用 version/fencing token 串行提交。解封可以先进入 `PENDING_RELEASE`，再次校验没有更高版本后再提交不可逆动作。若业务允许有最大网络迟到时间，也可以引入 grace window 或 event-time watermark，但代价是正常解封会被延迟。

因此这不是再加一把 Redis 锁就能解决的问题，而是要在“顺序保证、可用性和解封延迟”之间做明确取舍。

### 21. 状态机应该维护在哪里

**建议时长：30 到 45 秒。**

**参考回答：**

不能只维护在某个服务实例的 JVM 或 Go 进程内存中，因为多实例之间看不到同一份状态，重启后也会丢失。推荐把状态机放在权威且持久化的存储中，例如 MySQL 的玩家风控状态表，使用状态、expireAt、version 和更新时间做条件更新。

Redis 可以作为调度索引或缓存。如果业务把 Redis 作为状态源，也应把相关状态放在共享 key 中，并通过 Lua 保证原子迁移，同时接受其持久化和故障切换边界。对不可逆操作，我更倾向以数据库或专门的权威状态服务作为最终判断依据。

### 22. 多实例定时任务的进程模型

**建议时长：45 到 60 秒。**

**参考回答：**

这题要先与真实代码口径保持一致。项目复盘材料中记录了一层全局 cron 锁，例如 `customer-server:lock:cron`，正常情况下只有持有租约的实例扫描 ZSet；每条记录的用户级锁再作为故障切换或重复调度时的兜底。录音中回答成“所有实例同时扫描”，会让面试官继续追问重复读取和 Redis 压力。

锁实现不能只说 SetNX。应使用 `SET key token NX PX ttl` 原子加锁，续租或重新竞选时校验 token，释放时比较 token 后再删除。即使有调度锁，解封操作自身仍要幂等，因为实例可能在业务成功但任务确认前崩溃。

### 23. 怎样减少所有实例重复扫描

**建议时长：30 到 45 秒。**

**参考回答：**

小规模下可以用一个带租约的 leader 负责扫描，其他实例只在 leader 失效后接管；记录级幂等作为第二层保障。这样能够直接避免每个实例都执行相同的 `ZRANGEBYSCORE`。

规模扩大后，单 leader 可能成为吞吐瓶颈，可以把 ZSet 拆成固定虚拟分片，每个实例通过租约领取部分分片并周期续约。扩缩容只转移分片所有权，不重新哈希全部用户。还要监控每个分片的积压、最老任务延迟和领取者心跳，避免某个分片无人处理。

### 24. 实习主要使用 Go 吗

**建议时长：20 到 30 秒。**

**参考回答：**

是的，实习项目主要使用 Go，我参与的是游戏中台客服系统的后端需求。个人学习和项目积累更多在 Java，但在 Go 实习中已经使用过 Goroutine、HTTP 客户端、GORM、Redis 和配置中心。两种语言的语法和运行时不同，但服务拆分、并发控制、数据一致性和可观测性这些后端问题是相通的。

### 25. 是否了解 Docker、Kubernetes 和 Linux

**建议时长：30 到 45 秒。**

**参考回答：**

我有基础了解，但没有线上集群的运维权限，所以不会把自己描述成做过 Kubernetes 集群管理。我理解服务从镜像构建，到 Pod、Deployment、Service，再到滚动发布、健康检查、配置注入和日志监控的基本链路；平时也能使用 Linux 常用命令排查进程、端口、日志、CPU 和内存问题。

更深入的容器网络、调度器、CGroup、Namespace 和 Linux 内核问题，我目前只是学习阶段。如果岗位需要，我会优先补齐从服务异常到 Pod、节点和网络链路的实际排障能力。

### 26. 服务怎样发布和部署，你负责什么

**建议时长：45 到 60 秒。**

**参考回答：**

我的工作一般先在本地完成开发和自测，再部署到测试环境联调。正式发布前需要完成代码评审、测试验证，以及数据库变更和 Apollo 配置变更的审批。生产环境由有权限的运维或负责人通过 Kubernetes 发布，通常会经过灰度、指标和日志观察，再逐步放量；异常时回滚镜像或配置版本。

我实际负责的是代码、测试、配置项准备、变更说明和上线后的业务验证，没有亲自操作生产集群。这样回答既能说明我理解完整发布链路，也不会夸大自己的线上权限和经验。

### 27. 对开发语言是否有偏好

**建议时长：30 到 40 秒。**

**参考回答：**

我的核心方向是服务端和分布式后台开发，Java 是目前积累最系统的语言，Go 有真实实习经验，所以我能根据团队技术栈继续深入。语言确实是工具，但我不会回答成“什么都一样、没有偏好”，因为岗位还需要可验证的积累。现阶段我的优先级是 Java 或 Go 后端；如果游戏基础设施需要 C++，我也愿意补齐，但会诚实说明当前熟练度。

## 四、候选人反问的整理与优化

### 30. 为什么没有算法题

原问题可以保留，但不要表现成“没做算法题所以意外”。更好的问法是：

> 我注意到今天主要围绕项目方案和边界条件展开。想了解一下，这个岗位在后续面试和实际工作中，对算法能力、系统设计和工程能力的侧重分别是什么？

这个问法能帮助判断岗位要求，也不会让面试官误以为自己只按固定题型准备。

### 31. AI 在公司内部有哪些实际价值

**更好的问法：**

> 团队目前把 AI 主要用在编码提效、知识库检索，还是运维和发布场景？对于 AI 生成的代码，团队通常通过哪些评审、测试或指标判断它能否进入生产？

从面试官回答看，AI 已经广泛用于编码和知识检索，但团队尚未形成唯一最佳实践。真正重要的不是个人少写了多少代码，而是能否定义正确标准、识别生成结果的风险，并通过评审、测试和长期维护保证团队整体效率。

### 32. 是否应该减少基础知识投入

不建议把结论理解为“八股和基础不重要”。更准确的回答是：

> 计算机基础决定我能否看懂并验证方案，业务建模、边界分析和长期维护能力决定我能否做出正确方案。准备上我会继续巩固网络、数据库、并发和操作系统，同时把更多练习放到真实故障、规模扩展和一致性权衡中，而不是只背结论。

## 五、本场面试复盘

### 做得较好的地方

- 项目是真实业务，能够说明上游风控、客服系统和游戏服之间的关系。
- 面对不确定问题愿意思考，没有强行编造已经实现的能力。
- 在严格顺序问题中想到了状态机、乐观锁和唯一消息 ID，方向是有价值的。

### 需要重点改进的地方

1. 自我介绍信息过散。应先讲定位和代表经历，不要按学习顺序罗列课程与项目。
2. TTL 的回答不准确。TTL 不是业务调度器，关键问题是粒度、通知可靠性和无法自动执行解封，而不是简单说“TTL 会延期”。
3. Redis Cluster 原理答错。Cluster 不使用 Raft；一个大 ZSet 也不会自动拆到多个槽。
4. 一致性方案出现了明显的“先堆中间件”。简单需求应先判断能否用本地事务，再考虑任务表、幂等和对账，最后才是 MQ、CDC 或分布式事务。
5. SetNX 被描述得过强。它只能提供有时限的互斥，不能自动保证业务幂等、相反操作的顺序和跨系统一致性。
6. 多实例扫描口径需要与代码统一。若全局 cron 锁已经存在，应明确“单实例扫描、记录锁兜底”；如果确实是全实例扫描，则要主动说明重复读取成本和优化方案。
7. “语言没有偏好、什么都可以”会显得方向不清晰。应给出当前最强技术栈和目标岗位，再表达迁移意愿。
