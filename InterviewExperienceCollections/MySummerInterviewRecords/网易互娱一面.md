## 二、逐题回答

## A. 项目与 Redis ZSet 黑名单解封

### 1. 自我介绍，并介绍一个有难度的技术问题

**建议时长：60～90 秒。**

**参考回答：**

面试官您好，我是吉林大学计算机相关专业的本科生，求职方向是后端开发。我系统学习过 Java 后端，也有游戏中台的服务端实习经历，主要接触客服系统和支付风控相关需求，使用过 Redis、MySQL、定时任务和多实例部署下的并发控制。

实习中我负责过一个支付风控黑名单的到期解封功能。业务上，用户被临时封禁后需要在指定时间自动解封。我用 Redis ZSet 保存待执行任务，`score` 是解封时间，定时任务分批扫描 `score <= 当前时间` 的记录并调用解封接口。这个需求表面上是一个定时任务，真正的难点是多实例重复执行、解封与重新封禁并发、任务删除与业务执行无法组成同一事务。

当时的实现使用了 ZSet、`SetNX` 和幂等解封来减少重复处理。复盘后我认为更完整的设计还应加入封禁版本号、数据库条件更新、失败重试和监控告警，保证旧任务不会覆盖新状态，并在“任务不丢”和“允许重复”之间做明确选择。这个项目让我意识到，分布式锁只能解决一部分互斥问题，最终一致性仍要靠业务幂等、版本校验和补偿机制。

**表达边界：** 不要主动声称“完全高可用”或“绝对不重复”。如果没有生产指标证据，不要给出吞吐、CPU 或线上零故障数字。

### 2. ZSet 的 key、member 和 score 怎样设计？

**建议时长：30～45 秒。**

**参考回答：**

这三个字段要围绕“能按时间查询”和“能唯一定位一条业务任务”设计：

- `key` 表示这类待解封任务，例如 `customer-server:pay-risk:black`；数据量较大时也可以按项目或分片拆 key。
- `member` 至少包含 `userId + projectId`，因为同一个用户在不同游戏中的封禁状态互相独立。更稳妥的方案还会带上 `banVersion`，唯一标识本次封禁事件。
- `score` 使用解封时间戳，使任务按到期时间有序。

查询时使用 `score <= now` 找到已经到期的任务，而不是按与当前时间的绝对距离查“最近任务”。业务状态应以数据库或游戏服务为准，ZSet 只是调度索引，不能作为唯一事实源。

### 3. 为什么每批只取 100 条？积压超过 100 条怎么办？

**建议时长：40～60 秒。**

**参考回答：**

100 是批大小，不是“最多只能有 100 个待解封用户”。正确查询条件是先筛选所有 `score <= now` 的到期任务，再按 score 从小到大取前 100 条。这样限制单轮网络返回量和业务调用量，避免一次拉取过多任务拖垮下游。

如果积压超过 100 条，本轮处理完成后应立即继续拉下一批，直到没有到期任务，或者达到本轮最大处理时间；不能固定等到下一个很长的调度周期。工程上还要监控最老任务延迟、ZSet 到期任务数、处理成功率和失败数。若长期积压，应增加受控并发、分片或工作队列，而不是简单把批大小无限调大。

### 4. 怎样查询所有已经到期的任务？

**建议时长：20～30 秒。**

**参考回答：**

Redis 6.2 及以后可以写：

```redis
ZRANGE customer-server:pay-risk:black -inf <now> BYSCORE LIMIT 0 100 WITHSCORES
```

旧写法是：

```redis
ZRANGEBYSCORE customer-server:pay-risk:black -inf <now> WITHSCORES LIMIT 0 100
```

它的复杂度是 `O(log N + M)`，`N` 是 ZSet 元素总数，`M` 是本次返回的数量。`LIMIT` 只是限制一批返回多少条，后续仍要持续处理积压。

### 5. 分布式锁解决什么问题？锁粒度为什么是用户加项目？

**建议时长：45～60 秒。**

**参考回答：**

锁主要防止多个实例同时扫描到同一条 ZSet 记录，并发调用解封接口、重复写审计日志。锁粒度应对应业务唯一实体，即 `projectId + userId`，而不是只锁 `userId`，否则一个游戏的解封会无意义地阻塞另一个游戏。

获取锁不能只说 `SETNX`。至少应使用带过期时间和唯一 token 的原子命令，例如 `SET lockKey token NX PX ttl`；释放时校验 token 后再删除，避免实例 A 的锁过期后误删实例 B 新拿到的锁。锁 TTL 过短仍可能在业务未完成时失效，因此还要有续期、合理的超时控制，或让数据库条件更新成为最终兜底。

**边界：** Redis 锁解决的是一段时间内的互斥，不自动保证业务幂等、跨 Redis 与数据库的事务，也不自动解决主从切换下的所有一致性问题。

### 6. 多个游戏项目的封禁状态怎样存储？

**建议时长：30～45 秒。**

**参考回答：**

不能在全局用户表里只放一个 `blocked` 字段，因为同一个用户可能在 A 游戏正常、在 B 游戏被封禁。业务主键至少应包含 `projectId + userId`，如果还有支付、聊天等多种策略，还要再带 `strategyType`。

我会把游戏服务或业务数据库中的这条项目级策略记录作为事实源，保存状态、解封时间和版本号；Redis ZSet 只保存可重建的调度索引。这样即使 Redis 丢数据，也可以根据数据库中的待解封记录进行补偿或重建。

### 7. 不同项目是不同记录，为什么还需要锁？

**建议时长：30～45 秒。**

**参考回答：**

不同项目之间不需要互斥，真正需要防的是多个服务实例处理同一个 `projectId + userId` 任务。因此锁也必须是记录级，而不是用户级或全局级。

即使最终的 `UPDATE status = NORMAL` 是幂等的，重复执行仍可能重复调用下游 SDK、重复写日志或触发重复通知，所以仍有协调价值。但锁不是唯一方案，也可以使用调度级 leader、Lua 原子领取任务、消息队列竞争消费，再用数据库幂等作为最后防线。

### 8. 解封时用户又被重新封禁，怎样避免旧任务误解新封禁？

**建议时长：60～90 秒。这是本场项目深挖的核心。**

**参考回答：**

仅靠用户维度的分布式锁不够，因为重新封禁链路如果不使用同一把锁，旧解封任务仍可能覆盖新状态。根因是任务没有标识“它对应的是哪一次封禁”。

我会给每次封禁增加单调递增的 `banVersion`，任务携带 `projectId + userId + banVersion`。执行解封时做条件更新：只有数据库仍处于封禁状态、版本仍等于任务版本、并且 `unbanAt <= now` 才能解封。伪 SQL 如下：

```sql
UPDATE risk_policy
SET status = 'NORMAL'
WHERE project_id = ?
  AND user_id = ?
  AND status = 'BLOCKED'
  AND ban_version = ?
  AND unban_at <= NOW();
```

如果更新行数为 0，说明用户已被重新封禁、提前解封或状态发生变化，这个旧任务直接作废。这样正确性来自版本校验，而不是寄希望于两个链路“时间上不要碰巧并发”。

### 9. 为什么多个实例都扫描同一批任务？能否分片？

**建议时长：45～60 秒。**

**参考回答：**

让所有实例都扫描同一批 key，虽然可以靠记录锁去重，但会产生重复查询和锁竞争，扩容后扫描压力反而上升。更合理的方案有三类：

1. 通过调度级 leader 锁，只允许一个实例扫描，再把任务交给线程池处理。
2. 按 `projectId` 或稳定哈希进行分片，每个实例只负责部分分片；实例变化时需要处理重平衡。
3. 使用 Lua 原子领取任务或消息队列，让多个 worker 竞争消费而不是重复扫描。

小规模业务选择 leader 加批处理最简单；数据量和并发上来后再分片。面试时应先说明实际实现，再讲扩展方案，不能把优化方案说成已经部署。

### 10. 已经分片后还需要锁吗？

**建议时长：30～45 秒。**

**参考回答：**

正常情况下，稳定分片能显著减少同一任务被多个实例处理，但不能完全替代幂等和原子领取。实例重启、租约过期、重平衡、任务重试或网络超时都可能造成重复处理。

所以我会把锁从“主要正确性手段”降为协调手段，最终仍依靠任务唯一 ID、版本校验和条件更新。分片保证大多数时候不冲突，幂等保证发生重复时结果仍正确。

### 11. 应该先删 ZSet 任务还是先执行业务？

**建议时长：60～90 秒。**

**参考回答：**

两种顺序各有失败窗口：

- 先 `ZREM` 再解封：如果删除后服务崩溃或下游失败，任务会丢失。
- 先解封再 `ZREM`：如果业务成功后服务崩溃，任务会再次执行。

通常我更倾向于“至少一次”处理：先执行可幂等的业务，成功后再确认并删除任务。重复可以通过版本条件更新和请求幂等键消化，而任务永久丢失更难发现。如果下游是外部 SDK，还要处理“对方已成功但本地超时”的不确定结果，此时应用相同幂等请求 ID 重试。

更完整的方案是给任务增加 `PENDING/PROCESSING/DONE` 状态或使用可靠队列，并提供超时回收、有限重试、死信和人工补偿。Redis 与业务数据库之间没有天然事务，必须明确接受哪一种交付语义。

### 12. 删除时怎样避免把刚更新的新任务删掉？

**建议时长：45～60 秒。**

**参考回答：**

如果 member 只有 `userId + projectId`，重新封禁会通过 `ZADD` 更新同一 member 的 score。旧 worker 随后直接 `ZREM member`，就可能把新的解封计划一起删掉。

有两种稳妥做法：

1. member 带 `banVersion`，旧任务和新任务是两个不同成员；执行前再用数据库版本校验。
2. 删除前用 Lua 原子比较当前 score 是否仍等于本次读取的旧 score，匹配才删除。

```lua
local current = redis.call('ZSCORE', KEYS[1], ARGV[1])
if current and tonumber(current) == tonumber(ARGV[2]) then
    return redis.call('ZREM', KEYS[1], ARGV[1])
end
return 0
```

版本号比单纯比较时间戳表达力更强，因为两个业务事件可能恰好使用相同时间，也便于审计和条件更新。

### 13. 能否按 `score <= now` 批量删除所有到期任务？

**建议时长：30～45 秒。**

**参考回答：**

不能在只处理了前 100 条后直接执行 `ZREMRANGEBYSCORE key -inf now`，因为它会把其余尚未处理的到期任务也删除，造成任务丢失。

只能确认并删除已经成功处理或已经原子领取的成员。若要批量领取，可以用 Lua 在同一个 key 上完成“按 score 取一批并移除”，但移除后还要有 processing 集合、重试队列或数据库任务表承接，否则 worker 崩溃仍会丢任务。

## B. Redis 限流设计

### 14. 设计“单用户 60 秒内最多访问 5 次”的 Redis 限流系统

**建议时长：60～90 秒。**

**参考回答：**

我会先确认语义：题目要求的是任意连续 60 秒内最多 5 次，因此应使用滑动窗口，而不是自然分钟的固定窗口。key 按用户和接口区分，例如 `rate:{uid}:{routeId}`；ZSet 的 score 是请求时间戳，member 使用 `timestamp + requestId` 保证同一毫秒内的请求不会互相覆盖。

一次请求要完成四步：删除窗口外记录、统计窗口内数量、判断是否超过 5、允许时写入本次请求并设置过期时间。四步必须通过 Lua 脚本在 Redis 内原子执行，否则并发请求都可能先读到 4，随后一起放行。

拒绝时应返回明确的限流结果和可选的重试时间；同时监控拒绝率和热点 key。若业务只接受近似限流且 QPS 很高，可以考虑令牌桶；若只是固定窗口，可用 `INCR + EXPIRE`，但窗口边界可能在很短时间内放过接近两倍请求。

### 15. Redis 常用数据类型有哪些？本题选什么？

**建议时长：20～30 秒。**

**参考回答：**

常用基础类型是 String、Hash、List、Set、Sorted Set；实际还常用 Stream、Bitmap、HyperLogLog 和地理位置能力。这个题需要按请求时间排序、删除窗口外数据并统计窗口内数量，所以 Sorted Set 最自然。

如果只做固定窗口计数，String 的 `INCR` 更简单；数据结构应由限流语义决定，而不是看到 Redis 就固定回答 ZSet。

### 16. Hash 加 List 保存最近 5 次访问怎样更新？有什么问题？

**建议时长：30～45 秒。**

**参考回答：**

逻辑上可以为每个用户维护一个长度最多为 5 的队列：新请求到来时看队头时间，如果请求数已满且 `now - head < 60s` 就拒绝，否则弹出过期时间并把当前时间追加到队尾。

但 Redis Hash 的 value 不是一个可直接操作的嵌套 List，通常需要序列化后整段读改写，或者额外建立 List key。更关键的是“检查、弹出、追加”在并发下不是原子的，需要 Lua 或事务保护。ZSet 能直接按时间范围删除和计数，因此表达更清晰。

### 17. 用 ZSet 实现滑动窗口并保证原子性

**建议时长：60～90 秒，可边讲边写脚本。**

```lua
-- KEYS[1] = rate:{uid}:{routeId}
-- ARGV[1] = nowMillis
-- ARGV[2] = windowMillis，例如 60000
-- ARGV[3] = limit，例如 5
-- ARGV[4] = 唯一 requestId
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', now - window)
local count = redis.call('ZCARD', KEYS[1])

if count >= limit then
    return {0, count}
end

redis.call('ZADD', KEYS[1], now, ARGV[4])
redis.call('PEXPIRE', KEYS[1], window + 1000)
return {1, count + 1}
```

**口述补充：** Redis 保证单个脚本原子执行，所以不会出现多个并发请求同时读到旧计数再一起放行。时间源应统一，可以使用网关统一时钟或 Redis 服务端时间；member 必须唯一。生产中还要限制脚本执行时间，并考虑 Redis 故障时采用 fail-open 还是 fail-closed。

### 18. 多个 URL 或接口怎样设计 key？

**建议时长：30～45 秒。**

**参考回答：**

如果每个接口独立限流，使用 `rate:{uid}:{routeId}`。`routeId` 应是规范化的接口标识，例如 `GET:/orders/{id}`，不能直接拼完整 URL，否则查询参数和动态路径会制造大量 key。

如果还要做用户总限额，可以再维护 `rate:{uid}:all`。一次请求同时受“总限额”和“接口限额”约束时，需要明确先后顺序；若要求严格原子，可将相关 key 放到同一 Redis Cluster hash slot 后用 Lua 一次判断。

## C. 操作系统

### 19. 虚拟地址和物理地址有什么区别？

**建议时长：30～45 秒。**

**参考回答：**

虚拟地址是进程看到的地址，每个进程通常拥有独立、连续的虚拟地址空间；物理地址对应实际 RAM 中的物理页框。虚拟地址带来进程隔离、权限控制、共享内存和按需分配，使程序不需要关心物理内存是否连续。

同一个虚拟地址在不同进程中可以映射到不同物理页；不同进程的不同虚拟地址也可以映射到同一物理页，例如共享库和共享内存。

### 20. 物理地址是内存还是磁盘？怎样完成地址转换？

**建议时长：45～60 秒。**

**参考回答：**

物理地址通常指 RAM 的地址，不是磁盘地址。CPU 生成虚拟地址，MMU 先查 TLB；未命中时根据页表把虚拟页号转换成物理页框号，再加页内偏移得到物理地址。

如果页表项表明该页当前不在内存，会触发缺页异常，由操作系统把数据从可执行文件、映射文件或交换区加载到物理页，再更新页表后继续执行。因此磁盘是缺页换入换出的后备存储，但不能说“虚拟地址直接映射到磁盘地址”。

### 21. 进程和线程有什么区别？

**建议时长：40～60 秒。**

**参考回答：**

进程是资源隔离和拥有的基本单位，拥有独立虚拟地址空间、文件描述符表等资源；线程是进程中的执行流，也是常见的 CPU 调度单位。一个进程内的线程共享代码段、堆和打开的文件，但每个线程有自己的栈、寄存器上下文和线程局部存储。

进程隔离强，崩溃影响相对可控，但创建和通信成本更高；线程通信方便、切换通常更轻量，但共享内存会带来数据竞争，需要锁、原子变量或消息传递来同步。

### 22. `fork()` 后子进程能看到父进程的变量 A 吗？

**建议时长：30～45 秒。**

**参考回答：**

能。假设父进程执行 `A = 5` 后调用 `fork()`，子进程会看到当时内存快照中的 `A = 5`。Linux 通常通过写时复制实现：父子进程最开始共享只读物理页，任一方写入时内核才复制对应页。

所以父子进程中的 A 在逻辑上是两个独立变量。子进程把 A 改成 6，不会直接把父进程的 A 也改成 6；要共享后续修改必须使用共享内存等 IPC 机制。

### 23. 进程间通信方式有哪些？

**建议时长：30～45 秒。**

**参考回答：**

常见 IPC 包括匿名管道、命名管道、消息队列、共享内存、信号量、信号、Unix Domain Socket 和网络 Socket，也可以通过内存映射文件通信。

选择时看数据量、是否需要跨机器、消息边界和同步方式。共享内存速度快，但必须配合互斥锁或信号量；管道简单，适合有亲缘关系的进程；Socket 接口统一，既能本机也能跨网络；信号只适合传递少量事件，不能承载普通业务数据。

### 24. 管道是什么？父子进程怎样使用匿名管道？

**建议时长：45～60 秒。**

**参考回答：**

匿名管道是内核维护的字节流缓冲区，`pipe(fd)` 返回读端 `fd[0]` 和写端 `fd[1]`。通常先创建管道再 `fork()`，父子进程继承描述符，然后各自关闭不用的一端：

```c
int fd[2];
pipe(fd);
pid_t pid = fork();

if (pid == 0) {
    close(fd[1]);
    char buf[16] = {0};
    read(fd[0], buf, sizeof(buf));
    close(fd[0]);
} else {
    close(fd[0]);
    write(fd[1], "hello", 5);
    close(fd[1]);
}
```

管道没有天然消息边界，读写可能需要循环处理；所有写端关闭后，读端才会读到 EOF。匿名管道通常用于有亲缘关系的进程，无亲缘进程可以使用命名管道 FIFO 或 Socket。

## D. 计算机网络

### 25. HTTP 位于哪一层？

**建议时长：15～20 秒。**

**参考回答：**

HTTP 是应用层协议，规定请求、响应、方法、状态码、首部和语义。它不直接负责可靠传输，下面还会经过传输层、网络层和链路层。

### 26. HTTP 的传输层使用什么协议？

**建议时长：20～30 秒。**

**参考回答：**

不能笼统回答“HTTP 一定使用 TCP”。HTTP/1.1 和 HTTP/2 通常运行在 TCP 之上，HTTPS 还会在 HTTP 与 TCP 之间使用 TLS；HTTP/3 运行在 QUIC 之上，而 QUIC 基于 UDP 实现可靠传输和多路复用。

面试官如果问传统 HTTP，先答 TCP，再主动补充 HTTP/3 的例外即可。

### 27. TCP 和 UDP 有什么区别？

**建议时长：45～60 秒。**

**参考回答：**

TCP 面向连接，向应用提供可靠、有序、无消息边界的字节流，并通过序号、确认、重传、流量控制和拥塞控制保证传输。连接建立通常需要三次握手，关闭通常涉及四次挥手。

UDP 面向数据报，保留消息边界，不负责连接建立、可靠重传和有序交付，因此首部和状态更轻，但应用需要按场景自行处理丢包、乱序和拥塞。不能说 UDP“没有校验”：UDP 有校验和，只是它不提供 TCP 那套可靠传输机制。

实时音视频、DNS 等场景常使用 UDP，但“视频一定用 UDP、大文件一定用 UDP”都不准确，具体取决于上层协议和对延迟、可靠性的权衡。

### 28. 网站无法访问，怎样分层排查？

**建议时长：60～90 秒。**

**参考回答：**

我会先界定现象，再沿链路逐层缩小范围：

1. 浏览器开发者工具确认是 DNS、连接、TLS、超时还是已经收到 HTTP 状态码，并判断是单个用户、单个地区还是全量故障。
2. 用 `nslookup` 或 `Resolve-DnsName` 检查域名解析结果和 CNAME 链。
3. 用 `Test-NetConnection host -Port 443`、`nc -vz` 检查目标端口是否可达；`ping` 只能辅助判断，ICMP 被禁不代表网站不可用。
4. 用 `curl -v --connect-timeout 3 --max-time 10 https://host/path` 观察卡在 DNS、TCP 建连、TLS 握手还是等待首字节。
5. 已收到 HTTP 响应后，再检查反向代理、路由、鉴权、应用日志、下游依赖和数据库。

关键是用阶段和时间点定位，而不是把 4xx、5xx、DNS 和网络故障混在一起。

### 29. HTTP 404 可能是什么原因？

**建议时长：25～40 秒。**

**参考回答：**

404 说明请求通常已经到达某个 HTTP 服务器，并且服务器认为目标资源不存在。常见原因包括路径拼错、服务未部署该路由、静态资源缺失、反向代理路由或 Host 配置错误、网关转发到错误版本、重写规则或 CDN 缓存问题。

请求方法不支持更规范的状态码通常是 405；本地网络完全不通一般拿不到 404。因此看到 404 后应重点检查“响应来自哪一层”和路由配置，而不是先判断为网络断开。

### 30. 浏览器一直转圈，怎样用命令定位？`curl` 不返回说明什么？

**建议时长：60～90 秒。**

**参考回答：**

一直转圈不是一个具体错误，可能卡在 DNS、TCP 连接、TLS、服务端处理或响应体传输。可以这样定位：

```powershell
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443
curl.exe -v --connect-timeout 3 --max-time 10 https://example.com/
tracert example.com
```

`curl -v` 会显示解析到的 IP、连接、TLS 和请求响应过程。只用 `curl -I` 发送的是 HEAD 请求，有些服务不支持，不能把它当成唯一判断。`curl` 默认并不会无限自动重试；长时间不返回可能是连接或读取阶段没有超时，因此应显式设置 `--connect-timeout` 和 `--max-time`。

若端口可达但 TLS 失败，检查证书、SNI 和系统时间；若 TLS 成功但首字节很慢，转向反向代理、应用线程池、下游依赖和慢查询。

### 31. 域名怎样转换成 IP？

**建议时长：45～60 秒。**

**参考回答：**

浏览器先查自身缓存，操作系统再查 hosts 和本地 DNS 缓存。未命中时，系统的 stub resolver 把请求交给配置的递归 DNS 解析器。

递归解析器先查缓存；仍未命中时，通常按根服务器、顶级域服务器和权威 DNS 的转介链查询，处理可能存在的 CNAME，最终取得 A 或 AAAA 记录并按 TTL 缓存，再把 IP 返回给客户端。客户端随后才与目标 IP 建立 TCP 或 QUIC 连接，并在 HTTPS 场景完成 TLS 握手。

需要注意：通常是递归解析器替客户端完成逐级查询，不是浏览器亲自依次访问所有 DNS 服务器。

### 32. 多张同域名图片会复用同一个连接吗？

**建议时长：40～60 秒。**

**参考回答：**

取决于 HTTP 版本和连接状态。HTTP/1.1 默认支持持久连接，同一连接可以连续承载多个请求；为了并发加载，浏览器也可能对同一源建立少量多个 TCP 连接。

HTTP/2 通常在一个 TCP 连接上通过多个 stream 并发复用请求；HTTP/3 在一个 QUIC 连接上多路复用。是否能复用还受 origin、证书、代理、连接空闲超时和服务器配置影响。因此不能回答“每个图片都重新三次握手”，也不能绝对说“所有图片永远共用一个连接”。

## E. 数据结构与算法

### 33. 什么是二叉搜索树？

**建议时长：20～30 秒。**

**参考回答：**

二叉搜索树对每个节点都满足：左子树所有键小于当前键，右子树所有键大于当前键；重复键如何放置需要事先约定。因为这个有序性，对它做中序遍历会得到有序序列。

这里说的是整棵左右子树，不只是左右孩子与当前节点比较。

### 34. 二叉搜索树搜索复杂度是多少？最坏是多少？

**建议时长：20～30 秒。**

**参考回答：**

搜索复杂度是 `O(h)`，其中 `h` 是树高。树近似平衡时 `h = O(log n)`；如果插入顺序让树退化成链表，最坏是 `O(n)`。

因此普通 BST 不能无条件回答 `O(log n)`。AVL 树、红黑树等自平衡结构才会通过旋转把高度控制在对数级。

### 35. 有序序列逐个插入普通 BST 会得到什么？

**建议时长：20～30 秒。**

**参考回答：**

如果按升序逐个插入普通 BST，每个新元素都比已有节点大，会一直成为右孩子，最终退化成一条右斜链；降序则退化成左斜链，搜索和插入变成 `O(n)`。

要注意“按顺序插入”和“用有序数组构造平衡树”是两道不同的问题。后者可以每次选中点作为根，递归构造，得到高度为 `O(log n)` 的平衡树。

### 36. 堆是什么？大小关系和复杂度怎样？

**建议时长：35～50 秒。**

**参考回答：**

堆首先是一棵完全二叉树，通常用数组存储。最大堆满足每个父节点都大于等于孩子，因此根是全局最大值；最小堆相反，根是全局最小值。

堆只保证父子关系，不保证左右孩子有序，也不保证某棵子树内部完全有序。查看堆顶是 `O(1)`，插入和删除堆顶是 `O(log n)`，建堆可以做到 `O(n)`，查找任意指定元素最坏仍是 `O(n)`。

### 37. 100 万个整数取最大的 100 个，怎样做？

**建议时长：先用 60 秒讲方案，再用 5～8 分钟写代码。**

**先给结论：**

- 如果数据能放入内存、只要求找出结果且不要求有序，Quickselect 平均时间 `O(n)`、额外空间 `O(1)`，符合本场面试官的追问方向。
- 如果数据是流式输入、内存受限或希望复杂度更稳定，维护大小为 `k` 的最小堆，时间 `O(n log k)`、空间 `O(k)`，工程上更容易写对。
- 全量排序是 `O(n log n)`，做了不必要的排序。

**Quickselect 思路：**

目标是找到升序下标 `n - k`。每轮随机选择 pivot，通过三路分区把数组划分为“小于 pivot、等于 pivot、大于 pivot”三段。如果目标下标落在左段，只处理左段；落在右段，只处理右段；落在等值段就结束。随机 pivot 降低持续极端不平衡的概率，三路分区能避免大量重复值导致明显退化。

```java
import java.util.Arrays;
import java.util.concurrent.ThreadLocalRandom;

public class TopK {
    public static int[] topKLargest(int[] nums, int k) {
        if (nums == null || k < 0 || k > nums.length) {
            throw new IllegalArgumentException("invalid input");
        }
        if (k == 0) {
            return new int[0];
        }

        int target = nums.length - k; // 第 k 大对应的升序下标
        int left = 0;
        int right = nums.length - 1;

        while (left <= right) {
            int pivot = nums[ThreadLocalRandom.current()
                    .nextInt(left, right + 1)];

            // [left, lt) < pivot, [lt, gt] == pivot, (gt, right] > pivot
            int lt = left;
            int i = left;
            int gt = right;

            while (i <= gt) {
                if (nums[i] < pivot) {
                    swap(nums, lt++, i++);
                } else if (nums[i] > pivot) {
                    swap(nums, i, gt--);
                } else {
                    i++;
                }
            }

            if (target < lt) {
                right = lt - 1;
            } else if (target > gt) {
                left = gt + 1;
            } else {
                break;
            }
        }

        // 结果包含最大的 k 个数，但内部不保证有序
        return Arrays.copyOfRange(nums, target, nums.length);
    }

    private static void swap(int[] nums, int i, int j) {
        int temp = nums[i];
        nums[i] = nums[j];
        nums[j] = temp;
    }
}
```

**复杂度与边界：**

随机化 Quickselect 的期望时间是 `O(n)`，最坏仍是 `O(n^2)`；三路分区对大量重复值更友好。如果要求返回的 100 个数有序，还要对结果做一次 `O(k log k)` 排序。必须检查 `k = 0`、`k > n`、空数组、全相等、已有序、逆序和大量重复值。

**最小堆备选回答：**

遍历所有数，堆未满时入堆；堆满后，只有当前值大于堆顶才弹出堆顶并加入当前值。遍历结束后，堆中就是最大的 100 个数。由于 `k = 100` 很小，`O(n log k)` 在工程上也非常实用，并且可以处理无法一次装入内存的数据流。

## 三、本场回答中暴露出的主要问题

1. **项目描述不够稳定。** 扫描周期、key 设计、状态表位置前后说法有冲突。下次应固定为“业务事实源、ZSet 调度索引、任务唯一标识、执行流程、失败语义”五部分。
2. **把分布式锁说成了完整正确性方案。** 锁只能减少重复，无法单独处理重新封禁覆盖、锁过期、任务丢失和 Redis 与数据库跨系统一致性。
3. **Redis 命令不熟。** `ZRANGEBYSCORE`、`ZREM`、`ZREMRANGEBYSCORE` 的用途和风险应能直接说出。
4. **操作系统基础混淆。** 物理地址对应 RAM，不是磁盘；`fork()` 后子进程能看到父进程快照，并采用写时复制。
5. **网络回答存在事实错误。** HTTP 不是基于 UDP 的传统协议，TCP 也不能简单说成“更安全”；404 不是一般意义上的网络不通。
6. **排障缺少分层方法。** 应区分 DNS、TCP、TLS、HTTP、代理、应用和下游依赖，并为每层给出可执行命令。
7. **数据结构复杂度缺少高度变量。** BST 搜索应先答 `O(h)`，再说明平衡时 `O(log n)`、退化时 `O(n)`。
8. **算法编码前没有先固定不变量。** Quickselect 应先明确目标下标、分区区间含义、pivot 选择和左右边界，再开始写代码。
