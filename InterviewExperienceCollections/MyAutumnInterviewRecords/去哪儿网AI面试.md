## 二、本场结论

这是一场覆盖面较广、单题追问较深的 AI 基础面。AI 面试官通常不会根据候选人的犹豫主动降难度，而是会继续追问上一问中的关键词。因此，第一问如果只说出一个表面结论，后续很容易被连续追到原理和边界。

本场相对可取的地方：

1. 知道 B+ 树叶子节点链表适合范围扫描，也意识到非叶子节点只存索引键可以降低空间开销。
2. 短链系统中想到了数据库、唯一短码、索引和 Redis 缓存等核心组件。
3. NoGo 项目能够说明版本对局、胜率比较以及“搜索深度不是越深越好”的真实调整过程。
4. 对 AI 生成代码没有盲目肯定，主动提到了人工 Code Review、历史代码兼容性和模块化改造。

主要失分点：

1. **JVM 概念混淆。** G1 的关键不是把堆简单分成新生代、中年代和老年代，而是基于 Region、并发标记、回收收益预测和转移压缩来选择回收集合。
2. **并发工具没有形成模板。** “主线程等待多个子任务”应优先想到 `CountDownLatch`、`CompletableFuture.allOf` 或 `join`，而不是先猜 `synchronized`、`ReentrantLock`、读写锁。
3. **B+ 树只答了范围查询。** 等值查询追问真正考察的是非叶子节点更紧凑、扇出更大、树高更低，从而减少页访问次数。
4. **网络分层记忆不牢。** OSI 七层和 TCP/IP 四层被混在一起，HTTP、TCP/UDP、IP 所属层次也答反了。
5. **短链设计缺少端到端链路。** 应按“需求与容量 -> 短码生成 -> 写链路 -> 跳转读链路 -> 一致性 -> 高可用与安全”展开，而不是边想边堆组件。
6. **短码唯一性方案错误。** 多个哈希函数仍不能数学上保证无冲突；应使用全局唯一 ID 转 Base62，或使用随机码加唯一索引和冲突重试。
7. **缓存一致性顺序不稳。** 更新场景不应先更新缓存再更新数据库。常用方案是数据库作为事实源，提交数据库后删除缓存，并为删除失败建立可靠重试。
8. **项目选择与题目不完全匹配。** 面试官问“后端开发项目”，原回答用了偏算法工程的 NoGo 项目。可以讲，但开头应先说明边界；更稳妥的是换成真实实习中的后端项目。
9. **表达过于碎片化。** 多次使用“可能”“不是很清楚”“这个是什么”后继续猜。AI 面试中更好的处理是先承认未知边界，再给出自己确定的部分。

### 2. G1 相比 CMS 有哪些改进？可配置停顿时间怎样实现？

**建议时长：75～90 秒。**

先说结论：G1 的目标是在大堆场景下同时兼顾吞吐量和可预测停顿。它不是简单把堆再分几代，而是把整个 Java 堆划分成大小相等的 `Region`，每个 Region 在运行时可以承担 Eden、Survivor、Old 或 Humongous 等角色。

相比 CMS，G1 主要有四点改进：

1. CMS 主要回收老年代并采用标记清除，容易产生内存碎片；G1 在回收时会把存活对象转移到新的 Region，整体上属于压缩式回收，可以减少碎片。
2. G1 通过并发标记掌握各 Region 的存活对象比例，再在 Mixed GC 中优先选择回收收益高的老年代 Region，不要求每次完整回收整个老年代。
3. G1 使用 Remembered Set 记录跨 Region 引用，回收某组 Region 时不必扫描整个堆。
4. G1 有停顿预测模型。`-XX:MaxGCPauseMillis` 表示软目标，G1 根据最近各类 Region 的扫描、复制耗时和存活数据，估算一次停顿能纳入多少 Region，然后构造 Collection Set。

需要强调，停顿目标不是 SLA，也不是保证每次 GC 都能在这个时间内结束。对象存活率、分配速度、堆大小、Humongous 对象和系统负载都可能让实际停顿超过目标。

### 3. G1 怎样选择 Region？停顿目标过短有什么影响？

**建议时长：60 秒。**

G1 会结合并发标记结果和历史耗时预测来选择 Collection Set。Young GC 主要回收年轻代 Region；Mixed GC 还会从老年代候选 Region 中，优先选择垃圾占比高、预计回收收益大、复制成本能够放进本次停顿预算的 Region。

如果把 `MaxGCPauseMillis` 配置得过短，G1 为了追求单次停顿目标，通常会减小一次回收的工作量，年轻代也可能变小。结果是 GC 更频繁、CPU 消耗增加、吞吐量下降；如果回收速度长期追不上对象分配和晋升速度，还可能出现并发周期启动过晚、Evacuation Failure，甚至退化到 Full GC。

所以调优不能只盯单次停顿，还要同时看 P99 停顿、GC 频率、吞吐量、分配速率、晋升速率、堆占用和 Full GC 次数。停顿目标应结合业务延迟预算和压测结果设定。

### 4. 主线程等待三个独立子任务完成，怎样实现？

**建议时长：60～75 秒。**

如果只是一次性等待固定数量的子任务，我会优先使用 `CountDownLatch`。主线程创建计数为 3 的 Latch，每个子任务在 `finally` 中调用 `countDown()`，主线程调用 `await()`。把 `countDown()` 放在 `finally` 中很重要，否则某个任务异常时，主线程可能永久等待。

```java
CountDownLatch latch = new CountDownLatch(3);
AtomicReference<Throwable> error = new AtomicReference<>();

for (int i = 0; i < 3; i++) {
    executor.submit(() -> {
        try {
            runTask();
        } catch (Throwable t) {
            error.compareAndSet(null, t);
        } finally {
            latch.countDown();
        }
    });
}

boolean finished = latch.await(3, TimeUnit.SECONDS);
if (!finished) {
    throw new TimeoutException("subtasks timeout");
}
if (error.get() != null) {
    throw new RuntimeException("subtask failed", error.get());
}
```

如果三个任务本身有返回值、异常传播和后续组合逻辑，我更倾向于使用 `CompletableFuture.allOf(f1, f2, f3)`，因为它更适合表达异步任务编排。若直接创建了三个 `Thread`，也可以分别调用 `join()`，但在线程池和服务端代码里通常不手工创建线程。

### 5. 为什么不建议手工加锁？更合适的工具是什么？

**建议时长：45～60 秒。**

锁解决的是共享临界区的互斥或条件等待，而这个需求本质上是“一次性等待 N 个事件完成”。如果自己用 `synchronized` 或 `ReentrantLock` 维护计数器，还要正确处理 `Condition`、虚假唤醒、异常、超时和中断，代码复杂而且容易遗漏通知。

因此，一次性倒数等待直接使用 `CountDownLatch`；需要收集异步结果和异常时使用 `CompletableFuture.allOf`；需要多轮让一组线程在同一屏障点会合时，才考虑 `CyclicBarrier` 或 `Phaser`。选择并发工具时应先描述同步语义，而不是先从锁名字里猜一个。

### 6. CountDownLatch 和 CyclicBarrier 的核心区别

**建议时长：60 秒。**

`CountDownLatch` 是一次性的倒数门闩。一个或多个等待线程调用 `await()`，其他任务完成后调用 `countDown()`；计数减到 0 后门闩永久打开，不能重置。它适合“主线程等待 N 个子任务完成”。

`CyclicBarrier` 是可循环使用的栅栏。固定数量的参与线程都调用 `await()`，最后一个线程到达后，所有线程一起继续；下一轮还可以再次使用。它适合“多个线程分阶段并行计算，每个阶段结束时必须会合”。它还可以配置 barrier action，让最后到达的线程触发一次汇总动作。

异常语义也不同：`CountDownLatch` 中某个子任务失败不会自动把异常传给等待线程，需要业务代码自己记录；`CyclicBarrier` 中线程超时、中断或失败可能让栅栏进入 broken 状态，其他等待线程会收到 `BrokenBarrierException`。

### 7. InnoDB 为什么使用 B+ 树，而不是 B 树？

**建议时长：75 秒。**

数据库索引的核心成本通常是页访问，而 B+ 树更适合磁盘和页式存储。

第一，B+ 树的非叶子节点只保存索引键和子指针，不保存完整数据记录，所以同样大小的 16KB 页可以容纳更多键，扇出更大、树高更低。树更低意味着一次查询通常需要更少的页读取。

第二，所有记录都位于叶子层，查询路径长度更稳定。InnoDB 聚簇索引的叶子节点保存完整行，二级索引的叶子节点保存主键值。

第三，叶子页之间按键顺序通过双向链表连接。定位范围起点后，可以沿叶子页顺序扫描，不需要不断回到父节点，适合范围查询、排序、前缀扫描和分页。

第四，B+ 树与 InnoDB 的页分裂、页合并、Buffer Pool 缓存和预读机制配合较好。相比之下，B 树把记录分散在内部节点和叶子节点中，扇出更小，也不如 B+ 树方便连续范围扫描。

### 8. 等值查询时，B+ 树相比 B 树有什么优势？

**建议时长：45～60 秒。**

严谨地说，单次等值查询中 B 树有可能在内部节点提前命中，所以不能笼统地说 B+ 树每次都更快。B+ 树的主要优势来自整体工程特性：内部节点更紧凑，同一页能放更多键，因此扇出更大、树高通常更低；在大规模索引中，这往往能减少页访问和随机 I/O。

另外，B+ 树所有记录都在叶子层，查询路径更稳定，内部页也更容易常驻 Buffer Pool。即使查询的是二级索引，先定位二级索引叶子上的主键，再回到聚簇索引查整行，访问模型也清晰一致。

边界上，如果查询只需要二级索引中已有的列并形成覆盖索引，就不需要回表；如果需要其他列，才需要通过主键回表。

### 9. 非叶子节点只存索引键和指针，有什么好处？

**建议时长：45 秒。**

最直接的好处是提高单个索引页的扇出。假设页大小固定，不存完整行后，每个内部页可以放下更多“键 + 子页指针”，从而降低树高，减少从根节点走到叶子节点所需的页访问次数。

第二个好处是内部节点体积更小、热点更集中，更容易被 Buffer Pool 缓存。根节点和高层内部节点常驻内存后，大部分查询只需要访问少量低层页。

第三个好处是所有实际记录集中在叶子层，叶子页可以保持有序并串成链表，范围扫描和顺序预读更高效。

不能说它只是“减少内存开销”。更重要的是，它用更高扇出换来了更低树高和更少 I/O。

### 10. OSI 七层和 TCP/IP 四层怎样划分？

**建议时长：75～90 秒。**

OSI 从下到上是七层：

1. 物理层：传输比特流，典型对象是网线、光纤、中继器。
2. 数据链路层：帧、MAC 地址和局域网内传输，典型协议或技术有 Ethernet、VLAN，典型设备是二层交换机。
3. 网络层：跨网络寻址和路由，典型协议有 IPv4、IPv6、ICMP，典型设备是路由器。
4. 传输层：端到端进程通信，典型协议是 TCP、UDP。
5. 会话层：建立、管理和恢复会话。
6. 表示层：数据编码、压缩和加解密。
7. 应用层：直接服务应用，典型协议有 HTTP、DNS、SMTP、FTP。

TCP/IP 四层从下到上是：网络接口层、网际层、传输层、应用层。对应关系是：网络接口层大致覆盖 OSI 的物理层和数据链路层；网际层对应网络层；传输层仍是传输层；应用层合并了 OSI 的会话层、表示层和应用层。

面试中最容易答反的是：HTTP 和 DNS 属于应用层，TCP 和 UDP 属于传输层，IP 属于网络层或网际层。

### 11. TCP 和 UDP 的核心区别是什么？

**建议时长：60 秒。**

TCP 是面向连接、可靠、有序的字节流协议。建立连接通常需要三次握手，关闭连接通常需要四次挥手；它通过序号、确认、重传、校验、流量控制和拥塞控制保证数据按序交付。TCP 不保留应用消息边界，所以应用层需要自己处理粘包和拆包。

UDP 是无连接、尽力而为的数据报协议。它保留报文边界，但不保证送达、不保证顺序，也不自动重传；头部和状态更少，延迟与实现开销通常更低，并支持广播和多播。

典型选择是：HTTP/1.1 和 HTTP/2 通常基于 TCP；DNS 的普通查询常用 UDP，响应过大或区域传送会使用 TCP；实时音视频、游戏状态同步等更看重低延迟并能容忍部分丢包的场景常使用 UDP。HTTP/3 的 QUIC 则运行在 UDP 之上，但在用户态重新实现了可靠传输和拥塞控制等能力。

### 12. 怎样设计 QPS 1000、跳转延迟小于 50ms 的短链系统？

**建议时长：2～3 分钟。**

我会先确认短链是否允许修改、有效期、读写比、是否需要访问统计、QPS 1000 是平均值还是峰值，以及 50ms 是平均延迟还是 P99。原转写中的读写比参数识别不清，现场不能擅自补一个数字。

核心数据模型可以包含：`short_code`、`original_url`、`status`、`expire_at`、`created_at`、`version`。数据库对 `short_code` 建唯一索引，原始 URL 不一定建唯一索引，因为同一长链可能允许生成多个短码，用于不同渠道统计。

写链路如下：

1. 校验 URL 协议、长度、域名安全和有效期，防止生成恶意跳转。
2. 通过全局唯一 ID 转 Base62，或者随机码加唯一索引与冲突重试，生成短码。
3. 在 MySQL 中提交映射关系，数据库作为事实源。
4. 新增后可以主动写 Redis，也可以等第一次读时回填；如果写缓存失败，数据库记录仍然存在。

跳转读链路如下：

1. 用户访问 `/s/{code}`，服务先查 Redis 的 `code -> original_url/status/expire_at`。
2. 缓存命中且记录有效，直接返回 `302`。如果业务保证映射永久不变且希望浏览器长期缓存，也可以评估 `301`，但短链平台一般用 `302` 更便于更新和统计。
3. 缓存未命中时查询 MySQL，查到后回填 Redis；不存在的短码写一个较短 TTL 的空值，防止缓存穿透。
4. 热点 Key 失效时使用互斥重建或逻辑过期，避免大量请求同时回源。

QPS 1000 本身不算极端，关键是让绝大部分跳转只访问 Redis，并通过连接池、超时、限流和水平扩容控制尾延迟。访问统计不要同步阻塞跳转，可以异步写入日志或消息队列。还要监控请求量、P95/P99 延迟、缓存命中率、数据库回源率、错误率、热点 Key 和恶意 URL 命中情况。

### 13. 短链新增和更新时，怎样保证缓存与数据库一致？

**建议时长：75～90 秒。**

我会把 MySQL 作为事实源，使用 Cache Aside。

新增场景中，先在数据库事务里插入短码映射并提交。之后可以写 Redis 进行预热，也可以让第一次查询回填。即使缓存写入失败，读请求仍能回源数据库，不会丢失事实数据。

更新场景中，优先执行“更新数据库并提交 -> 删除缓存”，而不是“先更新缓存 -> 再更新数据库”。删缓存后，下一个读请求会从数据库读取新值并回填。为了处理删除缓存失败，可以把失效事件写入本地事务 Outbox，再由后台任务或 MQ 重试；也可以使用 Binlog/CDC 驱动缓存失效。TTL 只作为最终兜底，不能替代可靠失效链路。

并发边界是：一个旧读请求可能在写事务提交后，把旧值重新写回缓存。可以通过版本号、缓存写入前后的二次校验、短 TTL，或者在必要场景使用延迟二次删除来缩短不一致窗口。延迟双删只是补充手段，延迟时间很难精确覆盖所有慢查询，不能把它说成绝对一致。

短链映射如果业务允许，最好设计为创建后不可变；修改时创建新短码，可以显著降低一致性和浏览器缓存问题。

### 14. 怎样生成全局唯一短链码并避免冲突？

**建议时长：75 秒。**

更稳妥的方案是先生成全局唯一的数值 ID，再把它编码成 Base62 短码。ID 可以来自数据库号段服务、Snowflake 类算法或专门的发号器；Base62 只做可逆编码，不再引入哈希碰撞。数据库仍然要对 `short_code` 建唯一索引，作为最后一道约束。

如果不希望短码暴露大致业务量，可以对 ID 做可逆置换、加盐混淆，或者直接生成固定长度随机码。随机码方案必须依赖唯一索引检测冲突，冲突时重新生成，并监控重试率。码空间要根据预计记录量和可接受碰撞概率规划，不能等快耗尽时再扩长度。

对长 URL 直接做哈希再截断也可以使用，但截断后一定存在碰撞可能，需要保存“哈希结果 + 原 URL”，冲突时加盐或重试。使用多个哈希函数只能降低碰撞概率，不能保证全局唯一。

### 15. 分享一个最具技术挑战的后端开发项目

**建议时长：90 秒。**

本场原回答讲的是 NoGo 计算机博弈项目。它更偏算法工程，不是典型业务后端，所以开头应先把边界说清：

如果允许我讲一个包含数据管理和批量评测的算法工程项目，我想讲 NoGo 博弈程序；如果您更希望听纯后端项目，我也可以换成实习中的配置热更新或风控平台需求。

NoGo 是一种规则与围棋相近的棋类博弈。我们的目标是编写能够在 Botzone 一类对战平台自动决策的程序。初期主要使用蒙特卡洛树搜索和启发式规则，后续也尝试过基于自博弈数据的模型方案。我的主要工作是搭建早期 MCTS 主框架，队友在此基础上参与调参和判断规则优化。

项目的难点不是把某个算法跑通，而是在有限单步时间内平衡搜索广度、深度和模拟次数，并建立可重复的评测方法。我们保存对局记录和版本信息，通过固定基线、交换先后手和批量对局比较版本，再根据失败棋局定位启发式规则或搜索参数的问题。

这个项目让我建立了一个很重要的工程认识：算法改动必须有固定预算、可重复基线和量化评测，不能仅凭几局主观感受判断新版本更好。

> 边界：现有材料能支持“参与 NoGo 博弈、MCTS 主框架、队友共同优化、自博弈和批量对局评测”。具体对局总量、模型结构、奖项名称和个人贡献比例应在面试前对照代码、证书和实验记录确认。

如果面试官强调必须是后端项目，更推荐切换到实习中的 Apollo 配置接入：

我在在线途游实习时参与过客服中台的动态配置接入。项目已经有 Apollo 和公司内部 gconf 组件，我没有开发配置中心本身，负责的是业务侧多 Namespace 接入和配置变更后的运行时处理。

这项工作的难点是配置更新不能只“收到通知就覆盖”。我需要基于 `BindConfig` 绑定多组配置，通过 `OnChange` 监听变更；收到新配置后先解析和校验，成功后再替换内存对象，并按配置类型联动清理缓存或 reload Worker。并发读写时要用 `RWMutex` 或原子指针保证读线程看见的是完整版本；如果解析失败，则继续保留旧配置并记录日志和告警，不能让一份错误配置把服务打坏。

这个项目让我理解了动态配置的完整边界：Apollo 和 gconf 负责配置发布、监听等基础能力，业务代码仍要负责校验、原子切换、失败回退和变更后的副作用。面试时只说明已实际完成和验证的接入，不补充未经确认的线上指标。

### 16. 用哪些指标判断 NoGo 版本更好？

**建议时长：75 秒。**

核心指标是相同资源限制下的对局胜率，但不能只看一两局。我会固定每步时间或总计算预算，让新旧版本与同一个基线机器人进行足够多的对局，并尽量交换先后手、固定或记录随机种子，减少先手优势和随机波动。

原回答中提到每个版本运行 500～1000 局后比较胜率曲线。更严谨时还应给出样本数和置信区间，判断差异是否超过随机波动。除了总胜率，我还会拆分：

1. 先手和后手胜率。
2. 对不同类型对手的胜率，避免只针对一个固定机器人过拟合。
3. 平均单步耗时、P95/P99 决策耗时和超时率。
4. 非法落子率、异常退出率等正确性指标。
5. 若有可稳定定义的阶段标签，再分析前中后盘失败分布；不能用“智能程度”这种不可测量的词代替指标。

只有在胜率提升、耗时不超预算、稳定性不下降时，才能认为新版本更好。

### 17. 哪次最初判断被对局结果推翻？

**建议时长：60～75 秒。**

我们最初有一个判断：MCTS 搜索得越深，决策质量就会越好。后来在固定单步时间的大量对局中发现，单纯提高搜索深度不一定提升胜率，有时反而更差。

原因是计算预算固定。搜索树更深意味着能够展开的分支和完成的模拟次数减少，节点价值估计的方差变大；如果启发式策略本身有偏差，深搜还可能把这种偏差放大。博弈搜索真正要平衡的是搜索深度、广度、模拟次数以及探索和利用，而不是只优化一个参数。

后来我们固定对手、先后手和计算预算，对深度、模拟次数以及探索参数做分组实验，用批量胜率和超时率比较结果，再选择更稳定的组合。这次经历让我意识到，工程判断必须能被实验推翻，参数调优也要一次只改变少量变量，否则无法知道效果来自哪里。

### 18. 最近半年怎样学习并落地 AI 工具？

**建议时长：90 秒。**

最近半年我主要学习和实践的是 Coding Agent 和 Agent 工作流，包括 Codex、Claude Code 等工具。我不只把它们当聊天机器人，而是关注它们怎样读取仓库上下文、执行命令、生成改动、运行测试，以及怎样通过计划和验收条件约束输出。

在实际开发中，我使用过这样一套流程：技术方案先由人完成评审，再整理一份任务上下文，写清业务背景、已有代码、约束、编码规范、详细设计和验收条件；然后让 AI 先阅读相关模块并拆分任务，再按小批次生成代码和测试，执行自测后由人工检查 Diff、补充边界用例并做 Code Review。

它对样板代码、测试骨架、仓库检索和重复修改比较有效，但对跨模块架构、历史兼容和隐含业务规则并不可靠。因此最终方案、权限边界、代码合并和线上结果仍由开发者负责。我没有在原文中给出经过统计的提效百分比，所以更稳妥的结论是：它降低了部分检索和重复编码成本，但不能替代人工设计和验证。

### 19. 选择 AI 编程工具时看什么？

**建议时长：60～75 秒。**

我主要看六点：

1. 仓库上下文理解：能否准确找到调用链、配置、测试和历史约定，而不是只看当前文件。
2. 代码正确性：生成结果能否编译，是否覆盖异常和边界，是否会虚构不存在的 API。
3. 工具执行能力：能否受控地搜索、修改、运行测试和读取失败日志。
4. 可控性和可审查性：是否支持小 Diff、权限确认、回滚，以及清楚展示执行了哪些动作。
5. 数据安全：代码和业务上下文能否在公司的合规范围内使用，敏感数据是否会被发送到不允许的环境。
6. 成本与效率：延迟、上下文容量、稳定性和实际节省的时间是否匹配成本。

模型名称只是其中一个因素。我会用同一类真实任务比较“首次正确率、人工返工量、测试通过率和完成时间”，而不是只凭主观感觉说某个模型更自然。原文中的具体工具和模型版本识别不稳定，正式回答前应按真实使用记录确认。

### 20. 最影响落地的 AI 输出问题是什么？怎样解决？

**建议时长：90 秒。**

最影响落地的问题是：AI 往往能让当前功能跑通，但没有充分理解历史架构和后续扩展，容易生成耦合度高、重复逻辑多、命名和仓库风格不一致的代码。跨模块调用时，它还可能把多个下游能力硬编码进一个流程，导致测试困难，也不便于后续替换实现。

我的调整分四步：

1. 在生成前补全约束，明确现有接口、禁止修改范围、错误处理、兼容要求和验收用例。
2. 让 AI 先给出调用链和修改计划，确认理解一致后再分小模块实现，避免一次生成大面积改动。
3. 对下游能力抽出清晰接口或适配层，把编排逻辑与具体执行解耦，并补充单元测试、集成测试和失败场景。
4. 人工逐行审查 Diff，实际运行编译、静态检查和测试；对高风险操作保留人工确认，不把 AI 的“已经完成”当作验证结果。

如果发现问题来自上下文不足，我会补充相关代码和失败日志；如果问题来自架构判断，我会由人工先确定模块边界，再让 AI 完成局部实现。核心原则是让 AI 负责可验证的局部工作，开发者负责设计、事实核对和最终结果。

## 五、本场高频追问的速记版

1. G1：Region 化、并发标记、Remembered Set、转移压缩、停顿预测；`MaxGCPauseMillis` 是软目标。
2. 等待三个任务：一次性用 `CountDownLatch`，结果编排用 `CompletableFuture.allOf`，多轮会合用 `CyclicBarrier`。
3. B+ 树：内部节点更小 -> 扇出更大 -> 树高更低 -> 页访问更少；叶子有序链表适合范围扫描。
4. 网络分层：HTTP/DNS 在应用层，TCP/UDP 在传输层，IP/ICMP 在网络层。
5. 短链读链路：Redis -> MySQL 回源 -> 回填 -> 302；统计异步化。
6. 短码：全局唯一 ID -> Base62；随机码要唯一索引和冲突重试；多哈希不能保证唯一。
7. 缓存一致性：数据库是事实源，更新数据库后删缓存，失败通过 Outbox/MQ/CDC 重试，TTL 仅兜底。
8. 项目评测：固定预算、固定基线、交换先后手、足量样本、胜率与置信区间、延迟和异常率。
9. AI 辅助开发：人定方案和边界，AI 做局部实现与测试，人工审查并实际运行验证。
