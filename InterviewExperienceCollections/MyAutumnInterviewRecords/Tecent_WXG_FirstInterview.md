## 二、本场面试暴露出的主要问题

1. **没有先讲清业务闭环。** 介绍了审核规则和动作编排，却没有说明审核结果由谁消费、如何影响用户或支付主体、何时关单。
2. **个人贡献与平台能力混在一起。** TCC、Agent、数据同步平台属于公司既有能力；个人工作是业务接入、规则和动作编排、异常处理及联调。
3. **指标口径没有对齐。** `28%`、`115 次`、`36 次` 的统计周期和分母不同，现场没有先定义“链路触发、规则命中、自动完成、转人工”等事件。
4. **异步等待方案没有形成持久化状态机。** 不能依靠请求上下文或在内存中等待 5 秒；回调与超时应通过持久化状态、幂等键和条件更新竞争完成。
5. **ES 一致性回答偏离问题。** 面试官问的是 MySQL 更新后如何同步 ES，正确重点应是 CDC/Outbox、顺序、幂等、补偿和业务可接受的延迟，而不是后台轮询大表。
6. **把“状态机”误当成并发原子性。** 先查状态再更新存在 TOCTOU 竞态，需要数据库条件更新、版本号或唯一约束把检查和写入合并为一个原子操作。
7. **对进程、线程和协程的定义不够准确。** 进程主要承担资源隔离，线程通常是操作系统 CPU 调度的基本单位，协程由语言运行时或用户态调度。
8. **算法表达与复杂度不够稳定。** 合并 K 个链表应为 `O(N log K)`，滑动窗口可用单调队列做到 `O(N)`，零钱兑换是 `O(amount * coins.length)`，不是笼统的 `O(N^2)`。
9. **AI 协作容易被理解成“AI 代写”。** 应主动说明自己负责需求判断、方案取舍、代码审查、测试和交付责任，AI 只承担受控的分析与生成工作。

## 四、逐题参考回答

### 1. 请做一个自我介绍

面试官您好，我是吉林大学 2027 届本科生，求职方向是后端开发。

我有两段后端实习经历。第一段在途游游戏的平台中心，参与客服系统和支付风控相关需求；第二段在字节国际支付风控团队，参与运营审核平台、客诉自动化链路和处罚查询链路建设。我主要使用 Go 完成业务开发，也在持续学习 Java 后端、MySQL、Redis、消息队列和并发编程。

实习之外，我做过一个舆情分析 Agent 工程原型，用来学习意图解析、任务规划、受控工具调用和可恢复工作流。我希望继续做复杂业务场景下的后端工程，重点提升系统稳定性、并发控制和业务抽象能力。我的介绍就这些，谢谢面试官。

> 建议时长：60～90 秒。不要在自我介绍中展开所有项目细节，把追问空间留给面试官。

### 2. 你在字节的实习已经结束了吗

已经结束。我从 4 月实习到 8 月，8 月 14 日正常离职，离职前完成了负责需求的开发、测试和交接。

### 3. 这段实习有转正机会吗？为什么没有转正

当时团队没有面向校招实习生的转正 HC，所以没有走转正流程。这是团队招聘名额的原因，不是因为项目或绩效问题。我完成实习后正常参加秋招。

### 4. 请具体介绍一下你在字节国际支付风控团队做了什么

我们团队服务海外多条业务线的支付风控运营场景。上游风控策略对风险事件进行识别和处置后，部分用户会发起申诉或客诉，案件进入运营审核平台，由系统或 BPO 人工完成复核。

我投入最多的是客诉自动化链路。链路先接收并校验案件字段，再汇聚身份、支付和历史申诉等信息，把内部 Agent 的结构化结果作为一个决策信号，与业务规则共同判断。证据充分且规则明确时输出通过或拒绝；材料缺失、结果冲突、依赖异常或未覆盖场景转人工。随后由动作编排层调用受控的下游能力并回写工单状态。

我的职责是后端字段接入、规则和动作编排、异常兜底及联调。我不负责底层 Agent 模型训练，也不把公司配置平台或同步平台说成自己开发的。

### 5. 审核结果由谁消费，最终会执行什么动作

审核平台不能只产出一个标签。它会先持久化审核结论、原因码和规则版本，再由动作编排层根据案件类型调用对应下游能力：通过通常意味着解除或调整原有限制，拒绝通常维持原处置，无法确定则进入人工审核；动作完成后再回写工单并关单。

具体是否涉及退款、资金追回或某一种账户限制，要由真实案件类型和下游合同决定。我负责结果编排和接口调用，不负责制定资金规则。面试前还应从实际需求文档中准备一条脱敏案例，把“输入事实 -> 审核结论 -> 下游动作 -> 用户结果”讲完整。

### 6. 规则和动作的配置化具体配置了什么

配置可以分为四部分：

1. **路由信息：** 业务线、案件类型、规则版本和生效范围。
2. **条件表达式：** 对结构化字段做等值、集合、范围等判断。
3. **动作编排：** 规则命中后按顺序执行哪些受控动作，以及动作需要的参数。
4. **异常策略：** 条件不满足、依赖超时或结果冲突时，是终止、重试还是转人工。

代码侧应维护字段和动作白名单，并对参数做 Schema 校验。配置只能选择允许的能力，不能填写任意函数名或任意脚本。转写能确认我接入了规则表达式和顺序动作；白名单、灰度、审计等属于应说明的安全边界，不能在没有证据时说成全部由我独立建设。

### 7. 使用流程引擎还是文件配置

当时不是我从零开发一套 BPMN 流程引擎，而是基于公司内部 TCC 配置平台发布文件形式的业务配置。业务服务通过内部配置库读取并绑定到结构体，再由本地规则执行器和动作注册表执行。

因此更准确的说法是“配置驱动的轻量编排”，而不是“我开发了一个通用流程引擎”。

### 8. 文件配置发布后怎样解析和执行

服务启动时会通过公司配置库加载指定 Namespace 的配置，完成反序列化、结构校验并绑定到内存结构；配置变更时由平台推送或客户端监听更新。收到案件后，业务代码按业务线和案件类型选出规则集，计算表达式，再按照动作列表调用代码中已注册的执行器。

要把“配置分发”和“业务调度”分开：TCC 负责配置存储、发布和下发，业务服务负责何时选规则、怎样执行动作以及失败如何兜底。

### 9. 配置平台是你们开发的吗

TCC 和配套解析库是公司的内部基础设施，不是我开发的。我的工作是在业务服务中定义配置结构、接入平台、实现规则和动作的业务映射，并完成测试与发布。

### 10. 多条业务线怎样区分和隔离规则

接入层会携带明确的业务线标识或业务 Tag。规则选择时把业务线、案件类型和版本作为路由维度，只加载当前上下文对应的规则集，避免一条业务线的配置误作用到另一条业务线。

工程上还应隔离 Namespace 或配置目录、发布权限、灰度范围和监控维度。运行时必须校验“案件业务线与规则归属一致”，不能只依赖运营人员配对名称。

### 11. 公共规则未来按业务线变化，怎样避免复制

当时主要是按业务线分别配置，尚未抽出稳定的公共规则。这个事实要如实说，不能把复盘方案包装成已上线能力。

如果继续演进，我会分三层：公共字段归一化和通用谓词作为平台能力；公共规则作为可复用模板；业务线只覆盖差异参数或追加专属规则。规则最终在发布阶段展开成确定版本，运行时不做复杂继承。这样既减少复制，也能避免公共模板改动直接影响所有业务线。

### 12. 怎样避免团队成为规则交付瓶颈

问题的本质是所有权设计。如果每条业务规则都必须由后端工程师改配置并发布，业务数量增加后研发一定会成为瓶颈。

更合理的方向是由业务或运营拥有规则内容，研发提供受控的配置产品：字段和动作白名单、Schema 校验、权限审批、历史样本回放、灰度、版本审计和一键回滚。全新的字段来源或动作仍由研发接入；已有能力的组合由业务方在安全边界内自助完成。

### 13. `28%`、`115 次`、`36 次` 分别是什么口径

这三个数字不能直接放在一起相除，因为转写没有证明它们使用同一统计周期和同一个分母。面试时应先定义事件：

- **链路触发次数：** 满足入口条件并进入自动化流程的案件数。
- **规则命中次数：** 至少一条目标规则成立的案件数。
- **自动完成次数：** 最终由自动链路产出终态并成功执行动作的案件数。
- **转人工次数：** 进入流程后因不确定、异常或策略要求而转人工的案件数。

如果 `115` 是链路触发数、`36` 是自动完成数，那么二者的比例约为 `31.3%`，不能据此解释 `28%`。`28%` 很可能来自另一统计窗口或另一分母，但当前材料无法确认。最稳妥的回答是：“这三个数的口径我现场没有讲清，回去会按埋点和看板重新核对；在口径确认前不会把它们当成同一组效果指标。”

### 14. Agent 决策链与客诉自动化链路有什么区别

它不是完全独立的第二套流程，而是在原有客诉自动化链路上新增 Agent 信号。第一阶段先把案件接入、规则判断、动作执行和人工兜底跑通；后续再接入算法团队提供的 Agent 结果，作为规则判断的一个输入，提高材料识别或身份判断能力。

所以二者关系是“基础自动化编排 + 新增智能信号”，不能写成两个互不相关的大项目。

### 15. 是否负责 Agent 本身的开发

我负责的是 Agent 能力的后端接入，不负责模型训练或子 Agent 的内部推理逻辑。具体来说，我负责准备约定输入、调用内部接口、校验结构化响应、处理超时和错误码，并把结果映射为规则可消费的字段。模型选型、提示词和算法效果迭代由算法团队负责。

### 16. 怎样平衡 Agent 时效和效果

我会从准入、预算和降级三层控制：

1. 只让边界明确、确实需要 Agent 信号的案件调用，不让所有请求无差别进入慢链路。
2. 为调用设置明确的时间预算和截止时间，并记录 P95/P99、超时率和自动完成率。
3. Agent 超时或失败时返回 `unknown`，继续走传统规则或转人工，不能把依赖故障解释为拒绝用户。

如果业务不要求同步返回，可以把 Agent 调用异步化；但异步化只是释放请求线程，不等于可靠性已经解决，还需要持久化状态、消息重试和超时补偿。

### 17. 异步通知消费失败后怎样避免卡单

使用 MQ 时按“至少一次投递”设计。消费者收到结果后，先使用案件 ID 或请求 ID 做幂等校验，完成业务状态更新后再确认消息；处理失败则有限重试，超过阈值进入死信队列并告警。还需要定时对账扫描长期处于 `PENDING` 的案件，重新拉取结果或转人工。

仅仅说“消费者再读一次 MQ”不完整。必须同时说明 ACK 时机、重复投递幂等、重试上限、死信和最终对账。

### 18. 系统怎样判断 5 秒超时

不能把 5 秒截止时间只放在一次请求的 `context` 中，然后期望它跨进程、跨重启继续生效。发起 Agent 请求时，应持久化案件状态、请求 ID 和 `deadline_at`；随后通过延迟消息、时间轮或定时扫描触发超时事件。

Agent 回调和超时任务都尝试把状态从 `PENDING` 原子地改成自己的终态。谁先成功谁生效，后到事件只做幂等返回。这样即使服务重启，超时判断仍可恢复。

### 19. 怎样设计框架级长等待机制

我会把它建模为一个持久化状态机，而不是让线程或协程一直睡眠：

```text
创建任务并持久化 PENDING + deadline
        |
        +--> 发送 Agent 请求
        |
        +--> 注册延迟消息/超时索引

Agent 回调 --------------------+
                              +--> CAS: PENDING -> SUCCEEDED
超时事件 ----------------------+--> CAS: PENDING -> TIMED_OUT
```

核心字段包括 `case_id`、`request_id`、`status`、`deadline_at`、`version` 和结果摘要。回调和超时处理器通过数据库条件更新竞争，例如：

```sql
UPDATE audit_task
SET status = 'SUCCEEDED', version = version + 1
WHERE request_id = ? AND status = 'PENDING' AND version = ?;
```

受影响行数为 1 表示本次事件获胜；为 0 表示任务已被其他事件处理。消息发送与本地状态提交之间可使用 Outbox 保证最终一致，失败任务进入重试、死信和对账流程。超时后的业务语义应是转人工或走传统规则，而不是默认 Agent 判断为否。

### 20. 同步到 ES 解决了什么问题

这条链路面向多条件处罚记录查询。原先查询需要在 MySQL 的处罚主体和处罚明细等大表上进行组合筛选或关联，出现慢查询并影响下游。改造后把查询所需字段反规范化为 ES 文档，读请求优先使用 ES 的过滤和检索能力，MySQL 仍作为事实源。

回答时不能只说“表大所以用 ES”。还要说明查询条件组合、执行计划、扫描行数和改造前后 P95；如果这些数据没有核实，就诚实说没有保留准确值，不临时编数字。

### 21. MySQL 数据怎样同步到 ES

转写能确认的是：同步依赖公司内部数据平台，并且当时存在定时同步；我没有开发同步平台的底层实现。我的工作边界是定义索引字段、接入 ES 查询，并处理查询异常和必要的回源逻辑。

如果面试官问通用方案，可以补充“常见做法是初始全量同步，再订阅 binlog/CDC 做增量更新”，但必须明确这是设计知识，不是假装当时系统已经这样实现。

### 22. 能否接受 ES 的旧数据

是否能接受取决于字段和业务 SLA，不能笼统回答“增量不多所以可以”。展示类、统计类查询可能允许分钟级或小时级延迟；影响处罚生效、解除限制或资金决策的字段通常需要更强的新鲜度保障，必要时直接读取 MySQL。

如果采用定时同步，应明确最大延迟、同步水位、哪些接口允许旧读，以及发现滞后时的降级方式。当前转写只能确认现场认为部分延迟可接受，不能证明所有处罚数据都允许一天旧读。

### 23. 为什么不在更新 MySQL 时同步更新 ES

在业务事务中直接同步双写 MySQL 和 ES 会把两个系统耦合在一起，并产生经典的部分失败问题：MySQL 成功而 ES 失败，或 ES 成功而事务回滚。简单重试还可能带来乱序覆盖。

更可靠的方案是让 MySQL 作为事实源，在同一事务中写业务数据和 Outbox，或直接订阅 binlog/CDC；异步消费者根据业务主键和版本号幂等更新 ES。还需要处理初始全量与增量水位、乱序、重试、死信、监控和定期对账。对需要“读己之写”的场景，可以短时间读 MySQL，而不是要求 ES 承担强一致数据库的职责。

### 24. 账户止付/解止付原子能力怎样实现

先把“原子能力”定义清楚：对同一业务主体和同一请求，要么状态迁移成功一次，要么不产生效果，不能重复止付、重复解止付或停在半完成状态。

如果核心状态在单库中，我会把检查和更新合并成一条条件 SQL：

```sql
UPDATE account_control
SET status = 'STOPPED', version = version + 1
WHERE account_id = ? AND status = 'NORMAL' AND version = ?;
```

只有受影响行数为 1 的请求获得执行权。若后续还要调用外部系统，则本地事务中记录状态和 Outbox，外部动作按幂等请求号重试，最终通过回调或对账进入终态。数据库原子更新解决本地并发，Outbox 和幂等解决跨系统最终一致性。

### 25. 怎样避免重入或重复执行

为每次业务操作分配稳定的 `request_id`，在数据库上建立唯一约束，并保存处理状态和结果。重复请求先按 `request_id` 查询：已成功则返回原结果，处理中则返回处理中或稍后查询，失败且可重试才进入受控重试。

业务主体的状态迁移仍需条件更新。幂等键解决“同一请求重复提交”，条件更新解决“不同请求同时操作同一主体”，二者不能互相替代。分布式锁可以减少竞争，但不能取代数据库中的最终约束。

### 26. 状态机并发竞态怎样解决

状态机只规定哪些迁移合法，不自动保证“先读状态、再写状态”是原子的。两个线程都读到 `NORMAL` 后再分别写 `STOPPED`，就会同时认为自己成功。

解决办法是把前置状态写入更新条件，使用 CAS/乐观锁；或在事务中使用 `SELECT ... FOR UPDATE` 串行化同一主体。低冲突场景优先条件更新，高冲突且操作复杂时再考虑行锁。无论哪种方案，都要用数据库受影响行数决定是否真正获得执行权。

### 27. 这是线上实现还是改进方案

这场转写没有确认线上原子能力的完整实现。现场先提出了状态机，经过追问才意识到并发竞态，又提出加锁；因此不能在复盘后把“条件更新 + Outbox”说成自己当时已经上线的方案。

面试时应这样表达：“我当时接入的是公司已有原子能力，底层实现细节没有完全掌握；如果让我设计，我会使用幂等键、数据库条件更新和跨系统补偿。这里是我的复盘方案，不是对线上实现的冒领。”

### 28. GitHub 项目是否主要由 AI 协作完成

是，这个个人项目使用了较多 AI 辅助，AI 生成了相当一部分初始代码。我不会把每一行代码都说成手写，但项目目标、需求边界、方案取舍、代码审查、测试和最终验收由我负责。

我会把 AI 生成的代码视为待审查的外部贡献：逐个模块看 diff，核对数据流和失败路径，运行测试，并对自己不能解释的代码进行重写或删除。个人项目是工程化原型，不是线上生产系统；AI 辅助也不能替代我对最终结果负责。

### 29. AI 协作流程是什么

我的流程通常分为六步：

1. **建立上下文：** 让 AI 读取 PRD、接口文档和相关代码，只输出需求理解、未知项和风险点。
2. **确认方案：** 生成技术方案，我人工核对上下游、数据模型、异常语义和安全边界，再参加团队评审。
3. **拆分任务：** 按服务和模块拆成可独立验证的小任务，明确每步验收标准。
4. **增量实现：** 一次完成一个小任务，审查 diff，不让 AI 在未确认时大范围修改代码。
5. **验证回归：** 补充单元测试、集成测试、异常用例和回归清单，并实际运行。
6. **人工交付：** 经过代码评审、QA 和灰度后发布，由人承担上线责任。

在公司环境中只使用获批的内部工具处理内部文档和代码，不把敏感信息发送到未经授权的外部模型。MCP 或 Skill 只是工具接入与流程复用方式，不会自动保证结果正确。

### 30. Spec 驱动开发的理念和实现

Spec 驱动开发的核心是先把“要解决什么、必须满足什么、怎样验收”变成稳定契约，再让人和 AI 围绕同一份契约设计、实现和验证。它不是把一句需求换成更长的提示词，也不是让 AI 按文档自动开发到底。

一份可执行 Spec 通常包含：背景和目标、范围与非目标、业务规则、数据和接口契约、状态迁移、异常与降级、性能和安全约束、验收标准、测试用例及未决问题。实现过程中任务清单和代码变更都引用这些条目；需求变化先更新 Spec，再调整实现和测试。

### 31. Spec 应该写到什么粒度

默认应写到“行为和契约”粒度，而不是逐行规定实现：输入输出、字段语义、合法状态、接口错误、幂等要求、超时降级和验收用例必须明确；具体局部变量、私有函数拆分通常留给实现者。

只有在既有系统存在稳定集成约束时，才写具体函数、参数或代码位置，例如必须复用某个鉴权入口、事务边界或公共接口。判断标准是：如果换一种内部实现仍能满足合同，Spec 就不应过度绑定原代码结构。

### 32. 进程、线程和协程有什么区别

可以从资源、调度和开销三个维度回答：

- **进程：** 操作系统进行资源隔离和分配的基本单位，通常拥有独立虚拟地址空间、文件描述符等资源。进程切换和通信成本相对较高。
- **线程：** 进程内的执行单元，通常是操作系统 CPU 调度的基本单位。同一进程的线程共享地址空间和大部分资源，因此通信方便，但必须处理数据竞争。
- **协程：** 由语言运行时或用户态库调度的轻量任务。创建和切换成本通常低于线程，可以在少量线程上承载大量并发任务；协程本身不等于并行，真正使用多个 CPU 核仍需要底层多个线程。

以 Go 为例，goroutine 由 Go runtime 使用 G-M-P 模型做 M:N 调度，不是“迷你进程”。阻塞系统调用、抢占、栈增长和调度都由运行时协同处理。

### 33. 现场算法题使用什么语言

我会使用 C++17。现场先确认可以只写函数、无需标准输入输出，再说明会补充必要的数据结构定义和边界用例。语言选择应以自己最熟练、最能稳定写对为准，不要临时切换。

### 34. 合并 K 个升序链表

> 按对话推断题意：给定 `K` 个升序链表，合并为一个升序链表。

使用小根堆维护每条链表当前尚未合并的头节点。初始化时把所有非空链表头放入堆；每次弹出值最小的节点接到结果尾部，再把它的下一个节点放入堆。堆中最多有 `K` 个节点。

设全部链表节点总数为 `N`，每个节点入堆、出堆各一次，时间复杂度是 `O(N log K)`，额外空间是 `O(K)`。不能说成 `O(N log N)`，虽然那是一个宽松上界，但没有体现堆大小只有 `K`。

```cpp
#include <queue>
#include <vector>

struct ListNode {
    int val;
    ListNode* next;
    explicit ListNode(int x) : val(x), next(nullptr) {}
};

class MergeKListsSolution {
public:
    ListNode* mergeKLists(std::vector<ListNode*>& lists) {
        struct Greater {
            bool operator()(const ListNode* a, const ListNode* b) const {
                return a->val > b->val;
            }
        };

        std::priority_queue<
            ListNode*, std::vector<ListNode*>, Greater> heap;
        for (ListNode* head : lists) {
            if (head != nullptr) {
                heap.push(head);
            }
        }

        ListNode dummy(0);
        ListNode* tail = &dummy;
        while (!heap.empty()) {
            ListNode* node = heap.top();
            heap.pop();
            tail->next = node;
            tail = node;
            if (node->next != nullptr) {
                heap.push(node->next);
            }
        }
        return dummy.next;
    }
};
```

边界用例：`K == 0`、所有链表为空、只有一条链表、存在重复值和负数。

### 35. 滑动窗口最大值

> 按对话推断题意：给定数组 `nums` 和窗口大小 `k`，返回每个长度为 `k` 的窗口最大值。

现场使用“最大堆 + 下标”可以做到 `O(N log N)`：堆顶下标过期时持续弹出。但更优解是单调队列。队列保存下标，且对应值从队头到队尾单调递减；新元素进入前，删除队尾所有不大于它的元素，再删除队头已经离开窗口的下标。这样队头始终是当前最大值。

每个下标最多进队和出队一次，时间复杂度 `O(N)`，额外空间 `O(K)`。

```cpp
#include <deque>
#include <vector>

class SlidingWindowSolution {
public:
    std::vector<int> maxSlidingWindow(
            const std::vector<int>& nums, int k) {
        if (nums.empty() || k <= 0 || k > static_cast<int>(nums.size())) {
            return {};
        }

        std::deque<int> dq;
        std::vector<int> answer;
        for (int i = 0; i < static_cast<int>(nums.size()); ++i) {
            while (!dq.empty() && dq.front() <= i - k) {
                dq.pop_front();
            }
            while (!dq.empty() && nums[dq.back()] <= nums[i]) {
                dq.pop_back();
            }
            dq.push_back(i);

            if (i >= k - 1) {
                answer.push_back(nums[dq.front()]);
            }
        }
        return answer;
    }
};
```

边界用例：`k == 1`、`k == nums.size()`、递增数组、递减数组、全部相等、包含负数。若题目保证 `1 <= k <= n`，非法参数分支可以不写，但应口头说明依赖题目约束。

### 36. 零钱兑换

> 按对话推断题意：给定不同面额硬币 `coins` 和目标金额 `amount`，每种硬币可使用无限次，返回凑成目标金额所需的最少硬币数；无法凑成时返回 `-1`。

定义 `dp[x]` 为凑出金额 `x` 的最少硬币数。初始化 `dp[0] = 0`，其余为不可达哨兵值。对每个金额 `x`，枚举所有正数面额 `coin`；当 `x >= coin` 且 `dp[x - coin]` 可达时，用 `dp[x - coin] + 1` 更新。

时间复杂度是 `O(amount * coins.size())`，空间复杂度是 `O(amount)`。

```cpp
#include <algorithm>
#include <vector>

class CoinChangeSolution {
public:
    int coinChange(const std::vector<int>& coins, int amount) {
        if (amount < 0) {
            return -1;
        }

        const int unreachable = amount + 1;
        std::vector<int> dp(amount + 1, unreachable);
        dp[0] = 0;

        for (int current = 1; current <= amount; ++current) {
            for (int coin : coins) {
                if (coin > 0 && coin <= current &&
                    dp[current - coin] != unreachable) {
                    dp[current] = std::min(
                        dp[current], dp[current - coin] + 1);
                }
            }
        }
        return dp[amount] == unreachable ? -1 : dp[amount];
    }
};
```

边界用例：`amount == 0` 返回 `0`，空硬币数组且金额大于零返回 `-1`，无法凑出返回 `-1`。标准题通常保证面额为正数；若接口不保证，必须拒绝或忽略 `coin <= 0`，否则状态转移没有意义。

### 39. 怎样理解面试官的改进建议

面试官的反馈有两层。

第一，不能只记住自己改了哪段代码，要理解需求的完整上下游：谁产生案件、每个字段从哪里来、为什么做这个判断、谁消费结果、失败后怎样恢复，以及最终给用户和业务带来什么变化。只有看懂闭环，才能判断方案是否合理。
