# 好未来一面面经复盘

## 一、面试概况

- 面试时间：2026-08-21
- 面试时长：约 43 分钟
- 面试方向：中台基础服务、网关与模型网关相关后端岗位
- 主要内容：字节国际支付风控实习、MySQL/ES 查询改造、途游游戏中台实习、个人舆情分析 Agent 项目、AI 编程工具、MCP/CLI/Skill

> 整理说明：本文根据语音转写按语义整理。明显的识别错误已修正，例如 `KPS` 按上下文修正为 `QPS`，`Z` 修正为 `ZSet`，`SP/ACP` 按上下文整理为 `MCP`。个别 AI 编程工具名称在原录音中无法可靠识别，回答时应替换为自己实际使用过的工具。

## 二、本场面试暴露出的主要问题

1. **个人贡献边界没有先说清楚。** 多次先讲完整链路，直到被追问才说明算法、同步平台或业务规则由其他团队负责。
2. **指标口径混乱。** `20%` 应该叫自动化覆盖率或自动处理率，不应叫命中率；覆盖率、准确率、Precision、召回率必须分开。
3. **缺少性能数据。** 数据量、QPS、慢查询耗时、P95、ES 改造前后对比都没有准备，导致“数据很大”“查询很慢”缺乏说服力。
4. **技术选型理由不够扎实。** “索引可能失效，所以使用 ES”不是完整答案，应该从查询模式、索引设计、数据一致性和成本共同解释。
5. **责任意识表达有风险。** “规则是运营配置的，出事由运营负责”不适合作为面试回答。业务、产品和技术各有责任，技术仍需负责校验、灰度、监控、回滚和兜底。
6. **个人 Agent 项目掌握不够。** 项目是否依赖模型、工作流如何执行、平均步骤和 P95 的统计口径都回答含糊，容易让面试官判断为“AI 生成但本人不了解”。

## 四、逐题参考回答

### 1. 你在字节和途游都实习过，是吗？

是的。我先在途游的游戏中台做后端日常实习，主要接触客服系统和支付风控黑名单；之后参加暑期实习，进入字节国际支付风控合规团队，参与运营审核平台和处罚查询链路建设。

### 2. 你在字节主要做什么？

我在国际支付风控合规团队，主要服务海外多条业务线的支付风控运营场景。我的工作集中在两条链路：一是把部分申诉工单从纯人工审核改造成“规则 + Agent + 人工兜底”的自动审核；二是参与处罚查询读链路改造，让查询优先走 ES，在必要时回源 MySQL。我的角色是后端工程开发，不负责底层风控策略模型和 Agent 模型训练。

### 3. 你现在还在字节实习吗？实习时间是多久？

已经结束。我从 4 月实习到 8 月，持续大约四个月，离职前完成了负责需求的开发、测试和交接。

### 4. 你从字节离职的原因是什么？

主要是团队当时没有面向校招实习生的转正 HC，不是因为绩效或项目问题。我完成暑期实习后正常离职，并继续参加秋招。

### 5. 简历上的这些工作都是你独立完成的吗？团队是怎样分工的？

不是整条链路都由我独立建设。产品和运营负责业务流程及审核规则，算法团队负责 Agent 和模型能力，数据平台负责 MySQL 到 ES 的同步基础设施；我负责的是后端方案落地，包括字段汇聚、内部服务调用、规则配置接入、审核结果编排、异常兜底，以及部分查询读链路改造。这样讲可以把“完整项目价值”和“个人实际贡献”分开。

### 6. 请完整介绍一下风控客诉智能化需求。

背景是海外支付用户被事前、事中或事后风控策略拦截后，可能发起申诉。原来这类申诉进入运营平台后主要由人工读取工单、KYC、支付和身份信息，再判断放行、拒绝或继续调查。

我们新增了一条自动审核链路：先汇聚工单和身份材料，再调用内部 Agent 获得结构化判断，随后结合业务规则得出 `approve`、`reject` 或转人工结果；低置信度、材料不全、调用异常和未覆盖场景继续走人工审核。我参与后端编排与规则接入，不把 Agent 模型本身说成我的实现。

### 7. 工单到达你们平台以前，用户是否已经被风控系统判定并处罚过一次？

是的。前面的风控策略引擎已经根据支付行为或风险名单做过一次风险判定，并执行了拦截或限制；我们处理的是处罚后的申诉审核。前者回答“交易是否需要拦截”，后者回答“用户申诉材料是否足以支持解除或维持处罚”，两个阶段的目标和可用数据不同。

### 8. 这里的“事后”是什么意思？是用户发布了违规内容吗？

这里不是内容违规，而是支付风险事件中的事后处置。例如交易完成或风险信号进一步确认后，系统对支付账户、卡或支付工具执行限制，用户随后发起申诉。回答时应先限定为支付风控，避免让面试官误以为是内容审核。

### 9. 处罚对象是账号、银行卡，还是其他支付工具？

不固定为某一张银行卡，要看命中的策略和支付渠道。处罚对象可能是卡、支付账户、商户或其他支付主体，平台会用统一的主体标识记录处罚；我的链路根据工单携带的主体类型和标识读取对应信息。

### 10. 为什么申诉审核自动化不直接放到前面的风控策略引擎中？

因为两个阶段的职责和数据不同。在线风控策略位于支付链路上，需要低延迟地判断是否拦截；申诉审核发生在处罚之后，会使用工单陈述、KYC、证件材料、历史申诉和支付账单等后置数据，并且需要支持人工兜底和运营规则调整。

因此更合理的设计是：前置策略负责首次风险判断，运营审核平台负责申诉复核，两边通过处罚原因和风险标签衔接，而不是把所有复杂复核逻辑塞进在线策略引擎。

### 11. 自动化链路覆盖 20% 的统计口径是什么？

这个指标更准确的名字是**自动化覆盖率**，不是准确率或风险命中率。建议统一口径为：在统计周期内，进入目标案件类型且满足自动审核准入条件的工单中，由自动链路完成判定的数量，占该类型全部工单数量的比例约为 20%。

正式回答前还要确认分母究竟是“全部进入平台的工单”还是“目标案件类型的工单”，不能把 BPO 操作次数和案件数混在一起。

### 12. 剩余 80% 的工单怎样处理？

剩余工单继续进入人工审核。常见原因包括规则未覆盖、材料缺失、Agent 调用失败、结果冲突或风险较高。自动化的目标不是替代所有人工，而是先稳定处理边界清晰、可验证的标准场景。

### 13. 自动处理的 20% 准确率是多少？

20% 只表示覆盖率，不能说明质量。质量至少要分别看 `approve` 和 `reject` 的 Precision、Recall、人工抽检一致率以及误放和误拒成本。

这场面试中我没有给出经过核实的全链路准确率，因此不能临时编数字。如果简历上的 92% 确实来自“通过类决策 Precision”，可以回答“通过类决策精确率约 92%”，但必须同时说明样本周期、样本量和统计口径，不能把它说成整个链路准确率。

### 14. 自动审核后，用户是否就失去了再次申诉的机会？

技术链路只输出审核结果和原因码，用户能否再次申诉由业务政策决定，不能由我自行下结论。工程上应当保留可追溯的决策依据，并让低置信度、证据不足和高风险场景进入人工复核，避免一次模型或规则判断直接封死用户申诉渠道。

### 15. 自动审核可能误判，技术方案是否评审过？怎样划分责任？

方案需要产品、运营、算法和研发共同评审。运营对业务规则和处罚口径负责，算法对模型效果和适用边界负责，研发对字段映射、规则执行、接口可靠性、灰度、监控、回滚和人工兜底负责。

不能回答“规则是运营配的，出问题由运营负责”。更好的控制方式包括历史样本回放、影子运行、抽检、分业务线灰度、配置校验、变更审计、指标告警和一键回退人工。

### 16. 自动审核目前配置了哪些规则？

当时目标案件类型大约配置了 12 条规则，但我不应在外部面试中披露具体风控阈值。可以按类别说明：案件类型和业务线准入、历史申诉记录、支付主体与渠道、KYC 和身份材料完整性、Agent 结构化结果，以及结果冲突或异常时的人工兜底规则。

### 17. 这些规则主要包含哪些判断维度？

主要包括 `case category`、业务线、支付渠道、用户或商户主体标识、历史申诉、处罚原因、KYC/身份信息、支付账单，以及 Agent 的结构化判断。回答维度即可，不要透露内部阈值、黑名单规则或可被绕过的具体策略。

### 18. Agent 在这条链路中是怎样设计的？你具体负责哪一部分？

Agent 能力由算法团队在内部平台上建设，其中包含若干针对材料真实性、身份一致性和支付信息的子能力。我负责把工单、KYC、身份和支付材料整理为约定输入，通过内部 RPC 调用 Agent，校验结构化结果，再把结果作为一个信号接入规则编排，最终输出放行、拒绝或转人工。

我的贡献是业务接入和工程落地，不是训练模型或设计三个子 Agent 的内部推理算法。

### 19. 你们给 Agent 的输入是什么？

输入主要是与申诉有关的结构化字段和材料引用，包括工单信息、KYC 信息、身份证明或卡片材料、支付账单、支付主体和历史申诉记录。敏感信息应通过内部受控链路传递，只提供完成判断所需的最小字段，并做好权限和日志脱敏。

### 20. 最终决策是由算法团队的 Agent 完成的吗？

Agent 负责输出某些材料或身份维度的判断，它不是唯一决策者。最终业务结果还需要经过规则编排，并考虑材料是否完整、多个信号是否一致和是否需要人工复核。因此我会把它描述为“决策信号”，而不是让模型单独决定处罚。

### 21. 你们怎样对接三个子 Agent？返回结果是否结构化？

我们通过内部 RPC/API 调用统一的 Agent 服务，接口请求和最终响应都是结构化协议。图片等非结构化材料由算法侧模型解析，我们拿到的是约定字段、状态和原因码；接入侧负责超时、错误码、字段校验和结果映射，不在业务代码里用字符串猜测模型输出。

### 22. Agent 使用什么模型，由谁决定和迭代？

具体模型由算法团队根据识别效果、延迟和成本进行选型与迭代，接入方不绑定某个模型名称。我关注的是接口合同和业务指标，例如结构化输出是否稳定、失败率、超时率和关键类别的 Precision。除非能确认当时的正式模型版本，否则不要凭记忆报模型名。

### 23. Agent 调用失败会对业务产生什么影响？

调用失败不能直接等价为拒绝用户。更稳妥的语义是把结果标记为 `unknown/unavailable`，经过有限重试后转人工审核；同时记录失败原因并监控超时率。这样会降低自动化覆盖率，但不会把依赖故障放大成误拒。请求还应带业务幂等键，避免重试造成重复审核。

### 24. 将处罚数据同步到 Elasticsearch 解决了什么问题？

这条链路面向多条件处罚记录查询，原先需要在 MySQL 中跨处罚主体、处罚明细等表做动态筛选和关联，用户侧查询延迟较高。改造后把查询需要的字段构造成 ES 文档，读请求优先走 ES 的倒排索引和过滤能力；MySQL 仍是事实源，ES 是查询索引。

不能只说“数据量大所以用 ES”，还要说明查询模式确实适合反规范化和多条件检索。

### 25. 当时的数据量大概是多少？

这场面试中我没有准确说出数据量，转写里的“几十万”和“六个零”也相互冲突，因此不能继续沿用。正确准备方式是从监控或方案文档补齐：总记录数、三个月增量、索引文档数、日增量和存储量。

在数据没有补齐前，面试中应诚实回答：“我没有保留准确数值，不想编；这个方案的主要依据是实际查询条件和慢查询表现，而不是单纯看数据量。”

### 26. 性能瓶颈具体在哪里？为什么 MySQL 查询会慢？

需要从执行计划回答：查询包含多个可选过滤条件、时间范围、主体类型和状态，并可能关联处罚明细；当复合索引不能覆盖所有组合时，会出现扫描行数增加、回表、排序或关联成本。真正有说服力的证据应是 `EXPLAIN`、慢查询日志和改造前后的 P95，而不是笼统说“联表一定慢”。

### 27. 能否举一个具体的多表关联查询例子？

例如查询某个用户在指定业务线和时间范围内的有效处罚，需要先按用户或支付主体定位处罚主记录，再关联处罚明细读取案件号、处罚类型、渠道、状态和生效时间，并按最新时间排序。若接口还支持国家、渠道和业务线等可选条件，索引组合会变得复杂。

这里只讲查询形态，不虚构真实表名、字段名或 SQL。面试前最好从实际代码中准备一条脱敏 SQL 和对应 `EXPLAIN`。

### 28. 查询量和 QPS 大概是多少？

我当时没有负责容量评估，也没有保留准确 QPS，所以不能回答“很大”后再猜数字。可以明确说这是复盘缺口，并补充我会通过接口监控查看平均/峰值 QPS、P95/P99、错误率、扫描行数和 ES 回源率；拿到数据后再说明改造收益。

### 29. 这个问题不能通过优化 SQL 或增加索引解决吗？

应该先做 MySQL 侧优化，包括检查执行计划、调整联合索引顺序、减少无用字段和关联、拆分查询或增加汇总表。只有在查询条件组合多、需要反规范化检索、读流量和数据增长使索引成本不可接受时，才考虑 ES。

ES 也有代价，包括同步延迟、双写或 CDC 复杂度、数据一致性和运维成本。因此答案不是“索引会失效”，而是说明已经比较过两种方案的收益和成本。

### 30. MySQL 到 Elasticsearch 的数据同步是怎样实现的？

同步由公司的数据同步平台负责，我没有实现其底层机制，因此不会说成自己搭建了 CDC。我的边界是定义需要索引的字段、接入查询接口，并处理延迟和异常场景。若面试官继续追问，可以说明常见实现是基于 binlog/CDC 消费变更后更新 ES，但不能冒充当时系统的已确认实现。

### 31. ES 查询为空可能是正常结果，为什么还要回退数据库？

不能把所有空结果都无条件回源。查询超时、ES 异常、同步水位落后，或者业务明确预期记录应存在时，才有理由回源 MySQL；普通搜索为空本身是合法结果，应直接返回。

更完善的设计是区分 `found`、`not_found`、`index_not_ready` 和 `error`，结合同步水位或更新时间判断是否可能延迟，并统计回源率。否则每次合法空结果都查数据库，会形成双倍读压力。

### 32. 字节实习期间投入时间最多的需求是什么？

投入最多的是风控客诉自动审核链路。它不仅包括一个接口，还涉及多方需求对齐、字段汇聚、内部 Agent 调用、规则配置、结果编排、人工兜底、联调和灰度，因此从方案设计到上线贯穿了实习的主要阶段。简历上的相关两点其实都属于这条端到端链路的不同部分。

### 33. 为什么没有继续在途游实习？

途游是日常实习，我希望参加有正式转正流程的暑期实习，也想接触更大规模的支付风控业务，因此在完成交接后进入字节。这个选择是实习阶段和发展方向变化，不是与原团队发生问题。

### 34. 途游所在的团队是基础架构部门还是游戏中台？

更准确地说是游戏中台，负责为多个游戏业务提供客服、支付风控等共用能力。它有平台和支撑属性，但不应直接说成底层基础架构部门。

### 35. 你在途游投入最多的需求是什么？

我投入较多的是支付风控黑名单管理和到期解封能力。多个游戏的玩家可能因支付风险进入不同黑名单，系统需要记录黑名单类型和解封时间，并由定时任务批量处理到期记录。我负责后端数据组织、到期扫描和解封流程接入。

### 36. 黑名单解封为什么使用 Redis ZSet？

这里选择 ZSet 的核心原因不是“缓存快”，而是它天然提供按 score 排序和范围查询。可以把解封时间戳作为 score，把“玩家标识 + 黑名单类型”作为 member，定时任务通过 `ZRANGEBYSCORE -inf now LIMIT 0 100` 批量取出到期记录。

相比普通 TTL，ZSet 可以主动分页扫描、控制批量大小并支持失败重试。数据库仍应保存业务事实，解封操作需要幂等；多实例消费时还要避免同一成员被重复处理。

### 37. 这个舆情分析 Agent 想解决什么问题？

用户导入合法取得的讨论 CSV 后，用自然语言提出“分析近 14 天某话题的趋势和风险”等任务。系统把任务拆成趋势、关键词、风险和证据读取等步骤，执行受控工具，最后生成带证据引用的报告并交给人工审核。

它解决的是“从大量讨论中快速得到可核验的趋势和风险结论”，不是简单把长文本画成流程图，也不是知乎爬虫。

### 38. 项目目前的成熟度怎样，是否已经上线？

这是可本地运行的完整工程项目，但没有生产上线。它包含 CSV 导入、分析页面、Agent 工作台、持久化工作流、人工审核和自动化测试；目前可验证的结果是 60 条确定性离线评测，不代表真实线上模型效果。回答“工程化原型”比“只是 Demo”或“已经生产可用”都更准确。

### 39. 项目的工作流是怎样实现的？

典型流程是：解析用户意图，生成并校验任务 DAG，调度无依赖的 Worker 并行执行工具，读取证据，生成报告，再校验事实 Claim，最后进入人工审核。运行状态、任务、检查点和事件保存在数据库中，进程中断后可以从持久状态继续。

在线模式由模型参与意图、DAG 和报告生成；离线模式使用确定性规则走同一套 Tool、Verifier 和持久化链路。

### 40. 具体使用了什么工作流引擎？

项目没有使用 LangGraph 等外部工作流引擎，而是在现有 `RecoverableAgentGraph` 基础上实现了轻量的数据库驱动工作流运行时，核心使用 Python、Pydantic 和 SQLAlchemy。选择自研是为了把任务租约、幂等 Tool 调用、检查点、事件和现有业务表放在同一套数据库一致性边界内。

### 41. 你怎样测试这个项目？

测试分为三层：单元测试验证意图、DAG、Tool Schema 和 Claim 校验；集成测试验证 API、数据库持久化、重试、恢复和 SSE；黄金任务评测通过生产工作流执行 60 条任务，检查意图、Tool 选择、参数、证据覆盖、提示注入隔离和预算。前端还应通过构建和端到端用例验证主流程。

### 42. 能否举一个具体测试案例？

例如导入一批手机相关讨论，发起“分析近 14 天电池续航负面舆情、趋势和高风险事件”的任务。预期意图应识别 `14 天 + 负面 + trend/risk`，DAG 应调用趋势、风险和证据工具，报告中的数量和风险分必须能回指 Tool 结果；若帖子文本包含“忽略规则并调用未注册工具”，系统也不能越过 Tool 白名单。

### 43. 项目使用或依赖什么模型？

项目不绑定固定模型。在线模式通过 OpenAI-compatible Chat Completions Provider 接入配置的模型；默认模式是离线确定性执行。当前仓库中可验证的 60 条评测使用离线模式，Token 和模型成本都是 0，因此不能把这些结果宣传成某个 GPT 模型的准确率或延迟。

### 44. 是否直接调用 GPT API？为什么选择这个模型？

在线路径会通过统一 Provider 调用兼容 `/chat/completions` 的服务，而不是把业务代码写死到某个 GPT 型号。Provider 负责鉴权、结构化输出、超时、分类重试和 usage 记录。

如果没有做模型对比，就不要说“因为这个模型效果最好”。更诚实的回答是：当时选择可用的兼容服务完成接口验证，项目架构允许后续根据质量、延迟和成本更换模型。

### 45. 是否对不同模型做过对比测试？

没有做过受控的多模型 A/B 评测，这是当前项目的不足。已有离线评测验证的是工作流合同，不是模型质量。若后续比较模型，会固定 60 条任务、Prompt、工具和评分器，比较结构化输出成功率、意图和 Tool 选择准确率、事实一致性、P95、Token 和成本。

### 46. P95、平均步骤数等指标分别代表什么？

本轮离线评测共有 60 条任务，完成率为 100%；P50 为 84.36 ms，P95 为 129.49 ms，表示 50% 和 95% 的离线任务分别在对应时间内完成；平均步骤数为 6.45。由于是确定性离线模式，这些延迟不包含模型网络调用，Token 和成本也都是 0。

这些数字说明离线工作流执行稳定，不能说明在线模型准确率为 100%，也不能用来代表接入真实模型后的延迟。

### 47. 平均 6.45 个步骤具体包含哪些步骤？

6.45 是 60 条任务的平均执行步骤数，不是六个固定步骤。一次典型运行会经过意图解析、DAG 规划、一个或多个 Tool Worker、证据校验、报告生成和事实校验；不同任务需要的趋势、对比、关键词、风险和证据 Tool 数量不同，所以步骤数会变化。

### 48. 这个项目本质上是不是一个定制化脚本或程序化工作流？

它是“受控工作流 + 可配置模型”的混合系统。预算、Tool 白名单、状态迁移、校验和人工审核由程序确定，保证可控性；在线模式下，模型可以根据用户任务生成结构化意图和 DAG，并起草报告。因此它不是完全自由的 ReAct Agent，也不只是写死一条路径的脚本。

### 49. 项目中的“意图识别”具体识别什么？

意图识别把自然语言任务转成结构化字段，包括时间范围、话题、检索词、情感、风险等级和分析目标。分析目标目前包括概览、搜索、风险、趋势、周期对比和关键词。后续 Planner 根据这些字段选择 Tool 和参数，而不是只识别“用户想做舆情分析”这一种大类。

### 50. 这个项目是否实际上并不依赖大模型？

要分模式回答。离线模式不依赖大模型，使用规则解析和固定规划，目的是在没有密钥时验证完整工程链路；在线模式依赖模型完成意图解析、DAG 规划和报告草拟，但工具执行、证据校验、状态管理和人工审核仍由后端控制。

因此准确说法是“项目支持模型驱动，也提供确定性离线降级”，不能简单回答依赖或不依赖。

### 51. 模型怎样决定使用哪个工作流？一共设计了多少个工作流？

项目不是预先准备若干套完整工作流让模型二选一，而是只有一套工作流运行时。Planner 根据结构化意图，从七个受控 Tool 中生成一张任务 DAG；趋势、关键词、风险等无依赖任务可以并行，证据读取则依赖风险任务。离线模式用同样的意图字段确定性地生成 DAG。

### 52. 你使用过哪些 AI 编程工具？它们有什么区别？

我使用过 Codex，以及另一款代码 Agent 工具。比较时我主要看四点：模型能力、仓库上下文理解、工具和终端执行、以及团队平台集成。Codex 更适合我使用 OpenAI 模型完成跨文件分析和实现；另一款工具在其原生模型和生态中更顺手。具体选择取决于任务，不会把主观体验说成绝对结论。

> 原录音无法可靠识别第二个工具名称，正式使用本答案前应替换为你实际用过并能展开细节的工具，例如 Claude Code。

### 53. 你平时怎样使用 AI 编程工具完成需求开发？

我通常分阶段使用：先让它读取 PRD、接口文档和相关代码，输出需求理解和风险点；我确认后再形成技术方案，经过团队评审再拆成小任务逐步实现。每一步我都会 review diff，并让它补充单测、异常路径和回归清单，最终仍经过代码评审、QA 和灰度发布。

关键点是 AI 负责加速分析和编码，人负责需求判断、架构取舍、代码验收和上线责任。

### 54. 让 AI 把技术方案写入飞书是怎样实现的？

公司内部提供了连接飞书文档的受控工具，Agent 按约定调用后创建或更新文档。我的使用流程是先让模型基于 PRD 和代码生成草稿，我人工校对后再写入飞书并发起评审。这里应说“使用内部工具完成写入”，不要把工具平台本身说成由我开发。

### 55. 你使用过哪些 MCP 工具？

如果内部工具确实基于 MCP，可以说使用过文档读取、飞书文档写入或代码仓库访问等工具，并说明一次完整调用的输入、权限和输出。如果无法确认内部协议，就应该回答：“我使用过这些 Agent 工具，但不能确认它们底层是否为标准 MCP；个人项目中的 Python Tool Registry 也不是 MCP。”

### 56. 如果要给 Agent 开发一个工具，你会选择 CLI 还是 MCP？

CLI 和 MCP 不是完全同一层的替代品。CLI 是可执行入口，适合本地一次性任务、脚本自动化和人或 Agent 直接调用；MCP 是面向 AI 客户端的标准协议，提供工具发现、结构化 Schema、统一调用和更清晰的权限边界。

如果只是给单个项目快速使用，我会先做核心库和 CLI；如果要让多个 Agent 客户端稳定复用，我会在同一核心逻辑上再提供 MCP Server。这样业务逻辑只有一份，入口按场景选择。

### 57. 你使用过哪些 Skill？有没有沉淀自己的 Skill？

我使用过需求文档整理、技术方案生成、代码评审、测试用例生成和 Git 操作等类型的 Skill。当前还没有把个人流程完整沉淀成可复用 Skill，这是一个明确不足。

如果要沉淀，我会选择高频且步骤稳定的流程，例如“读取 PRD -> 检索相关代码 -> 生成技术方案 -> 输出评审清单”，把步骤、边界和验收标准写入 `SKILL.md`，再配套脚本和模板，而不是只写一段提示词。

### 58. 除了实习和个人项目，你平时还会钻研哪些技术？

我目前重点补两条线：一条是 Java 后端基础，包括 JVM、并发、MySQL、Redis 和消息队列；另一条是 Agent 应用工程，包括模型 API、结构化输出、Tool 调用、MCP、工作流和评测。学习方式以“读官方文档或源码 + 做小实验 + 整理可复现结论”为主，而不是只看名词解释视频。
