## 三、本场面试暴露出的主要问题

1. **B+ 树复杂度回答错误。** B+ 树和平衡二叉搜索树的查找都属于对数复杂度，核心区别是 B+ 树扇出更大、树高更低，因此磁盘页 I/O 更少，不是现场所说的 `O(MN log MN)`。
2. **没有围绕完整 SQL 一次设计联合索引。** 一开始拆成多个独立索引，导致过滤、排序和 `LIMIT` 无法在同一棵 B+ 树上连续完成。
3. **覆盖索引与回表的判断不稳定。** InnoDB 二级索引叶子节点本来就包含主键；是否追加 `amount` 应依据覆盖收益、字段宽度、写放大和实际执行计划决定。
4. **没有识别深分页的本质。** `LIMIT offset, size` 需要扫描并丢弃前 `offset` 行，越往后越慢；全量任务应使用基于稳定唯一游标的 Keyset Pagination。
5. **大批量离线处理只想到分表和多线程。** 还应回答任务切片、检查点、租约、限流、RPC 幂等、条件更新、失败重试和对账。
6. **把 Redis 的线程模型与业务并发安全混在一起。** Redis 单条命令原子执行，不代表客户端的多条命令组成原子业务操作；Redis 6 的 I/O 线程也不等于多个线程并发修改同一个 Key。
7. **混淆 `SET NX`、Lua 和 Pipeline。** `SET NX` 用于原子抢占；Lua 用于把“校验锁所有者 + 删除”等多步逻辑原子化；Pipeline 只减少网络往返，不保证整批命令原子执行。
8. **项目机制理解不够深入。** 面试官最后明确指出：得到提示后需要及时调整思路，同时要继续深挖自己参与项目中“为什么这样设计、失败边界是什么、如何验证”。

### 7. MySQL 索引通常是什么结构？InnoDB 中应怎样设计索引

**建议时长：60～75 秒。**

先说结论：InnoDB 的常规索引主要使用 B+ 树。聚簇索引的叶子节点保存整行记录，二级索引的叶子节点保存二级索引列和主键值；通过二级索引拿到主键后，必要时再回到聚簇索引取完整行，这就是回表。

索引设计不能脱离 SQL。我通常按四步考虑：第一，看 `WHERE` 中的等值、范围条件；第二，看 `ORDER BY`、`GROUP BY` 能否复用索引顺序；第三，看返回列是否值得做覆盖；第四，结合选择性、更新频率和字段宽度控制索引数量。

最后用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 验证访问类型、扫描行数、是否回表、是否出现 `Using filesort`，而不是只凭规则猜索引。

### 8. 为什么数据库索引常用 B+ 树，而不是二叉搜索树、红黑树或 B 树

**建议时长：60 秒。**

核心原因是减少页 I/O。数据库按页读写，B+ 树的内部节点只保存键和子指针，一个页能放很多分支，扇出很大，所以千万级数据通常也只有少量层级。二叉树和红黑树每个节点只有两个分支，数据量大时树会很高，访问磁盘页的次数更多。

相比 B 树，B+ 树把完整记录集中在叶子层，内部节点能容纳更多键；所有查询路径长度更稳定，叶子节点还按键有序并相互连接，范围扫描和排序访问更自然。

因此 B+ 树的优势不是大 O 复杂度突然改变，而是更高扇出、更低树高和更好的范围访问能力。

### 9. B+ 树与平衡二叉搜索树的查找复杂度有什么区别

**建议时长：30～45 秒。**

两者从渐进复杂度看都是对数级。平衡二叉搜索树是 `O(log_2 N)`，扇出为 `m` 的 B+ 树树高大约是 `O(log_m N)`。

数据库更关心页 I/O，而不是只看比较次数。B+ 树的 `m` 很大，所以树高通常远小于二叉树；进入一个页以后再通过页内查找定位记录。因此不能回答成 `O(MN log MN)`，正确重点是两者都为对数复杂度，但 B+ 树所需的随机页访问更少。

### 10. 给定一个订单表和高频查询，这个表与查询的索引应怎样设计

**建议时长：60～90 秒。**

> 题面缺失，以下按对话推断：查询大致是按 `order_id`、`status` 等值过滤，按 `created_at` 排序，取最新若干条，并返回 `id`、`amount` 等字段。

我会先把完整 SQL、字段基数、返回行数和写入频率确认清楚。对于上述查询，基础联合索引可以设计为：

```sql
CREATE INDEX idx_order_status_created
ON orders (order_id, status, created_at DESC);
```

等值过滤列放前面，排序列紧随其后。这样数据库先定位到某个 `order_id + status` 的连续索引区间，再按 `created_at` 的索引顺序读取前几条，遇到 `LIMIT` 后可以尽早停止。

如果 `id` 是主键，InnoDB 二级索引叶子节点已经带有 `id`，一般不用重复追加。`amount` 是否加入索引要看覆盖收益和索引膨胀，不能只为避免一次回表就无条件加入。

### 11. 联合索引为什么通常先放等值过滤列？什么是最左前缀原则

**建议时长：45～60 秒。**

联合索引按列顺序进行字典序排列。例如索引是 `(order_id, status, created_at)`，会先按 `order_id` 排，再在相同 `order_id` 内按 `status` 排，最后在前两列都相同时按 `created_at` 排。

最左前缀原则是：查询从索引最左列开始，能够连续利用若干列。跳过首列直接查 `status`，通常无法有效定位这棵索引；遇到范围条件后，后续列通常不能再用于继续缩小扫描范围，但仍可能用于覆盖或部分排序。

本题的 `order_id` 和 `status` 是等值条件，所以先放这两列，再放排序列 `created_at`，能够形成一个内部有序的连续区间。

### 12. 查询要返回 `id` 和 `amount` 时，哪些列应放进联合索引？怎样权衡覆盖索引与索引体积

**建议时长：60 秒。**

先区分两个字段。若 `id` 是 InnoDB 主键，所有二级索引记录本来就包含主键值，因此通常不必为了返回 `id` 再显式追加一次。

`amount` 不在过滤和排序条件中。如果把它追加到索引尾部，例如 `(order_id, status, created_at DESC, amount)`，查询可能成为覆盖索引，减少回表；但 MySQL 没有独立的 `INCLUDE` 列语义，`amount` 会真实增大索引记录，降低页扇出，并增加写入、更新和缓存成本。

因此我的判断标准是：查询是否高频、返回行数是否小、`amount` 是否短且少更新、回表是否真的成为瓶颈。最终通过执行计划和压测决定，而不是看到返回列就全部塞进索引。

### 13. InnoDB 的主键索引和非主键索引有什么区别

**建议时长：45～60 秒。**

InnoDB 的主键索引是聚簇索引，叶子节点保存整行记录，一张表只有一个聚簇组织顺序。二级索引是独立的 B+ 树，叶子节点保存二级索引键和主键值。

通过二级索引查询时，如果所需列都能从二级索引拿到，就是覆盖索引；否则先得到主键，再访问聚簇索引取行，称为回表。

如果表没有显式主键，InnoDB 会尝试选择非空唯一索引；仍没有时会生成隐藏行标识。工程上应主动选择短、稳定、递增趋势合理的主键，避免把宽字符串放进所有二级索引叶子节点。

### 14. 查询包含 `ORDER BY created_at` 时，联合索引应怎样设计？一定要写 `DESC` 吗

**建议时长：45～60 秒。**

如果前面的 `order_id`、`status` 都是等值条件，就把 `created_at` 放在它们之后，例如 `(order_id, status, created_at DESC)`。数据库定位到等值前缀后，可以直接按创建时间顺序扫描并在满足 `LIMIT` 后停止。

对于只有一个排序列且方向统一的场景，B+ 树可以反向扫描，所以升序索引也常能支持 `ORDER BY created_at DESC`。MySQL 8 支持真正的降序索引，显式写 `DESC` 能表达意图；当多个排序列方向混合时，索引方向是否匹配更重要。

还要给排序增加稳定的唯一键，例如 `ORDER BY created_at DESC, id DESC`，避免相同时间的数据在分页时漂移。

### 15. 建立两个独立索引后，底层是一棵 B+ 树还是两棵 B+ 树

**建议时长：20～30 秒。**

是两棵独立的 B+ 树。每定义一个普通 B+ 树索引，InnoDB 都会维护一套独立的键顺序和叶子页。再加上聚簇索引，这张表实际上可能同时维护多棵树。

因此索引不是越多越好。每增加一个索引，查询可能多一种访问路径，但插入、删除和更新都要同步维护这棵树，也会增加磁盘和 Buffer Pool 占用。

### 16. 两个独立索引怎样参与查询？为什么它们通常不能同时高效完成过滤和排序

**建议时长：45～60 秒。**

优化器通常选择成本最低的一棵索引作为主要访问路径，再对剩余条件过滤或排序。MySQL 在部分场景可以使用 Index Merge，把多个索引得到的主键集合求交或求并，但这不等于把两棵树拼成一棵有联合顺序的树。

例如一棵树按 `(order_id, status)` 排，另一棵树按 `created_at` 排。前者能快速过滤，却不能保证结果按创建时间排列；后者有时间顺序，却可能需要扫描大量不属于该订单和状态的记录。求交之后原有顺序也未必能直接用于 `ORDER BY`。

所以本题更适合建立 `(order_id, status, created_at)` 联合索引，让过滤和排序在同一棵树的同一个连续区间内完成。

### 17. 对于“按订单和状态过滤、按创建时间取最新若干条”的查询，最终联合索引和查询过程是什么

**建议时长：60 秒。**

可以把查询和索引设计成：

```sql
SELECT id, amount, created_at
FROM orders
WHERE order_id = ?
  AND status = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;

CREATE INDEX idx_order_status_created_id
ON orders (order_id, status, created_at DESC, id DESC);
```

查询时，先沿 B+ 树定位 `order_id + status` 的等值前缀，再从该区间中 `created_at + id` 最大的位置开始顺序读取。因为叶子记录已经按所需顺序排列，读取 20 条后即可停止，不需要先取出一万条再额外排序。

如果 `id` 是主键，它在二级索引中本就存在；是否仍显式把它作为排序尾列，要结合 MySQL 版本、确定性排序和执行计划判断。`amount` 不在索引时只需对最终少量结果回表，通常是可接受的。

### 18. 使用 `LIMIT offset, size` 扫描百万或上亿行数据有什么性能问题

**建议时长：45～60 秒。**

`LIMIT 1000000, 20` 不是直接跳到第一百万行。数据库通常仍要沿索引扫描前一百万零二十条，再把前一百万条丢弃，所以单页成本是 `O(offset + size)`，越往后越慢。

如果从第一页一直扫到最后一页，重复跳过的数据会越来越多，总工作量可能接近二次增长。若查询还需要回表或排序，成本会更高。

此外，分页过程中数据持续插入、删除或状态变化，还可能造成重复处理和漏处理。因此面向用户的翻页可以限制深度；面向全量任务应改用 Keyset Pagination，并配合快照边界和检查点。

### 19. 怎样使用游标分页优化深分页？游标为什么要包含唯一键

**建议时长：60 秒。**

游标分页不记录“第几页”，而是记录上一批最后一条记录的排序键。按创建时间倒序分页时，可以写成：

```sql
SELECT id, amount, created_at
FROM orders
WHERE order_id = ?
  AND status = ?
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

对应索引是 `(order_id, status, created_at DESC, id DESC)`。下一页从上次的 `(last_created_at, last_id)` 之后继续，不再扫描并丢弃前面所有行。

游标必须包含唯一键，因为 `created_at` 可能重复。只记录时间会让同一时间点的记录出现重复或遗漏；加入 `id` 后形成稳定全序。离线全量任务还应记录快照上界，明确运行期间新数据是否进入本轮处理。

### 20. 如果一个订单有一亿条子订单，需要逐批调用 RPC 并更新状态，怎样设计可靠的离线处理任务

**建议时长：90 秒。**

我会把它设计成可恢复的批处理，而不是一个进程从头跑到尾。

第一，建立 `job` 和分片任务记录，保存 `run_id`、订单范围、游标、状态、重试次数和租约。可以按主键范围切片，让多个 Worker 并行处理，但并发度由数据库和下游 RPC 容量决定。

第二，每批通过稳定游标读取，例如 `WHERE order_id=? AND status=0 AND id>? AND id<=snapshot_max ORDER BY id LIMIT ?`，并建立匹配的 `(order_id, status, id)` 索引。批次大小通过压测选择，不能固定认为 20 或 1000 一定最好。

第三，为每个下游调用携带业务幂等键，例如 `sub_order_id + target_status + run_id`。RPC 成功后使用条件更新：

```sql
UPDATE sub_order
SET status = 1
WHERE id = ? AND status = 0;
```

影响行数为 1 才表示本次完成了合法状态迁移。失败使用指数退避和有限重试，超过阈值进入失败表或死信队列，任务可从检查点恢复。

最后要有 QPS 限制、超时、熔断、监控、暂停和回滚开关，并在结束后按状态和数量对账。分表只能提升并行能力，不能替代幂等、状态机和恢复机制。

### 21. Redis 有没有类似数据库二级索引的能力

**建议时长：45 秒。**

Redis 核心不是关系型数据库，没有自动为任意字段维护通用二级索引，也不支持像 MySQL 那样自由组合 `WHERE` 条件。

但可以根据访问模式手工建索引：用 Key 做唯一定位，用 Set 做倒排集合，用 ZSet 按分数排序和范围查询，用 Hash 保存对象字段。例如用 `user:{id}` 存对象，再用 `city:beijing` 的 Set 保存用户 ID。

这种索引需要应用自己保证与主数据的一致性。如果确实需要全文检索和复杂字段查询，可以在部署允许时使用 RediSearch 等模块；否则应选择 MySQL、Elasticsearch 等更适合的存储。

### 22. Redis 和 MySQL 各有什么优缺点？什么场景分别选择它们

**建议时长：60～75 秒。**

MySQL 适合作为结构化业务数据的事实源。它支持表关系、丰富查询、约束、事务、持久化和恢复，适合订单、账户、配置等需要强一致和可审计的数据；代价是访问路径更重，面对热点高并发时要注意索引、锁和容量。

Redis 主要把数据放在内存中，提供 String、Hash、List、Set、ZSet 等高效结构，适合缓存、计数、排行榜、限流、会话和短期协调。它延迟低，但内存成本高，查询能力有限，淘汰、过期、故障切换和持久化配置都可能影响数据边界。

工程上通常不是二选一：MySQL 保存最终事实，Redis 承担热点读和临时状态。此时还要明确缓存更新、失效、重建和一致性策略。

### 23. MVCC 是做什么的？它怎样服务于事务隔离

**建议时长：60 秒。**

MVCC 是多版本并发控制，主要让读操作在很多场景下不必阻塞写操作。InnoDB 记录事务版本信息，旧版本通过 Undo Log 串联；事务读取时根据 Read View 判断哪个版本对自己可见。

在 `READ COMMITTED` 下，通常每条一致性读语句生成新的 Read View；在 `REPEATABLE READ` 下，同一事务中的一致性读通常复用快照，所以多次读取能看到稳定版本。

MVCC 主要服务于一致性非锁定读，不代表所有并发问题都被消除。当前读、更新和删除仍要使用锁；范围更新还涉及 Next-Key Lock。事务的原子性、持久性也不只是由 MVCC 提供。

### 24. Redis 有事务吗？它与 MySQL 事务有什么区别

**建议时长：45～60 秒。**

Redis 有 `MULTI/EXEC` 事务，也可以用 `WATCH` 做乐观并发控制。`MULTI` 之后的命令先入队，`EXEC` 时连续执行，其他客户端命令不会插入这批命令中间。

但它和 MySQL 事务不同：Redis 通常不会像关系型数据库那样在运行时错误后自动回滚已经执行的命令，也没有完整的多行约束和隔离级别语义。`WATCH` 发现被监视 Key 变化时会让 `EXEC` 失败，由客户端重试。

如果需要“读取、判断、修改”在 Redis 内原子完成，Lua 脚本或 Redis Functions 往往更直接。但它们也只能保证单个 Redis 执行边界内的原子性，不能自动覆盖 MySQL、MQ 和外部 RPC。

### 25. Redis 命令大体串行执行，为什么业务上仍然会出现并发问题

**建议时长：45～60 秒。**

Redis 单条命令是原子的，服务端内部数据结构不会被两条普通命令同时改坏。但一个业务动作往往由多条命令组成，命令之间可能穿插其他客户端操作。

例如客户端 A 执行 `GET counter` 得到 10，客户端 B 也得到 10；A `SET 11` 后，B 再 `SET 11`，一次增加被覆盖。问题不是 Redis 的 Hash 表线程不安全，而是“读 + 计算 + 写”没有形成一个原子业务操作。

解决方式是优先使用原子命令，如 `INCR`、`SET NX`；更复杂的条件读改写用 Lua、事务或重新设计数据模型。跨系统正确性还要依靠数据库约束、幂等和状态机。

### 26. Redis 6 引入 I/O 多线程后，是否变成多个线程并发修改同一个 Key

**建议时长：30～45 秒。**

不是。Redis 6 的 I/O 线程主要帮助处理网络读写和协议解析，常规命令执行仍大体由主线程串行完成，所以不能据此解释为多个线程同时修改同一个 Key。

Redis 还可能有后台持久化、释放内存和模块线程，但对于面试讨论的普通 Key 命令，核心结论仍是单条命令原子、命令序列可能交错。业务并发问题来自多客户端的复合操作，而不是 Redis 6 把普通写命令改成了共享内存式并行写。

### 27. 请举一个 Redis 多步骤操作并发不安全的具体例子

**建议时长：45 秒。**

以黑名单到期任务为例，两个 Worker 同时读取到同一个待解封用户。如果流程是“先查是否处理过 -> 调用解封 RPC -> 写入已处理标记”，两个 Worker 都可能在标记写入前通过检查，于是下游 RPC、日志或通知被执行两次。

可以用原子领取或 `SET task_lock:{user}:{project} token NX PX ttl` 减少重复执行，但最终仍要给下游请求幂等键，并在数据库中用状态和版本做条件更新，防止旧的解封任务覆盖新的封禁状态。

这个例子体现的是业务流程的并发，而不是 Redis 单条命令把数据结构写坏。

### 28. 为什么不能先 `GET` 判断锁不存在，再执行 `SET`？`SET NX` 解决了什么问题

**建议时长：30～45 秒。**

`GET` 和 `SET` 是两条独立命令。客户端 A、B 可能都先读取到锁不存在，然后都执行 `SET`，两边都以为自己获得了锁，这就是典型的检查与执行竞态。

`SET key token NX` 把“不存在才写入”合成一条 Redis 原子命令，同一时刻只有一个客户端能得到成功结果。实际使用还应在同一条命令中加入过期时间，例如 `SET key token NX PX 30000`，避免客户端崩溃后形成永久死锁。

### 29. 一个基本正确的 Redis 分布式锁应怎样获取

**建议时长：45～60 秒。**

获取锁使用一条命令：

```text
SET lock:{business-key} <unique-token> NX PX 30000
```

`business-key` 决定锁粒度，应该只互斥真正冲突的业务对象；`unique-token` 标识锁的所有者，可以使用足够随机的请求 ID；`NX` 保证不存在才写；`PX` 设置租期，防止持锁实例崩溃后永久占锁。只有返回 `OK` 才表示获取成功。

不建议拆成 `SETNX` 再 `EXPIRE`，因为两条命令之间进程可能崩溃。客户端还要设置获取超时、有限重试和随机退避，不能无限自旋。

锁只是减少并发执行，业务最终正确性仍要由幂等键、条件更新或唯一约束保证。

### 30. 已经使用 `SET NX`，为什么释放锁还需要 Lua？为什么不能直接 `DEL`

**建议时长：60 秒。**

`SET NX` 只保证抢锁原子，释放锁还必须确认“当前锁仍属于我”。假设实例 A 获得锁后执行过久，锁先过期；实例 B 随后获得同名锁。此时 A 如果直接 `DEL`，就会误删 B 的锁。

因此释放时要先比较 token，再删除，而且两步必须原子完成：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

如果在客户端先 `GET` 再 `DEL`，两条命令之间锁仍可能过期并被别人重新获取。Lua 脚本在 Redis 内连续执行，避免这个检查删除竞态。

### 31. 如果业务没有执行完锁就过期了，怎样处理

**建议时长：60～75 秒。**

先承认边界：仅靠 TTL 无法保证长任务期间永远只有一个执行者。旧持有者卡顿时锁可能过期，新持有者开始执行，随后旧持有者又恢复，二者会短暂并行。

可以从三层处理：第一，根据正常耗时和尾延迟设置合理租期，必要时由确认仍持有锁的客户端做有限续期；第二，为每次获锁分配递增的 fencing token，下游只接受比当前版本更新的操作，拒绝迟到的旧持有者；第三，业务落库使用幂等键、唯一约束和版本条件更新作为最终防线。

看门狗续期只能降低提前过期概率，不能解决网络分区、长暂停和所有故障。若下游不支持 fencing，就更不能把 Redis 锁当成唯一正确性保证。

### 32. Pipeline 和 Lua 分别解决什么问题？Pipeline 中的一批命令是原子的吗

**建议时长：60 秒。**

Pipeline 解决的是网络性能问题。客户端连续发送多条命令，再批量读取响应，减少客户端与 Redis 之间的 RTT。它不保证这一批命令作为整体原子执行，其他客户端命令仍可能穿插；批次过大还会占用客户端和服务端缓冲区。

Lua 解决的是 Redis 内部多步逻辑的原子性。脚本执行期间不会插入其他普通命令，适合“读取 -> 判断 -> 修改”，例如校验锁 token 后删除。

所以二者可以同时出现但职责不同：批量给多个业务 Key 执行独立的 `SET NX` 时用 Pipeline 降低 RTT；释放每把锁时用 Lua 保证校验和删除原子。Pipeline 整批仍不是一个全有或全无的事务。

### 33. Redis 内存达到上限时有哪些淘汰策略

**建议时长：45～60 秒。**

Redis 达到 `maxmemory` 后，常见策略可以按作用范围分为两组：

- `noeviction`：不淘汰，写命令返回错误；
- `allkeys-lru`、`allkeys-lfu`、`allkeys-random`：从所有 Key 中按 LRU、LFU 或随机方式淘汰；
- `volatile-lru`、`volatile-lfu`、`volatile-random`：只从设置了过期时间的 Key 中淘汰；
- `volatile-ttl`：优先淘汰剩余 TTL 更短的 Key。

Redis 的 LRU、LFU 通常是采样近似实现，不是维护全量精确链表。策略选择取决于 Redis 是纯缓存还是混合存储；若同一实例里有不能丢的数据，不能只靠选择一个淘汰策略掩盖数据分层问题。

### 34. 除了 LRU，还了解哪些缓存替换算法

**建议时长：30～45 秒。**

常见的还有 FIFO、LFU 和 Random。FIFO 按进入缓存的先后淘汰，实现简单，但不考虑访问热度；LFU 淘汰访问频率最低的数据，更适合长期热点，但要处理频率老化，否则历史热点可能长期占据缓存；Random 成本低，但命中率不可预测。

工程中还有 2Q、ARC、TinyLFU 等方案，用来同时考虑最近访问和访问频率，减少一次性大扫描造成的缓存污染。选择算法要结合访问分布、元数据成本和实现复杂度，不能只背名称。

### 35. LRU 的核心原理和数据结构是什么？`get`、`put` 的复杂度是多少

**建议时长：45～60 秒。**

LRU 淘汰最长时间没有被访问的数据。要让 `get` 和 `put` 都达到 `O(1)`，通常组合使用 HashMap 和双向链表。

HashMap 从 Key 直接找到节点；双向链表维护最近使用顺序。链表头表示最近访问，链表尾表示最久未访问。`get` 命中后把节点移到头部；`put` 已存在时更新值并移到头部；插入新节点后若超过容量，就删除尾部节点并从 Map 移除。

双向链表能在已知节点时 `O(1)` 删除；若只有单链表，还要寻找前驱节点。实现时要特别处理容量为 0、更新已有 Key、删除尾节点和 Map/链表同步。

### 36. 请使用 Java 实现支持构造、`get` 和 `put` 的 LRU Cache

**建议时长：先用 30 秒讲结构，再用 8～12 分钟编码和自测。**

> 题面缺失，以下按常见接口还原。`get` 未命中返回 `-1`，`put` 插入或更新键值。

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    private static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> cache = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = Math.max(0, capacity);
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = cache.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = cache.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }

        if (capacity == 0) {
            return;
        }

        Node added = new Node(key, value);
        cache.put(key, added);
        addAfterHead(added);

        if (cache.size() > capacity) {
            Node removed = removeTail();
            cache.remove(removed.key);
        }
    }

    private void moveToHead(Node node) {
        removeNode(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void removeNode(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private Node removeTail() {
        Node node = tail.prev;
        removeNode(node);
        return node;
    }
}
```

手写完成后至少主动验证四个用例：普通插入和命中、超容量淘汰最旧 Key、更新已有 Key 后该 Key 变成最近使用、`capacity = 0` 时不保存数据。所有 Map 和链表修改都集中在几个小函数中，能减少现场指针错误。

### 37. 该抖音电商团队主要负责什么业务

**建议时长：20～30 秒。**

根据面试官开场介绍，团队主要负责抖音电商商家侧的应用和平台能力，为商家提供 AI 相关运营工具、经营工具和金融工具。岗位同时涉及较多后端工程开发和 AI 应用侧建设。

这个信息只代表本场面试官对所在团队的口头介绍。后续如果进入下一轮，可以继续确认具体业务域、核心服务、语言栈、AI 与传统后端工作的比例，以及新人最先承担的模块。

### 38. 怎样理解面试官对本场表现的建议，后续应怎样改进

**建议时长：45～60 秒。**

面试官的反馈有两层。第一，在得到明确提示后，不要继续维护原来的错误假设，要复述提示、更新模型，再给出新的结论。第二，对自己参与过的项目还需要继续深挖，不能只说用了 Redis、Lua、Pipeline 或某个平台，而要解释为什么这样设计、各组件分别解决什么问题、失效边界在哪里。

后续我会按统一框架准备每个项目：业务问题是什么 -> 数据和调用链怎样流转 -> 我负责哪一段 -> 为什么选这个方案 -> 并发、超时和故障时会怎样 -> 用什么指标、日志和测试验证 -> 出问题怎样降级或回滚。

做现场题时先确认题面和不变量，再讲数据结构与复杂度；得到提示后先停下来重新组织，而不是边写边沿着旧思路补丁式修改。本场最需要补强的是联合索引、深分页、Redis 原子性和分布式锁的边界。
