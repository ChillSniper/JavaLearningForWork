## 二、本场复盘

这场 AI 面试名义上有 9 个主问题，但每题都会继续追问，实际可以拆成 25 个问题。考察重点不是冷门知识，而是能否在短时间内做到三件事：先界定问题，再给出结构化结论，最后主动补充适用边界。

表现较好的地方：

1. 数据结构题能想到“哈希表 + 双向链表”，并能继续讨论冲突、内存和并发问题。
2. 数据库题能把条件更新、悲观锁、乐观锁和高并发削峰联系起来。
3. 上下文切换题能覆盖寄存器状态、调度成本、Cache/TLB 局部性和 CPU 亲和性。
4. TCP 题知道三次握手的报文顺序，也能解释为什么不需要四次。
5. 项目题有实时约束、算法选择、实验验证和后续优化意识，不只是介绍功能。

主要问题：

1. **情绪化自言自语被完整录入。** 这是本场最严重的问题。不会答时应说“我先明确一下问题边界”或“我从原理和工程取舍两方面回答”，不能辱骂题目或系统。
2. **部分回答没有先校准题意。** “优化链表随机查询”必须先确认是按 key 查节点，还是按下标随机访问；两者的数据结构不同。
3. **数据库锁分类混杂。** 乐观锁通常是基于版本号的并发控制方案，不等于数据库中的一种实体锁；回答时应与共享锁、排他锁、记录锁等分开。
4. **TCP 解释略显绝对。** “防止历史 SYN 建立无效连接”可以作为辅助例子，但核心仍是交换并确认双方初始序列号，并让双方确认双向收发能力。
5. **项目表述存在证据冲突。** 当前转写提到 “MCTS + Alpha-Beta + bitboard”，但仓库既有记录能够确认的是 MCTS/启发式框架，以及后续 CNN 自博弈方案。没有代码或实验记录前，不应把前一套方案说成已实现成果。
6. **游戏经历应保持真实一致。** 当前转写使用《王者荣耀》，但已有个人面试记录明确写的是长期玩《炉石传说》。正式回答应选择自己真正熟悉、能经得住机制追问的游戏。
7. **结果描述过于空泛。** “效果很好、明显提升”没有口径。没有可复现实验数据时，应只说明约束、验证方法和可确认结果，不临时编胜率、搜索节点数或延迟数据。

## 四、逐题参考回答

### 1. 请做一个简单的自我介绍

**建议时长：60～90 秒。**

面试官您好，我是一名 2027 届本科生，求职方向是服务端开发。我有两段后端实习经历：第一段在途游游戏中台参与客服系统、玩家召回和支付风控黑名单相关需求；第二段在字节国际支付风控合规团队参与运营审核平台、客诉自动化链路和处罚查询相关需求。

其中我投入较多的是风控客诉自动化。原先部分申诉案件主要由人工审核，我们把案件字段、历史记录和内部 Agent 的结构化结果汇聚起来，再通过可配置规则完成自动判定，无法确定的案件继续转人工。我主要负责后端接入、规则与动作编排、异常兜底和联调，不负责底层模型训练。

这两段经历让我对 MySQL、Redis、消息消费、分布式一致性和跨团队协作有了更具体的认识。我希望继续做服务端开发，在复杂业务中提升工程设计和稳定性能力。

### 2. 怎样优化链表查询，同时保留高效插入、删除

**建议时长：60 秒。**

我会先确认“随机查询”的含义。如果是根据唯一 key 查找节点，可以使用 `HashMap<K, Node>` 加双向链表：哈希表负责把 key 映射到节点，平均查询复杂度是 O(1)；双向链表负责维护顺序，拿到节点后插入和删除也是 O(1)。LRU Cache 就是典型应用。

但如果题目要求按第 k 个位置访问，哈希表加链表并不能自然解决，因为中间插入或删除会让大量下标映射失效。这时可以根据需求选择跳表、分块链表，或者在读多写少时改用动态数组。核心是先确认查询维度，再选数据结构。

### 3. 怎样处理哈希冲突并避免性能恶化

**建议时长：45～60 秒。**

哈希冲突无法完全避免，常见处理方式有拉链法和开放寻址法。以 Java `HashMap` 为例，它主要使用拉链法；当负载因子达到阈值时会扩容并重新分布元素，减少单个桶中的节点数量。

Java 8 中，如果某个桶的链表长度达到树化阈值，并且数组容量也达到要求，会把链表转换成红黑树，将该桶内查询从 O(n) 改善到 O(log n)；如果数组容量还小，通常优先扩容。除此之外，key 的 `hashCode` 和 `equals` 必须正确实现，并避免使用分布性很差或可被恶意构造的 key。

### 4. 这种设计不适合哪些场景

**建议时长：45～60 秒。**

第一，数据量很大但内存敏感时不适合，因为哈希桶、节点对象和双向指针都会增加空间开销。第二，需要范围查询、按序遍历或找前驱后继时不适合，因为哈希表不保序，跳表或平衡树更自然。第三，如果只需要按 key 查询而不需要维护顺序，链表是多余成本。

另外，高并发 LRU 不能直接用普通 `HashMap + 双向链表`。`get` 命中后通常还要把节点移动到链表头部，所以它不是纯读操作；如果没有锁、分段或成熟并发缓存实现，多线程会破坏链表结构。

### 5. 怎样理解数据库锁机制

**建议时长：75～90 秒。**

数据库锁的目标是在并发读写时保护数据一致性，并帮助数据库实现事务隔离。可以从几个维度理解：按兼容性分为共享锁和排他锁；按粒度分为表锁和行锁；InnoDB 在索引记录上还有记录锁、间隙锁和临键锁，用来处理当前读和范围更新中的并发问题。表级意向锁用于快速判断表内是否存在行锁意图。

还要把锁和 MVCC 区分开。普通快照读通常通过 MVCC 读取一致性版本，不一定加行锁；`SELECT ... FOR UPDATE`、更新和删除属于当前读，会涉及锁。乐观锁则通常通过业务版本号或条件更新检测冲突，它是一种并发控制思路，不等于 InnoDB 内部的一种实体锁。

### 6. 普通库存扣减怎样选择并发控制方案

**建议时长：60 秒。**

对于逻辑简单的库存扣减，我优先使用单条条件更新，把“检查库存”和“扣减”合并成数据库原子操作：

```sql
UPDATE sku_stock
SET stock = stock - :quantity
WHERE sku_id = :skuId
  AND stock >= :quantity;
```

根据受影响行数判断是否成功，这样可以避免先查再改产生竞态。如果扣减前必须读取多行并执行复杂校验，可以在事务中使用 `SELECT ... FOR UPDATE`；冲突较低且允许重试时，也可以使用版本号乐观锁。无论哪种方案，还要使用订单号或扣减流水号保证业务幂等。

### 7. 高并发热点库存怎样优化

**建议时长：75 秒。**

只依赖数据库行锁时，大量请求会竞争同一热点行，连接和事务在数据库中排队，吞吐和尾延迟都会恶化。可以先在入口做限流和资格校验，再用 Redis Lua 做原子预扣或令牌发放，把成功请求写入消息队列，后端按可控速度落库。

但 Redis 不能直接替代数据库事实。数据库仍保存最终订单和库存状态，消费端必须幂等；Redis 预扣成功但下单失败时需要补偿，消息失败要有重试、死信和对账。库存分桶也可以降低单热点竞争，但会增加桶间汇总和补偿复杂度，应在确有容量压力时使用。

### 8. 乐观锁大量失败时怎样处理

**建议时长：45～60 秒。**

乐观锁大量失败说明场景已经从低冲突变成高冲突。首先应限制重试次数，使用指数退避和随机抖动，避免所有请求立即重试形成重试风暴；同时监控冲突率、成功率和重试次数。

如果冲突持续很高，应调整并发模型，例如改用悲观锁、按业务 key 串行化、消息队列排队，或者对热点资源分片。不能无限重试，也不能把版本冲突当成系统异常直接吞掉。

### 9. 什么是上下文切换，进程和线程切换有何区别

**建议时长：60～75 秒。**

上下文切换是 CPU 从一个可执行任务切换到另一个任务时，保存当前任务的程序计数器、栈指针和通用寄存器等运行状态，再恢复下一个任务状态的过程。它还会带来调度器开销，并可能降低 CPU Cache 和 TLB 的局部性，所以切换过多会影响吞吐和尾延迟。

同一进程内的线程共享虚拟地址空间，线程切换通常不需要切换完整地址空间；不同进程拥有独立地址空间，往往还涉及页表和地址转换相关状态，因此进程切换通常更重。但实际成本还取决于内核路径、CPU 架构和工作集，不能简单认为一次切换会清空所有缓存。

### 10. 怎样减少不必要的上下文切换

**建议时长：60 秒。**

我会先用监控或 profiling 判断切换来自线程过多、锁竞争还是阻塞 I/O，再针对原因优化。CPU 密集型任务的工作线程通常控制在核心数附近，使用线程池避免频繁创建和销毁线程；大量网络连接可以使用 `epoll`、Netty 等 I/O 多路复用和事件驱动模型，用少量 EventLoop 管理连接。

还可以缩小锁的临界区、减少共享状态、批量处理 I/O 或消息，降低频繁阻塞和唤醒。目标不是把上下文切换降到零，而是减少没有业务价值的调度和竞争。

### 11. CPU 绑定能否减少上下文切换，有什么副作用

**建议时长：45～60 秒。**

CPU 亲和性更直接减少的是线程在不同核心之间迁移，不保证上下文切换次数一定下降。它的主要收益是保持 CPU Cache 和 TLB 局部性，在低延迟、固定工作线程或 NUMA 场景中可能有效。

副作用是限制操作系统动态负载均衡。绑定不合理时会出现某些核心满载、其他核心空闲；多个繁忙线程绑到同一核心仍会频繁切换；还要考虑超线程和 NUMA 内存位置。因此应基于指标验证，不能把绑核当作通用优化。

### 12. TCP 三次握手为什么不是两次

**建议时长：60～75 秒。**

第一次，客户端发送 `SYN`，携带初始序列号 `x`；第二次，服务端返回 `SYN + ACK`，自己的初始序列号是 `y`，并确认 `x + 1`；第三次，客户端再发送 `ACK`，确认 `y + 1`。之后双方进入已建立状态。

三次握手的核心是交换并确认双方初始序列号，同时确认双向收发路径可用。只有两次时，服务端虽然收到了客户端的 SYN，也向客户端发出了自己的 SYN，但还不知道客户端是否已经收到服务端的初始序列号。第三次 ACK 补上了这个确认，因此三次是完成双方序列号同步所需的最小交互。

### 13. 历史 SYN 为什么不会直接建立有效连接

**建议时长：45 秒。**

假设一个旧 SYN 在网络中延迟很久后到达服务端，服务端可以回复 `SYN + ACK`，但此时客户端没有对应的连接状态，通常不会返回能够完成本次握手的有效 ACK，或者会返回 RST。服务端会停留在 `SYN-RECEIVED`，重传若干次后超时释放半连接，不会直接进入 `ESTABLISHED`。

这个例子说明第三次确认能避免服务端仅凭一个旧请求就认为连接已经完全建立，但它只是辅助解释。三次握手更根本的目的仍是双向确认初始序列号和通信能力。

### 14. 为什么不使用四次握手

**建议时长：45 秒。**

理论上可以拆成四步：客户端发 SYN，服务端单独回 ACK，服务端再发 SYN，客户端再回 ACK。但建立连接时，服务端对客户端 SYN 的确认和服务端自己的 SYN 可以合并在同一个 `SYN + ACK` 报文中，所以三次已经完成全部必要信息交换。

四次也能建立连接，只是多一次报文和一个 RTT 内的额外交互，没有必要。TCP 挥手常见四次，是因为一端确认收到 FIN 时，自己的发送方向可能还不能立即关闭，ACK 和 FIN 不一定能合并。

### 15. 介绍有实时约束的计算机博弈项目

**建议时长：75～90 秒。**

我参加过一个计算机博弈项目，比赛平台是北京大学 Botzone，项目对象是 9×9 的 NoGo，也就是不围棋。它和围棋相似，但不允许提子，也不能走自杀棋。程序需要根据当前棋盘状态，在平台给定的单步时间预算内生成合法且尽可能高质量的落子。

初赛阶段，我主要完成了蒙特卡洛树搜索和启发式策略的核心框架，队友在此基础上参与规则判断、参数调整和测试。后续阶段团队又尝试过基于 Python 的简易 CNN，并通过自博弈生成训练数据。这个项目让我真正处理了规则正确性、搜索质量、时间限制和实验可复现性之间的取舍。

> 事实边界：当前材料能够支持 `Botzone + NoGo + MCTS/启发式 + 后续 CNN 自博弈`。转写中的 `Alpha-Beta 残局搜索、bitboard、Zobrist/置换表` 只有在能用代码或实验记录证明时再讲。每步时间上限和奖项名称也应按比赛规则、证书原文确认。

### 16. 这个项目最难的地方是什么

**建议时长：60～75 秒。**

最难的不是单独实现某个搜索算法，而是在固定时间预算下同时保证规则正确、搜索稳定和落子质量。底层状态复制、合法性判断或随机模拟只要慢一点，单位时间内的搜索次数就会下降，最终表现出来的可能不是确定性报错，而是整体胜率波动。

我的处理方式是先用小棋盘局面和边界用例验证规则，再固定随机种子做策略对照，最后通过 profiling 找到状态更新、合法性判断和搜索中的热点。这样可以把“效果变差”拆成可复现、可定位的工程问题，而不是只靠不断调参。

### 17. 固定时间预算下怎样做技术选型

**建议时长：60 秒。**

技术选型不能只比较理论上谁更强，而要看固定时间内能产生多高质量的决策。NoGo 的状态空间和分支较大，直接做很深的穷举搜索成本高；MCTS 可以通过选择、扩展、模拟和回传，把计算集中到更有希望的分支，再结合领域启发式提高有限预算下的采样效率。

工程上还要控制状态表示、合法性检查和内存分配成本。只有在实际代码确实实现并验证后，才能继续讲 bitboard、置换表或残局 Alpha-Beta，不能把“可以优化”说成“已经实现”。

### 18. 是否对比过方案，最终效果怎样

**建议时长：45～60 秒。**

我会把比较条件固定下来：相同时间预算、相同对手集合、固定随机种子或足够多的对局，再看胜率、超时率和单位时间搜索次数。这样才能判断收益来自算法本身，还是来自随机波动。

现有记录可以确认团队最终在全国性计算机博弈比赛中获得一等奖，但当前材料没有保存可信的节点数或胜率对比，所以面试中我只会说明方案在时间限制内稳定完成对局，并支撑了最终比赛结果，不会临时编“提升百分之多少”。正式面试前应按证书确认比赛全称、年份、奖项和获奖队伍比例。

### 19. 项目有哪些经验、不足和后续优化方向

**建议时长：60 秒。**

第一，先用小规模用例保证规则正确，再谈性能和策略。第二，实时系统不能只看算法复杂度，还要看固定时间内最终产出的结果质量。第三，只要算法包含随机性，就必须固定随机种子、对手和时间预算，建立可复现实验。

不足是 MCTS 的模拟策略和评估比较依赖启发式与参数，重复状态也会浪费计算。后续可以在真实实现基础上增加状态缓存或置换表、改进策略网络、做更系统的自博弈和消融实验。但这些属于优化方向，未落地前不能说成既有成果。

### 20. 分享最近学习的新技术：Redis

**建议时长：75 秒。**

我最近比较系统地复习和验证了 Redis。学习动机来自真实后端场景：热点数据读取、排行榜、延迟任务和多实例并发控制，仅知道 `GET/SET` 不足以设计可靠方案。

我的学习分三层。第一层读官方文档，建立数据结构、持久化、复制和 Cluster 的整体认识；第二层针对实际问题深入命令语义和失效边界；第三层通过本地最小示例和实习场景验证，例如用 ZSet 按时间组织待处理任务，用 Pipeline 降低批量请求 RTT，以及用唯一 token 配合 Lua 校验后释放分布式锁。

最终效果不是“学会了所有 Redis 原理”，而是形成了从业务问题、命令语义到失败场景的分析方法，也更清楚 TTL、分布式锁和缓存一致性方案各自不能保证什么。

### 21. 文档没有明确说明时怎样确认真实行为

**建议时长：45～60 秒。**

我会先记录版本、配置和运行环境，再构造最小可复现样例，通过控制变量确认问题边界。然后结合日志、性能指标、网络请求或源码提出假设并逐个验证，而不是直接依赖搜索结果。

如果问题涉及并发或故障，我会主动加入超时、重试、进程重启和网络异常等条件。最后把实验结论放回真实业务场景复核，并记录适用版本和限制。这样既能解决当前问题，也能沉淀可复用的排查过程。

### 22. 分享一次团队合作经历

**建议时长：75～90 秒。**

我印象较深的是字节国际支付风控客诉自动化项目。它不是我一个人独立完成的：产品和运营负责案件流程与审核口径，算法团队负责内部 Agent 能力，相关平台提供数据和基础设施；我负责后端字段汇聚、内部服务调用、规则与动作编排、异常兜底和联调。

团队没有简单按页面切任务，而是先把完整链路拆成输入事实、自动判断、处理动作和人工兜底，再明确接口合同与负责人。我的工作除了完成后端模块，还包括推动上下游字段和错误码对齐，并在联调中把问题定位到具体接口或规则版本。这个经历让我认识到，团队协作的关键是让职责、接口和验收标准都可验证。

### 23. 出现方案分歧时怎样推动决策

**建议时长：60 秒。**

我会先把“个人偏好”转换成可验证的工程问题：分歧究竟来自接口职责、数据模型、可靠性，还是开发成本。比如动作类型不断增加时，直接写分支上线快，但后续扩展和回滚成本高；完全动态化又会扩大风险。

我的做法是列出稳定部分和变化点，提出受控配置方案：代码维护动作白名单和参数 Schema，配置只选择允许的动作，变更需要校验、版本和回滚。然后和导师及上下游一起评审，以业务时效、改动范围和故障影响作取舍。决策后把接口、负责人和验收用例写清楚，再通过联调和代码评审收敛，而不是争论谁的方案更“高级”。

### 24. 选择熟悉的游戏并分析一个体验问题

**建议时长：60 秒。**

我长期玩得比较多的是《炉石传说》。一个比较影响体验的问题是移动网络抖动或切网后，客户端已经播放出牌动画，但服务端确认没有及时返回；严重时会进入重连，恢复后棋盘状态和客户端刚才看到的不一致，回合计时也可能已经继续推进。

对回合制卡牌游戏来说，问题不只是平均延迟高，而是玩家无法确认刚才的操作是否真正生效。根因通常涉及上行请求丢失、确认返回延迟、客户端表现先于服务端权威结果，以及重连时状态恢复不完整或不够快。

> 原转写使用《王者荣耀》，但仓库已有个人记录明确说明长期玩《炉石传说》。正式面试应选择真实熟悉的游戏；如果确实更熟悉《王者荣耀》，再按实际体验替换，不能只背网络术语。

### 25. 怎样优化弱网下的游戏体验

**建议时长：75 秒。**

首先坚持服务端权威。每个玩家操作携带递增序列号和请求 ID，客户端在未确认前保留“待确认”状态；超时可以重发，但服务端必须按请求 ID 幂等处理，避免一次出牌执行两次。

其次优化重连。服务端保存可恢复的对局快照和快照后的操作日志，客户端重连时携带最后确认的序列号，服务端返回缺失增量；差距过大时直接下发新快照。回合计时以服务端时间为准，客户端只做显示，重连后重新校准。

最后做弱网适配和观测：压缩关键消息、缩短心跳与断线判定的恢复路径，监控 RTT、抖动、丢包率、重连成功率和恢复耗时。像《炉石传说》这样的回合制游戏不需要像 FPS 那样大量位置预测，重点是操作不重不丢、状态可恢复和结果一致。

## 五、转写术语校正

- `OE / OM`：应为 O(1) / O(n)
- `you are you cache`：应为 LRU Cache
- `free / nex`：应为 `prev / next`
- `电表转换成红黑数`：应为链表转换成红黑树
- `record lock / deep look / next key look`：应为 Record Lock / Gap Lock / Next-Key Lock
- `slack for date / full update`：应为 `SELECT ... FOR UPDATE`
- `import 或 net`：应为 `epoll` 或 Netty
- `CS / and spot`：按上下文应为 CAS、LockSupport 或并发数据结构
- `CPU cache 上面`：应为 CPU Core，Cache 是缓存层级
- `syn rallied / sync online 加 economy / economy`：应为 SYN / SYN + ACK / ACK
- `signalized 的 shift`：应为 `SYN-RECEIVED` 状态
- `logo / 对程序 logo`：应为 NoGo / 不围棋程序
- `proceeding`：按上下文应为 profiling
- `robust hash`：按上下文可能是 Zobrist Hash，但原词无法完全确认
- `差值缓冲区`：实时游戏语境下通常是插值缓冲区；本回答改为更符合卡牌游戏的快照与操作日志恢复
