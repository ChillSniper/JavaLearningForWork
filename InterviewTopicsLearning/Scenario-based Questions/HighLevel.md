以下我为你细致整理的高频场景题及标准答题思路，按照**高并发/秒杀、缓存与数据库、分布式系统、消息队列、海量数据处理、线上排查**六大类别进行分类：

### 一、 高并发与秒杀系统场景（绝对高频）

#### 1. 如何设计一个秒杀系统？如何防止超卖？

- **考察点：** 系统架构能力、并发控制、Redis、MQ。
- **回答思路：**
  - **前端/网关层：** 按钮置灰防抖，Nginx限流，IP黑名单防刷。
  - **缓存层（核心）：** 请求不能直接打到数据库。提前将库存预热到Redis。
  - **防超卖方案：** 使用Redis的`Lua脚本`（保证原子性）进行库存扣减。或者使用`Redisson`分布式锁。
  - **异步削峰：** Redis扣减成功后，立即返回给用户“排队中/抢购成功”，同时生成订单消息发送到**消息队列（MQ）**。
  - **数据库层：** 消费端慢慢从MQ拉取消息，异步落库（MySQL）。数据库扣减库存时加上乐观锁（`update stock = stock - 1 where id = ? and stock > 0`）作为最后一道防线。

#### 2. 接口响应极慢，如何应对突发的流量洪峰？

- *考察点：** 降级、限流、熔断。
- **回答思路：**
  - **限流：** 在网关层（如Spring Cloud Gateway / 自身写的中间件）通过令牌桶算法或漏桶算法进行限流。
  - **降级：** 牺牲非核心业务（如关闭评论、日志降级为异步），保证核心交易链路畅通。
  - **熔断：** 当下游服务不可用时，触发熔断器（如Hystrix/Sentinel），直接返回默认值或错误，防止雪崩。
  - **扩容：** 配合K8s进行容器的快速水平扩容。

### 二、 缓存与数据库一致性场景

#### 1. 缓存穿透、缓存击穿、缓存雪崩是什么？怎么解决？

- *考察点：** Redis经典三连问。
- **缓存穿透（查不到）：** 查一个一定不存在的数据，缓存不命中，每次都打到DB。
  - *解决：* ① 缓存空对象（设置较短过期时间）；② **布隆过滤器（Bloom Filter）**拦截。

#### 2. 缓存击穿（量太大）

- *描述：** 热点Key在失效的瞬间，海量并发请求直接打到DB。
  - *解决：* ① 使用互斥锁（Redis `SETNX`），只让一个线程去查DB重建缓存，其他线程等待；② 热点数据设置“逻辑过期”时间，后台异步线程去更新缓存。

#### 3. 缓存雪崩（大面积失效）

- *描述：** 大量Key在同一时间过期，或者Redis宕机。
  - *解决：* ① Key的过期时间加上一个随机值，避免同时过期；② 搭建Redis集群（高可用）；③ 服务降级和限流。

#### 4. 先更新数据库还是先更新缓存？如何保证双写一致性？

- *考察点：** 架构设计、CAP理论。
- **回答思路：**
  - **推荐策略（Cache Aside Pattern）：** 先更新数据库，**后删除缓存**（不是更新缓存）。
  - **极端并发下的问题：** 如果删除缓存失败怎么办？
  - **解决方案：**
  - **延迟双删：** 更新DB -> 删除缓存 -> 休眠几百毫秒 -> 再次删除缓存。（为了防止读线程把脏数据再次写回缓存）。
  - **终极方案（异步监听）：** 更新DB后，通过Canal（或Golang的go-mysql-elasticsearch）监听MySQL的`Binlog`，将变更消息丢入MQ，消费者消费MQ去重试删除Redis缓存，保证**最终一致性**。

### 三、 分布式系统与接口设计场景

#### 1. 如何保证接口的幂等性？（用户连点两次提交订单怎么办？）

- *考察点：** 幂等性设计。
- **回答思路：**
  - **前端拦截：** 提交后按钮置灰（只能防君子）。
  - **数据库唯一索引：** 给订单号/流水号建唯一索引，重复插入直接报错。
  - **Token机制：** 页面加载时请求后端获取一个全局唯一的Token存入Redis。提交时带上Token，后端收到后利用`Lua脚本`删除Redis中的Token，删除成功才放行，失败则视为重复提交。
  - **状态机：** 更新时带上状态判断（例如：`update order set status='PAID' where id=1 and status='UNPAID'`）。

#### 2. 分布式锁怎么实现？

- *考察点：** Redis与Zookeeper的应用。
- **回答思路：**
  - **Redis实现：** 使用`SET key value NX PX 10000`命令（NX保证互斥，PX设置超时防止死锁）。
  - **缺陷与进阶：** 业务没执行完锁过期了怎么办？引入**看门狗（WatchDog）机制**（如Java的Redisson库），后台开个定时任务，只要业务没执行完，就不断为锁续期。
  - **ZK实现：** 利用Zookeeper的临时顺序节点，谁的序号最小谁拿到锁，客户端断开连接节点自动删除（防死锁）。

### 四、 消息队列（MQ）场景

#### 1. 消息发出去丢失了怎么办？（如何保证消息不丢失？）

- *考察点：** MQ的可靠性投递。
- **回答思路（以Kafka/RabbitMQ为例）：**
  - **生产者端：** 开启确认机制（如RabbitMQ的`Confirm`模式，Kafka的`acks=all`），确保消息到达Broker且所有副本同步完成。
  - **Broker端：** 开启持久化，同步刷盘。
  - **消费者端：** 关闭自动ACK，改为业务处理（如落库）成功后**手动ACK**。

#### 2. 消息积压了怎么处理？

- *考察点：** 线上紧急事故处理能力。
- **回答思路：**
  - **定位原因：** 是消费者挂了？还是下游数据库慢？还是流量突增？
  - **应急处理：** 紧急扩容消费者实例数量（如果Topic的分区数足够）。
  - **如果是消费者处理慢：** 可以把原有消费者当成“搬运工”，不处理业务，直接将消息快速转发到更多的新Topic中，然后用几倍的新消费者去消费新Topic。
  - **死信队列：** 对于处理一直失败的消息，丢入死信队列（DLQ），人工介入排查。

### 五、 海量数据处理场景（大厂极爱考）

#### 1. 100亿个URL，如何找出其中重复的？（单机内存仅有2G）

- *考察点：** 分治思想、哈希。
- **回答思路：** 内存装不下，必须**分而治之**。
  - 遍历100亿个URL，对每个URL求Hash值，然后对1000取模（`hash(url) % 1000`）。
  - 将这些URL分配到1000个小文件中。这样相同的URL一定会被分配到同一个小文件中。
  - 单机依次读取这1000个小文件，将文件中的URL放入内存的`HashSet`中寻找重复项。

#### 2. 有10亿个无序整数，如何快速判断一个数字是否存在？

- *考察点：** Bitmap / 布隆过滤器。
- **回答思路：**
  - 如果只要求精确查找：使用**Bitmap（位图）**。一个数字对应一个bit位，1代表存在，0代表不存在。10亿个位大约只需要120MB内存。
  - 如果允许极小误判：使用**布隆过滤器（Bloom Filter）**，多个Hash函数映射到位图上，空间利用率更高。

### 六、 线上问题排查场景

#### 1. 线上服务器CPU突然飙升到100%，你怎么排查？

- *考察点：** Linux命令、JVM/Go工具。
- **回答思路（Java为主，Go类似）：**
  1. 使用 `top` 命令找出CPU占用最高的**进程ID (PID)**。
  2. 使用 `top -Hp <PID>` 找出该进程中占用CPU最高的**线程ID (TID)**。
  3. 将线程ID转为十六进制（`printf "%x\n" <TID>`）。
  4. 使用 `jstack <PID> | grep <十六进制TID> -A 20` 打印堆栈信息。
  5. 查看代码，通常是因为**死循环**、**频繁Full GC**或**正则回溯**导致。
  - *(Golang选手可回答使用 `go tool pprof` 进行CPU Profile采集和火焰图分析)*。

#### 2. 发生OOM（内存溢出）如何排查？

- **回答思路：**
  1. 确保线上启动参数配置了 `-XX:+HeapDumpOnOutOfMemoryError`，OOM时会自动生成Dump文件。
  2. 如果没配，使用 `jmap -dump:format=b,file=heap.hprof <PID>` 手动导出内存快照。
  3. 将Dump文件导入到 **MAT (Memory Analyzer Tool)** 或 VisualVM 等工具中分析。
  4. 查看大对象（大集合、大报表导出）、内存泄漏（ThreadLocal未清理、静态Map不断塞数据）。

### 七、 数据库与分库分表场景

#### 1. 线上有一条慢查询SQL，你怎么排查和优化？

- *考察点：** 索引底层原理、`EXPLAIN`分析。
- **回答思路：**
  - **定位：** 开启MySQL慢查询日志（Slow Query Log），找出执行时间较长的SQL。
  - **分析：** 使用 `EXPLAIN` 命令分析执行计划。重点看 `type`（有没有走全表扫描 `ALL`，理想是 `ref` 或 `range`）、`key`（实际使用的索引）、`Extra`（是否出现 `Using filesort` 内存排序或 `Using temporary` 临时表）。
  - **优化方案：**
  - **索引失效：** 检查是否有左模糊匹配（`LIKE '%xx'`）、对列使用了函数/计算、或者违反了最左前缀法则。
  - **回表过多：** 如果查询的字段很少，考虑建立**联合索引（覆盖索引）**，避免回表查询。
  - **数据量太大：** 考虑分库分表或将归档数据迁移至Elasticsearch。

#### 2. 深度分页问题（例如 `LIMIT 10000000, 10`）怎么解决？

- *考察点：** MySQL B+树机制、SQL优化。
- **回答思路：**
  - **问题原因：** MySQL会查出 10000010 条数据，然后丢弃前面的 10000000 条，只返回最后 10 条，回表开销极大。
  - **方案一（延迟关联/子查询）：** 先通过索引覆盖只查出主键ID，然后再根据ID去查整行数据。`SELECT * FROM t INNER JOIN (SELECT id FROM t LIMIT 10000000, 10) AS a ON t.id = a.id;`
  - **方案二（游标/游标分页）：** 如果业务允许（比如只能“上一页/下一页”，不能直接跳页），记住上一页最后一条的ID，下次查询带上条件：`WHERE id > 上次最大ID LIMIT 10`。

#### 3. 单表数据量到千万级别了，怎么进行平滑的分库分表（数据迁移）？

- *考察点：** 分库分表策略、双写迁移。
- **回答思路（不停机双写方案）：**
  - **第一阶段：** 代码中配置双数据源，所有的写操作（增删改）同时写入旧表和新表（分库分表后的集群）。
  - **第二阶段：** 写一个后台脚本，将旧表的存量数据迁移到新表中。
  - **第三阶段：** 数据校验脚本运行，对比新旧表数据是否一致，如有差异则进行补偿。
  - **第四阶段：** 灰度切换，读操作逐步切到新表；观察稳定后，下线旧表写逻辑。

### 八、 分布式事务场景

#### 1. 下单扣库存，订单服务和库存服务不在同一个数据库，怎么保证数据一致性？

- *考察点：** 分布式事务理论（CAP/BASE）、Seata、可靠消息。
- **回答思路：**
  - **强一致性（2PC/Seata AT模式）：** 适用于内部后台管理系统。通过全局事务协调器（TC），一阶段锁定资源，二阶段统一提交或回滚。缺点是锁粒度大，性能差。
  - **最终一致性（可靠消息最终一致性/RocketMQ事务消息）：** 适用于高并发电商场景。订单创建后，发送半事务消息给MQ -> 本地执行订单入库 -> 成功则提交消息，失败则回滚消息 -> 库存服务消费消息扣库存。如果库存扣减失败，通过重试机制或人工介入解决，保证最终一致。
  - **TCC模式：** Try（预留资源） -> Confirm（确认执行） / Cancel（取消回滚）。适用于需要强隔离性、且有资金结算的场景，但对业务代码侵入性强。

### 九、 经典业务系统设计场景

#### 1. 微信抢红包系统怎么设计？

- *考察点：** 算法、高并发、锁。
- **回答思路：**
  - **金额分配算法：** “二倍均值法”。每次抢到的金额 = 0.01 ~ (剩余金额 / 剩余人数) * 2。保证每个人抢到的概率相对公平，且不需要提前分配好所有的红包。
  - **高并发拆包：** 发红包时，生成一个包含红包总金额、个数的记录存入Redis。
  - **抢红包：** 利用Redis的 `DECR` 命令（原子性）扣减红包个数。抢到的用户进入MQ异步落库。
  - **保证不超发：** Redis Lua脚本保证（剩余金额 >= 当前人抢到的金额）。

#### 2. 微博/朋友圈的 Feed 流（信息流）系统怎么设计？

- *考察点：** 推拉模型。
- **回答思路：**
  - **拉模式（Pull / 读扩散）：** 用户打开朋友圈时，去获取自己所有关注人的发帖记录，并在内存中根据时间排序。优点：存储空间小；缺点：关注人过多时（比如大V的粉丝），拉取慢。
  - **推模式（Push / 写扩散）：** 用户发动态时，异步将这条动态推送给所有粉丝的“收件箱”（Timeline）。优点：读的时候极快（直接查自己的收件箱）；缺点：大V发帖会导致海量写入（写风暴）。
  - **推拉结合（大厂方案）：** 普通用户采用“推模式”；对于大V（粉丝百万级），采用“拉模式”。用户查看动态时，整合自己收件箱的内容（普通关注人）和大V发件箱的内容，合并排序。

#### 3. 短链接系统怎么设计？（比如 bit.ly 或 t.cn）

- *考察点：** 发号器、哈希、重定向。
- **回答思路：**
  - **核心逻辑：** 发号器生成一个全局唯一的ID（如雪花算法或MySQL自增ID），将ID转换为 **Base62编码**（a-z, A-Z, 0-9），如ID为 10000 转换为短串。数据库中保存 `长链接 <-> 短链接` 的映射关系。
  - **重定向机制：** 用户访问短链接，系统查到长链接后，返回 **HTTP 302（临时重定向）** 而不是 301（永久重定向）。因为 301 会被浏览器缓存，后端无法统计点击量。
  - **缓存：** 热点短链接映射加入Redis，防止高并发访问拖垮DB。

### 十、 安全与架构治理场景

#### 1. 公司有很多个内部系统，如何实现单点登录（SSO）？

- *考察点：** Session机制、JWT、OAuth2.0。
- **回答思路：**
  - **同域下单点登录：** 将Cookie的Domain设置在父域名下（如 `.company.com`），后端的Session存储在统一的Redis集群中。
  - **跨域下单点登录（CAS流程）：**
  1. 用户访问系统A，未登录，重定向到统一认证中心（SSO）。
  2. 在SSO完成登录，SSO生成一个Token（如JWT），重定向回系统A，并在SSO的域下种下全局会话Cookie。
  3. 系统A拿到Token向SSO验证，通过后允许访问。
  4. 用户再访问系统B，重定向到SSO，SSO发现存在全局Cookie，直接发放系统B的Token，实现无感知登录。

#### 2. 如果线上系统不断抛出 “Too many open files” 异常，是什么原因？

- *考察点：** Linux文件句柄限制。
- **回答思路：**
  - 在Linux中，“一切皆文件”，包括网络连接（Socket）。
  - **原因分析：** 可能是系统并发量极大，创建了海量Socket连接；或者是代码有Bug，打开了文件/网络流但没有调用 `close()` 方法关闭资源（资源泄漏）。
  - **解决：** 紧急排查代码中未关闭的流（用 `lsof -p <PID>` 查看打开的文件描述符）；如果确实并发高，修改服务器参数 `ulimit -n` 调大最大文件句柄数。

### 十一、 多线程与并发编程实战场景

#### 1. 商品详情页需要展示商品信息、价格、库存、评价等，这些数据在不同的微服务中，如何优化接口响应时间？

- *考察点：** 异步编排、并发等待。
- **回答思路：**
  - **串行转并行：** 如果挨个调用，总耗时是 `T1+T2+T3+T4`。可以使用多线程并发调用。
  - **Java方案：** 使用 `CompletableFuture`。将四个调用封装为四个异步任务，最后使用 `CompletableFuture.allOf().join()` 等待所有任务完成，总耗时降为 `max(T1, T2, T3, T4)`。
  - **Golang方案：** 使用 `goroutine` + `sync.WaitGroup`（或 `errgroup`）。开启多个协程去拉取数据，主协程 `Wait()` 阻塞等待，组装后返回。
  - **兜底策略：** 如果某个非核心接口（如评价）超时，不能让整个页面挂掉，需要设置超时时间并给出默认值（降级）。

#### 2. 线上的线程池参数应该怎么设置？如果任务队列满了怎么处理？

- *考察点：** 线程池调优、拒绝策略。
- **回答思路：**
  - **参数设置原则：** 不能一刀切，要看是**CPU密集型**（核心线程数设为 CPU核数+1）还是**IO密集型**（通常设为 CPU核数 * 2，或更高，看IO等待时间比例）。
  - **大厂实践：** 采用**动态线程池**方案（如开源的 `Hippo4j` 或美团的 `dynamic-tp`），将线程池参数（核心线程数、最大线程数、队列长度）配置在配置中心（Nacos/Apollo），修改后不用重启服务直接生效。
  - **拒绝策略：** 默认是抛异常（`AbortPolicy`）。如果是不能丢弃的重要任务，可以改为 `CallerRunsPolicy`（让调用者线程自己去执行），或者将任务记录到数据库/日志中，后续后台线程补偿重试。

### 十二、 复杂查询与异构数据同步场景

#### 1. 订单表按“买家ID”进行了分库分表，那卖家想查自己的订单（或者想按订单号查询）怎么办？

- *考察点：** 分库分表带来的查询维度问题（数据冗余/异构）。
- **回答思路：**
  - **按订单号查询：** 生成订单号时，将“买家ID”的哈希值或分库分表基因**融入到订单号**中。解析订单号就能知道该订单在哪个库哪张表。
  - **卖家查询（异构表）：** 通过监听订单表的 `Binlog`（如 Canal 中间件），在后台异步再构建一份**“按卖家ID分库分表”**的冗余表。买家查买家库，卖家查卖家库。
  - **复杂多条件搜索：** 后台服务（如 `Logstash` 或定制化 Go/Java 消费者）将数据同步到 **ElasticSearch (ES)** 中，所有复杂查询走 ES，拿到了订单号再去数据库查详情。

#### 2. 怎么保证 MySQL 和 ElasticSearch 的数据一致性？

- *考察点：** 异构数据源同步机制。
- **回答思路：**
  - **同步双写（不推荐）：** 业务代码写完 MySQL 直接写 ES，耦合高，影响性能。
  - **异步 MQ 双写：** 写完 MySQL 发送 MQ，消费者去更新 ES。缺点是代码侵入性依然存在。
  - **主流方案（基于 Binlog）：** 业务层完全无感知，利用 Canal 伪装成 MySQL 的从节点，拉取 Binlog，解析后推送到 MQ，再由专门的数据同步服务消费并更新到 ES 中（保证最终一致性）。

### 十三、 微服务治理与网关场景

#### 1. 注册中心（如 Nacos / Eureka / Zookeeper）突然全部宕机了，微服务之间还能互相通信吗？

- *考察点：** 微服务底层机制、客户端缓存。
- **回答思路：**
  - **可以通信。**
  - **原理：** 微服务的消费者在启动和运行过程中，会从注册中心拉取服务提供者的实例列表，并**缓存在本地内存中**。
  - 宕机后，只是无法感知到**新的服务上线**或**旧服务下线**，但基于本地缓存的实例列表，依然可以发起 RPC 或 HTTP 调用。

#### 2. 公司要上线一个大版本新功能，如何保证平滑过渡，不影响老用户？（如何实现灰度发布？）

- *考察点：** 网关路由、AB Test。
- **回答思路：**
  - **网关层控制（API Gateway）：** 在网关处（如 Spring Cloud Gateway 或 Nginx）配置路由策略。
  - **基于权重的灰度：** 分配 5% 的流量去新版本集群，95% 走老版本，观察无异常后逐步调大权重。
  - **基于规则的灰度（AB测试）：** 根据 HTTP 请求头中的参数（如 `user_id` 取模，或者判断地域、内部体验账号标识），通过自定义路由断言（Predicate），精准将特定用户路由到新版本服务。

### 十四、 网络协议与实战场景

#### 1. 用户反馈扫码登录页面一直没反应，而扫码登录是怎么设计的？

- *考察点：** 扫码登录原理、长短轮询、WebSocket。
- **回答思路：**
  - **流程设计：** PC端打开页面，向后端请求一个唯一标识（UUID/Token）并生成二维码，状态为“待扫描”。
  - 手机端扫码，将UUID和手机端用户的Token绑定，状态改为“已扫描，待确认”。手机端点击确认，状态改为“已确认”。
  - **PC端如何获取状态变化？**
  - **传统方案（短轮询）：** PC端前端写个定时器，每隔 2 秒请求一次后端问状态。缺点：大量无效请求，浪费服务器性能。
  - **进阶方案（长轮询）：** PC端请求后端，后端如果没有状态变更，就**把请求挂起（阻塞）**，直到有结果或超时才返回。极大减少请求次数。
  - **主流方案（WebSocket）：** PC端与后端建立 WebSocket 长连接，手机端扫码确认后，后端主动向 PC 端推送登录成功的消息并附带 Token。

#### 2. 服务器上出现大量的 `TIME_WAIT` 状态的连接，会引发什么问题？怎么解决？

- *考察点：** TCP 四次挥手实战。
- **回答思路：**
  - **原因：** `TIME_WAIT` 出现在主动关闭连接的一方（比如高并发下主动断开短连接的服务器）。它是为了保证最后一个 ACK 能到达对方，且让网络中残留的旧报文消亡。
  - **引发的问题：** 占用服务器大量的本地端口（默认最多65535个），导致无法发起新的对外连接；占用内存和 CPU。
  - **解决：**
  1. **业务层面：** 尽量使用长连接（HTTP `Keep-Alive`，数据库/Redis 连接池），避免频繁建立和关闭连接。
  2. **OS 层面调优：** 修改 `sysctl.conf`，开启 `tcp_tw_reuse`（允许将 TIME_WAIT socket 重新用于新的 TCP 连接），缩短 `tcp_fin_timeout` 时间。

### 十五、 语言底层级线上排查场景（Java / Go 特定）

#### 1. (Java方向) 线上系统响应突然变得一卡一卡的，监控显示 CPU 并没有飙高，怎么排查？

- *考察点：** JVM 垃圾回收（GC）。
- **回答思路：**
  - 很可能是发生了 **频繁的 Full GC**（会引发 Stop The World，暂停所有业务线程，导致系统卡顿）。
  - 排查步骤：使用 `jstat -gcutil <PID> 1000` 观察老年代内存使用率和 Full GC 的频率及耗时。
  - 如果发现 Full GC 频繁，导出 Dump 文件使用 MAT 分析，通常是因为：1. 内存泄漏（大对象未释放）；2. 经常进行大批量数据查询；3. JVM 内存分配不合理（如新生代太小，导致对象过早进入老年代）。

#### 2. (Golang方向) 线上服务内存持续上涨，没有下降趋势，怎么排查和解决？

- *考察点：** 内存泄漏、Goroutine 泄漏。
- **回答思路：**
  - Go 语言中引起内存泄漏最常见的原因是 **Goroutine 泄漏**（协程死锁或被永远阻塞，导致其占用的栈内存和关联的对象无法被 GC 回收）。
  - **排查工具：** 开启 `net/http/pprof`。
  - **具体步骤：** 访问 `http://ip:port/debug/pprof/goroutine?debug=1` 查看当前 Goroutine 数量。如果数量异常大且持续增加，抓取 Profile 并使用 `go tool pprof` 分析，看是哪行代码卡住了协程（常见的比如：向无缓冲的 channel 写数据但无人读取，或者 context 没有正确调用 cancel）。

### 十六、 大文件与资源处理场景

#### 1. 前端需要上传一个 5GB 的视频文件，后端应该怎么设计来保证稳定性和速度？

- *考察点：** 分片上传、断点续传、大文件处理。
- **回答思路：**
  - **前端分片（Chunking）：** 前端利用 HTML5 的 `File API` 将 5GB 文件切分成多个小块（如每块 5MB），并计算整个文件的 **MD5 值**（用于秒传和校验）。
  - **并发上传：** 前端并发将分片发给后端，请求头带上 `文件MD5`、`当前分片序号`、`总分片数`。
  - **后端接收与断点续传：** 后端接收分片，存入临时目录或对象存储（OSS）。如果网络中断，前端下次上传前先请求接口查询“已上传的分片序号”，只上传缺失的部分。
  - **合并分片：** 所有分片上传完毕后，前端发起“合并请求”，后端校验所有分片并在后台异步合并。合并期间返回前端“处理中”状态。

#### 2. 用户上传了大量重复的文件（比如同一张表情包），怎么节省服务器存储空间？

- *考察点：** 秒传机制、哈希摘要。
- **回答思路：**
  - **“秒传”原理：** 在数据库中建立一张文件摘要表，核心字段是 `文件MD5值` 和 `真实存储路径 (URL)`。
  - 用户上传前，前端先计算文件的 MD5 传给后端。后端去数据库查这个 MD5 是否存在。
  - 如果存在，说明服务器上已经有这个文件了。后端直接在当前用户的名下插入一条记录，指向已存在的文件 URL，并直接告诉前端“上传成功”（实际并未传输文件体）。

### 十七、 定时任务与调度场景

#### 1. 电商系统中“订单创建 30 分钟未支付自动取消”，怎么实现？

- *考察点：** 延迟任务、死信队列、时间轮。
- **回答思路（由简到繁）：**
  - **方案一（定时扫表）：** 写个定时任务每分钟扫一次订单表（`where status=未支付 and create_time < 30分钟前`）。**缺点：** 数据库压力大，且有延迟误差。
  - **方案二（Redis 键空间通知 / ZSet）：** 将订单号存入 Redis 的 `ZSet`，`score` 设为过期时间的时间戳。后台线程定时利用 `ZRANGEBYSCORE` 拉取已过期的订单。
  - **方案三（主流：MQ 延迟队列）：** 比如 RocketMQ 自带延迟消息级别，或者 RabbitMQ 使用死信队列（DLX）+ TTL。订单创建时发一条延迟 30 分钟的消息，30 分钟后消费者收到消息，去数据库检查状态，如果未支付则执行取消逻辑。

#### 2. 线上有多个微服务实例，怎么保证定时任务同一时刻只在一个实例上执行？

- *考察点：** 分布式锁、分布式调度框架。
- **回答思路：**
  - **简单方案：** 任务执行前，先去 Redis 抢占**分布式锁**（`SETNX`）。抢到锁的实例执行任务，没抢到的直接 return。
  - **企业级方案：** 引入分布式任务调度中心（如开源的 **XXL-JOB** 或 ElasticJob）。在调度中心配置路由策略为“第一个”或“轮询”，由调度中心统一触发某个实例执行，避免并发冲突。

### 十八、 社交与排行榜场景

#### 1. 游戏里有上百万玩家，怎么设计一个实时的战力排行榜（Top 100）？

- *考察点：** Redis ZSet 底层原理。
- **回答思路：**
  - 不要用数据库的 `ORDER BY` 加 `LIMIT`，性能扛不住。
  - 使用 **Redis 的 Sorted Set (ZSet)** 数据结构。
  - 玩家战力变化时，执行 `ZADD leaderboard score userId`。
  - 获取前 100 名时，执行 `ZREVRANGE leaderboard 0 99 WITHSCORES`（时间复杂度仅为 O(log(N) + M)）。
  - **进阶追问：如果分数相同，想让先达到该分数的玩家排前面怎么办？**
  - 将 Score 改造为一个浮点数或大整数：`分数 + (某一极大数据 - 达到该分数的时间戳)`。这样分数相同时，时间戳越小（越早），整体 Score 越大。

#### 2. 外卖 APP 里的“附近距离我 3 公里内的商家”，是怎么算出来的？

- *考察点：** LBS 服务、GeoHash。
- **回答思路：**
  - **Redis GEO 方案：** 利用 Redis 的 `GEOADD` 存储商家的经纬度，用户刷新时使用 `GEORADIUS` 传入用户的经纬度和半径（3km），即可快速返回商家列表。
  - **数据库 GeoHash 方案：** 将二维的经纬度映射为一个一维的字符串（GeoHash 算法）。距离越近的地点，它们的 GeoHash 字符串前缀越匹配。在数据库中对 GeoHash 字段建索引，通过 `LIKE '前缀%'` 快速筛选。

### 十九、 第三方对接与重试机制场景

#### 1. 我们的系统调用微信支付接口，如果遇到网络超时，怎么处理？

- *考察点：** 幂等性、重试机制、补偿机制。
- **回答思路：**
  - **不能直接当失败处理：** 网络超时可能是请求没发出去，也可能是微信处理成功了但响应没回来。
  - **主动查询：** 捕获超时异常后，发起一次对微信支付“订单查询接口”的调用，以微信端的状态为准。
  - **异步重试回调：** 如果查询接口也超时，可以采用**指数退避算法**（如隔 1s, 2s, 4s, 8s）将重试任务放入延迟队列，同时提供一个“手动同步状态”的按钮供客服或用户兜底操作。

#### 2. 如果你的接口被竞争对手恶意疯狂调用（CC 攻击），怎么防范？

- *考察点：** 安全防护、限流降级。
- **回答思路：**
  - **接入层拦截：** 在 Nginx 或 WAF（Web应用防火墙）层，针对单一 IP 限制请求频率（`limit_req`）。如果触发阈值，直接封禁 IP 一段时间。
  - **应用层限流：** 使用 Sentinel 或 Redis 滑动窗口限流。针对 `User-Agent`、`IP`、`设备指纹` 等维度进行多条件联合限流。
  - **业务层校验：** 核心接口增加图形验证码、滑块验证，增加机器调用的成本。
