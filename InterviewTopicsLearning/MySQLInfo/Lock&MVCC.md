# Lock & MVCC

MySQL 的锁机制和 MVCC 是高级开发工程师面试中**绝对的必考点**。它们是 MySQL 并发控制的基石。我为你分模块梳理得通俗易懂一些。

##

---

### 一、 MySQL 中的锁机制详解

MySQL 的锁按照**粒度**主要分为全局锁、表级锁和行级锁。日常开发和面试最常遇到的是 InnoDB 引擎下的**行级锁**和**表级锁**。

#### 1. 按照锁的属性（操作类型）分类

无论是表锁还是行锁，都可以分为读锁和写锁：
**共享锁（S锁 / 读锁）：** 允许多个事务同时读取同一个资源，但都不允许修改。互相不阻塞。
**排他锁（X锁 / 写锁）：** 当一个事务获取了写锁，其他事务既不能读（这里指当前读，快照读除外）也不能写。排斥其他一切锁。

#### 2. 表级锁 (Table Locks)

每次操作锁住整张表，开销小，加锁快，但并发度极低。

**表锁：** 直接对整张表加读锁或写锁（`LOCK TABLES t READ/WRITE`）。
**元数据锁（MDL）：** 系统自动加的。当你对表执行增删改查时，自动加 MDL 读锁；当你修改表结构（比如加一列 `ALTER TABLE`）时，自动加 MDL 写锁。防止别人正在查数据时，表结构被改了。
**意向锁（Intention Locks）：** InnoDB 特有的表级锁，分为意向共享锁(IS)和意向排他锁(IX)。**它的唯一目的就是提高加表锁的效率。** 比如事务A给表里的某一行加了行级写锁，系统会自动给这张表加上表级意向写锁（IX）。如果此时事务B想给整张表加表级写锁，发现表上有 IX 锁，就知道表里肯定有行数据被锁着，直接排队等待，而不需要去遍历每一行看有没有行锁。

#### 3. 行级锁 (Row Locks) —— InnoDB 核心

每次操作锁住具体的行数据，开销大，加锁慢，但并发度最高。InnoDB 的行锁是**针对索引加的锁**，不是针对记录本身。
**记录锁（Record Lock）：** 锁住具体的某一条索引记录。比如 `SELECT * FROM t WHERE id = 1 FOR UPDATE;`，如果 id 是唯一索引，就加记录锁。
**间隙锁（Gap Lock）：** 锁住两个索引记录之间的“间隙”，**不包括记录本身**。它的目的是防止其他事务在这个间隙里插入新数据，从而**防止幻读现象**。（仅在可重复读 RR 隔离级别下生效）。
**临键锁（Next-Key Lock）：** **Record Lock + Gap Lock 的结合体**。它不仅锁住某条记录，还锁住这条记录前面的间隙。这是 InnoDB 在可重复读（RR）隔离级别下的**默认行锁算法**。比如索引有 1, 5, 10，如果锁住了 5，实际上是锁住了 `(1, 5]` 这个左开右闭的区间。

### 二、 面试关于 MySQL 锁的高频问题

**MySQL 的行锁是怎么实现的？**
    答：InnoDB 的行锁是通过给**索引上的索引项加锁**来实现的，而不是给表的物理行记录加锁。如果你的 SQL 语句没有走索引，InnoDB 就会退化成**全表扫描，把所有记录都加上临键锁，相当于锁表了**！这在生产环境是灾难。

**什么是死锁？怎么解决？**
    答：死锁是指两个或多个事务互相持有对方需要的锁，并请求对方已持有的锁，导致死循环。比如：事务A锁住行1请求行2，事务B锁住行2请求行1。
    解决：InnoDB 有死锁检测机制（`innodb_deadlock_detect=on`），会自动回滚其中一个代价较小的事务，让另一个继续。业务端可以通过保持加锁顺序一致、尽量减小事务范围来预防。

**悲观锁和乐观锁的区别？**
    答：**悲观锁**是真正利用数据库底层的锁机制（如 `FOR UPDATE`的排他锁），认为别人一定会并发修改。**乐观锁**不是数据库层面的锁，而是业务代码层面的控制，通常通过给表加一个 `version` 字段来实现，更新时判断 `version` 是否变化（CAS 思想），适合读多写少的场景。

### 三、 MVCC（多版本并发控制）详解

在没有 MVCC 的时代，为了保证数据一致性，读写操作是互相阻塞的（读要等写完，写要等读完）。
**MVCC 的核心目的就是：实现读-写冲突时的非阻塞并发，提高系统并发性能。** 让“快照读”不需要加锁。

#### 1. 当前读 vs 快照读

**当前读：** 读取的是记录的**最新版本**，并且读取时要保证其他并发事务不能修改当前记录，**需要加锁**。例如：`SELECT ... FOR UPDATE`，`UPDATE`，`DELETE`。
**快照读：** 不加锁的普通的 `SELECT`。读取的是记录的可见版本（可能是历史版本）。

#### 2. MVCC 的三大核心组件

MVCC 是通过“隐藏字段 + Undo Log + Read View”来实现的：

**隐藏字段：** InnoDB 每行数据除了你建的列，还有几个隐藏列：
    `DB_TRX_ID`：最近一次修改这条记录的事务 ID。
    `DB_ROLL_PTR`：回滚指针，指向这条记录在 Undo Log 中的上一个历史版本。
**Undo Log（回滚日志）：** 记录了数据修改前的状态。多个事务对同一行数据修改时，Undo Log 会通过 `DB_ROLL_PTR` 形成一条**版本链**。链表头是最新数据，链表尾是最老数据。
**Read View（读视图）：** 事务进行“快照读”时，会生成一个 Read View。它相当于拍了一张当前系统活跃事务的“快照”。Read View 里面记录了：
    当前系统未提交的活跃事务列表（`m_ids`）。
    最小活跃事务ID（`min_trx_id`）。
    下一个应该分配的事务ID（最大活跃事务ID + 1，`max_trx_id`）。

#### 3. MVCC 是怎么判断该读哪个版本的？（可见性算法）

当查询一条记录时，顺着版本链往下找，用每个版本的 `DB_TRX_ID` 和 Read View 对比：

如果版本的 `TRX_ID < min_trx_id`，说明这个版本在生成 Read View 前就已经提交了，**可见**。

如果版本的 `TRX_ID >= max_trx_id`，说明是生成 Read View 后才开启的事务修改的，**不可见**，继续找上一个版本。

如果在 `min` 和 `max` 之间，则看 `TRX_ID` 是不是在 `m_ids`（活跃事务列表）里。如果在，说明修改它的事务还没提交，**不可见**；如果不在，说明修改它的事务已经提交了，**可见**。

#### 4. RC 和 RR 隔离级别下的 MVCC 区别（面试重点）

**读已提交（RC）：** **每次执行 SELECT 语句时**，都会生成一个全新的 Read View。所以能读到别的事务刚提交的数据（不可重复读）。
**可重复读（RR）：** **只有在事务中第一次执行 SELECT 时**，生成一个 Read View，之后的 SELECT 都复用这同一个 Read View。所以整个事务期间看到的数据快照是不变的，解决了不可重复读问题。
