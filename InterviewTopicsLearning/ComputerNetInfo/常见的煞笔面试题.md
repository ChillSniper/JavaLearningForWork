# 计算机网络常见面试题

## 一、TCP 三次握手

**过程：**

1. 客户端 → 服务端：`SYN=1, seq=x`（客户端进入 SYN_SENT）
2. 服务端 → 客户端：`SYN=1, ACK=1, seq=y, ack=x+1`（服务端进入 SYN_RCVD）
3. 客户端 → 服务端：`ACK=1, seq=x+1, ack=y+1`（双方进入 ESTABLISHED）

**字段含义：**

- **SYN**（Synchronize Sequence Numbers）：同步序列号，发起连接时置 1
- **ACK**（Acknowledgment）：确认标志，确认对方时置 1
- **seq**：本方的初始序列号（随机生成，防止旧包干扰）
- **ack**：期望收到对方的下一个序列号 = 对方 seq + 1

**为什么需要第三次握手？**

1. **验证双向通信能力**：两次握手后服务端不知道自己发的消息客户端能否收到，第三次握手才能验证双向收发均正常
2. **防止历史失效连接**：旧 SYN 延迟到达时，若只有两次握手，服务端会建立连接并分配资源，但客户端已关闭，造成资源浪费。三次握手时客户端会回复 RST，服务端释放资源

> 三次是验证双向收发能力的最少次数，两次不够，四次多余。

## 二、TCP 四次挥手

**过程：**

1. 主动方 → 被动方：`FIN=1`（主动方进入 FIN_WAIT_1）
2. 被动方 → 主动方：`ACK=1`（主动方进入 FIN_WAIT_2，被动方进入 CLOSE_WAIT，继续发剩余数据）
3. 被动方 → 主动方：`FIN=1`（被动方进入 LAST_ACK）
4. 主动方 → 被动方：`ACK=1`（**主动方进入 TIME_WAIT**，被动方进入 CLOSED）
5. 主动方等待 2MSL 后进入 CLOSED

**为什么是四次而非三次？**

服务端收到 FIN 必须立刻回 ACK，但 FIN 要等自身数据发完才能发，ACK 和 FIN 不能合并。

**TIME_WAIT 为什么等 2MSL？**

- **保证最后的 ACK 到达**：ACK 若丢失（1MSL），被动方重传 FIN（1MSL），主动方需还在等待状态才能响应，否则被动方永远卡在 LAST_ACK
- **让旧报文自然消亡**：防止网络中滞留的旧连接报文污染同四元组的新连接

## 三、TCP 和 UDP 的区别

| 维度          | TCP                      | UDP                 |
| ------------- | ------------------------ | ------------------- |
| 连接          | 面向连接（三次握手）     | 无连接              |
| 可靠性        | 可靠（确认、重传、排序） | 不可靠（尽力而为）  |
| 效率          | 低（头部大、有控制机制） | 高（头部仅 8 字节） |
| 顺序          | 保证有序到达             | 不保证顺序          |
| 流量/拥塞控制 | 有                       | 无                  |
| 适用场景      | HTTP、FTP、数据库        | 视频、DNS、游戏     |

## 四、HTTP 和 HTTPS 的区别

| 维度 | HTTP     | HTTPS          |
| ---- | -------- | -------------- |
| 端口 | 80       | 443            |
| 安全 | 明文传输 | TLS/SSL 加密   |
| 证书 | 不需要   | 需要 CA 证书   |
| 性能 | 略快     | 握手有额外开销 |

**HTTPS 握手过程（TLS 1.3 简化版）：**

1. 客户端发送支持的加密套件列表 + 随机数
2. 服务端选定加密套件，返回证书 + 随机数
3. 客户端验证证书（CA 链），生成预主密钥，用服务端公钥加密发送
4. 双方用三个随机数生成对称密钥，后续通信用对称加密

> 非对称加密用于**密钥交换**，对称加密用于**数据传输**（性能更高）

## 五、HTTP 1.0 / 1.1 / 2.0 / 3.0 区别

| 版本     | 核心改进                                                             |
| -------- | -------------------------------------------------------------------- |
| HTTP 1.0 | 短连接，每次请求都要建立/关闭 TCP                                    |
| HTTP 1.1 | 长连接（keep-alive）、管道化（但有队头阻塞）                         |
| HTTP 2.0 | 多路复用（一个 TCP 连接并发多个请求）、头部压缩（HPACK）、服务端推送 |
| HTTP 3.0 | 基于 QUIC（UDP）、彻底解决队头阻塞、内置 TLS、连接迁移               |

**队头阻塞：**

- HTTP 1.1：前一个请求未响应，后续请求排队等待
- HTTP 2.0：应用层解决了队头阻塞，但 TCP 层丢包仍会阻塞所有流
- HTTP 3.0：QUIC 基于 UDP，每个流独立，丢包只影响该流

## 六、DNS 解析过程

```java
浏览器输入 www.example.com
    ↓
1. 浏览器缓存 → 2. OS hosts 文件 → 3. 本地 DNS 缓存
    ↓ 若都未命中
4. 向本地 DNS 服务器查询（递归查询）
    ↓
5. 本地 DNS → 根域名服务器（返回 .com 服务器地址）
6. 本地 DNS → .com 顶级域名服务器（返回 example.com 服务器地址）
7. 本地 DNS → example.com 权威域名服务器（返回 IP）
    ↓
8. 本地 DNS 缓存结果，返回给客户端
```

- **递归查询**：客户端只问本地 DNS，本地 DNS 负责问到底
- **迭代查询**：本地 DNS 每次返回下一个要问的服务器地址，客户端自己问

## 七、浏览器输入 URL 到页面显示，发生了什么？

1. **DNS 解析**：域名 → IP
2. **TCP 三次握手**：建立连接
3. **TLS 握手**（HTTPS）：建立加密信道
4. **发送 HTTP 请求**：GET / HTTP/1.1
5. **服务器处理并响应**：返回 HTML
6. **浏览器解析 HTML**：构建 DOM 树
7. **加载 CSS / JS**：构建 CSSOM，执行脚本
8. **渲染页面**：Layout → Paint → Composite
9. **TCP 四次挥手**（或保持长连接）

## 八、TCP 可靠传输机制

| 机制            | 作用                                       |
| --------------- | ------------------------------------------ |
| 序列号 + 确认号 | 保证数据有序，检测丢包                     |
| 超时重传        | 超时未确认则重发                           |
| 快速重传        | 收到 3 个重复 ACK 立即重传                 |
| 滑动窗口        | 流量控制，避免发送方压垮接收方             |
| 拥塞控制        | 慢启动 → 拥塞避免 → 快速恢复，避免压垮网络 |

## 十、Cookie 和 Session 的区别

| 维度     | Cookie                   | Session                    |
| -------- | ------------------------ | -------------------------- |
| 存储位置 | 客户端浏览器             | 服务端                     |
| 安全性   | 低（可被篡改/窃取）      | 高（数据在服务端）         |
| 容量     | 约 4KB                   | 无限制（受服务端内存）     |
| 生命周期 | 可持久化（设置过期时间） | 默认随会话结束             |
| 跨域     | 受同源策略限制           | 依赖 Cookie 传递 SessionID |

> **JWT** 是无状态的替代方案：将用户信息签名后存在客户端 Token 中，服务端无需存储 Session，适合分布式系统。
