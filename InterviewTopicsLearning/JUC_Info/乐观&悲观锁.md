# 乐观锁 & 悲观锁

---

## 一、核心思想对比

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| **核心假设** | 冲突一定会发生，先加锁再操作 | 冲突很少发生，操作完再校验 |
| **策略** | 独占资源，其他线程阻塞等待 | 不加锁，提交时检测冲突，冲突则重试或失败 |
| **代价** | 线程阻塞、上下文切换开销大 | 冲突率高时大量重试，CPU 浪费 |
| **适合场景** | 写多、冲突概率高 | 读多写少、冲突概率低 |

---

## 二、悲观锁

### 2.1 原理

操作数据前先获取锁，整个操作过程其他线程被阻塞。基于"悲观"假设：**不加锁就一定会出问题**。

### 2.2 Java 中的实现

```java
// 方式1：synchronized
public synchronized void transfer(Account from, Account to, int amount) {
    from.deduct(amount);
    to.add(amount);
}

// 方式2：ReentrantLock
private final ReentrantLock lock = new ReentrantLock();

public void transfer(int amount) {
    lock.lock();
    try {
        // 临界区操作
    } finally {
        lock.unlock(); // 必须在 finally 中释放
    }
}
```

### 2.3 数据库中的实现

```sql
-- SELECT ... FOR UPDATE（行级悲观锁，事务提交/回滚时释放）
BEGIN;
SELECT * FROM account WHERE id = 1 FOR UPDATE;  -- 加行锁
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

### 2.4 悲观锁的问题

- **性能低**：线程阻塞 + 操作系统上下文切换代价高
- **死锁风险**：多个悲观锁嵌套获取时可能死锁
- **不适合高并发读场景**：读操作也被串行化，浪费资源

## 三、乐观锁

### 3.1 原理

不加锁，操作前记录"版本/旧值"，提交时校验数据是否被其他人修改过：

- **没被修改** → 更新成功
- **已被修改** → 失败重试 或 直接报错

### 3.2 实现方式一：CAS（Compare And Swap）

**CAS 是乐观锁的一种实现，不等于乐观锁本身。**

```java
CAS(内存地址, 期望值, 新值)
→ 若内存中的值 == 期望值，则将其替换为新值，返回 true
→ 若内存中的值 != 期望值（说明被别人改了），返回 false，调用方重试
```

```java
// Java 中的 AtomicInteger 底层就是 CAS
AtomicInteger counter = new AtomicInteger(0);

// 自旋 CAS（底层调用 Unsafe.compareAndSwapInt，CPU 原子指令）
counter.incrementAndGet();

// 手动 CAS 循环（模拟原理）
int oldVal, newVal;
do {
    oldVal = counter.get();
    newVal = oldVal + 1;
} while (!counter.compareAndSet(oldVal, newVal)); // 失败就重试
```

**CAS 底层依赖 CPU 的 `cmpxchg` 原子指令**，不依赖操作系统锁，因此是无锁的（实际是自旋）。

#### CAS 的三大问题

**① ABA 问题**:

```java
线程A读到值=1，准备CAS为2
线程B将值 1→2→1（改了又改回来）
线程A执行CAS，发现值还是1，认为没人改过，成功了

但实际上数据已经被别人动过！

```

解决：`AtomicStampedReference`（带版本号）或 `AtomicMarkableReference`（带标记位）

```java
// 版本号方案：每次修改版本号+1，CAS 同时校验值和版本号
AtomicStampedReference<Integer> asr = new AtomicStampedReference<>(1, 0);
int[] stampHolder = new int[1];
Integer val = asr.get(stampHolder);     // 同时获取值和版本号
asr.compareAndSet(val, 2, stampHolder[0], stampHolder[0] + 1); // CAS 时校验版本号
```

**② 自旋开销问题**
竞争激烈时，CAS 失败率高，大量线程自旋消耗 CPU。
解决：`LongAdder`（分段累加，减少单点竞争）；限制重试次数后升级为悲观锁。

**③ 只能保证单个变量的原子性**
多个变量的组合操作无法用单个 CAS 保证原子性。
解决：`AtomicReference` 将多个变量封装成一个对象后整体 CAS；或改用悲观锁。

### 3.3 实现方式二：版本号机制（数据库乐观锁）

最常见的数据库乐观锁方案，与 CAS 无关，靠 SQL 条件判断实现。

```sql
-- 表设计：增加 version 字段
CREATE TABLE product (
    id BIGINT PRIMARY KEY,
    stock INT NOT NULL,
    version INT NOT NULL DEFAULT 0
);

-- 读取时记录 version
SELECT id, stock, version FROM product WHERE id = 1;
-- 返回：stock=100, version=5

-- 更新时同时校验 version（乐观锁核心）
UPDATE product
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;   -- ← 条件带上旧 version

-- 判断 affected rows：
-- = 1 → 更新成功（没有并发冲突）
-- = 0 → 别人先改了，重试 或 返回失败
```

**变体：时间戳（updateTime 字段）替代 version**，原理相同。

```java
// MyBatis-Plus 中的乐观锁插件
@Version                      // 加这个注解，框架自动处理 version 字段
private Integer version;
```

## 四、乐观锁 vs 悲观锁 详细对比

| 维度 | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| **实现原理** | 操作前加互斥锁 | 操作前记录版本/旧值，提交时校验 |
| **Java 实现** | `synchronized`、`ReentrantLock` | `AtomicXxx`（CAS）、版本号 |
| **数据库实现** | `SELECT ... FOR UPDATE` | `WHERE version = ?` 条件更新 |
| **并发吞吐** | 低（线程串行） | 高（无阻塞，并发进行） |
| **冲突处理** | 等待锁释放后重试 | 检测到冲突后重试或失败 |
| **死锁风险** | 有 | 无（不加锁） |
| **适合读写比** | 写多 | 读多写少 |
| **上下文切换** | 多（线程阻塞/唤醒） | 无（自旋或直接失败） |
| **数据一致性** | 强（持锁期间独占） | 依赖正确的版本号校验 |

## 五、业务场景关联

### 悲观锁适合的场景

**1. 高并发写操作，冲突概率高**：

- 银行转账、库存扣减（秒杀核心逻辑）
- 支付流水生成（绝对不能重复）

**2. 操作涉及多条记录，需要事务一致性**：

```sql

-- 转账操作，必须原子完成，适合悲观锁
BEGIN;
SELECT * FROM account WHERE id IN (1, 2) FOR UPDATE; -- 同时锁两行
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

**3. 任务调度防重（分布式定时任务抢占）**：

```sql
-- 多个节点竞争同一个任务，用悲观锁防止重复执行
SELECT * FROM job WHERE status = 'PENDING' LIMIT 1 FOR UPDATE;
```

---

### 乐观锁适合的场景

**1. 读多写少，冲突概率低**：

- 文章点赞数、商品浏览量、用户积分累加
- 用户信息修改（同时修改同一用户信息的概率极低）

**2. 库存扣减（中低并发场景）**：

```sql
-- 乐观锁扣库存
UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = #{version} AND stock > 0;  -- 同时防超卖
```

**3. 分布式场景下的无锁并发**：

- Redis 中用 `WATCH` + `MULTI/EXEC` 实现乐观锁（事务+监视键）

```java
WATCH stock          # 监视 key，若被修改则事务失败
MULTI
DECR stock
EXEC                 # 若 stock 在 WATCH 后被改过，EXEC 返回 nil
```

**4. JUC 中的原子操作场景**：

- 计数器：`AtomicLong`、`LongAdder`
- 引用更新：`AtomicReference`
- 无锁队列：`ConcurrentLinkedQueue`（内部大量 CAS）

---

### 混合使用：先乐观，失败后升级悲观

高性能系统常见模式：

```java
// 先尝试乐观（CAS），失败重试 N 次后降级为悲观锁
for (int i = 0; i < MAX_RETRY; i++) {
    if (counter.compareAndSet(expected, newVal)) {
        return; // 成功
    }
}
// 重试耗尽，退化为悲观锁
synchronized(this) {
    counter.set(newVal);
}
```

## 六、面试高频问题

**Q1：乐观锁和悲观锁的区别是什么？**
> 悲观锁认为并发冲突一定发生，操作前加锁（`synchronized`/`SELECT FOR UPDATE`），其他线程阻塞等待；乐观锁认为冲突很少发生，不加锁，提交时通过 CAS 或版本号校验是否被修改，冲突则重试。悲观锁适合写多场景，乐观锁适合读多写少场景。

**Q2：CAS 是乐观锁吗？**
> CAS 是乐观锁的**一种具体实现方式**，不是乐观锁本身。乐观锁是一种思想：操作前不加锁，提交时检测冲突。除了 CAS，数据库版本号机制也是乐观锁，Redis WATCH 也是乐观锁，它们和 CAS 没有关系。

**Q3：CAS 有哪些问题？如何解决？**

> 1. **ABA 问题**：值被改了又改回来，CAS 无法感知。解决：`AtomicStampedReference`（版本号）
> 2. **自旋开销**：竞争激烈时大量失败重试耗费 CPU。解决：`LongAdder` 分段；限制重试次数；或改用悲观锁
> 3. **只能保证单变量原子性**：无法同时保证多个变量。解决：`AtomicReference` 封装对象；或用悲观锁

**Q4：数据库乐观锁怎么实现？**
> 表中增加 `version`（或 `update_time`）字段，读取时记录版本号，更新时在 WHERE 条件中加 `AND version = #{旧版本号}`，同时将 version+1。判断 affected rows：= 1 表示成功，= 0 表示被其他事务抢先修改，需重试或返回失败。

**Q5：秒杀场景中用乐观锁还是悲观锁？**
> 取决于并发量：
>
> - 并发量极高（万级 QPS）时，乐观锁冲突率极高，大量重试会放大数据库压力，**不适合纯乐观锁**。通常配合 Redis 预扣库存（Redis 单线程天然原子性）+ MQ 异步落库，数据库层面冲突已极少，再用乐观锁兜底。
> - 并发量中等时，乐观锁（版本号）扣库存够用，且无死锁风险。
> - 如果要用悲观锁（`FOR UPDATE`），需注意事务要短，否则长时间持锁会成为瓶颈。

**Q6：synchronized 是悲观锁还是乐观锁？**
> **悲观锁**。虽然 JDK 6 后引入了偏向锁、轻量级锁等优化，看起来轻量级锁用了 CAS，但从**设计思想**上看，synchronized 是先加锁再操作的悲观模式。CAS 在这里只是优化手段，降低锁开销，不改变其悲观锁的本质。

**Q7：LongAdder 为什么比 AtomicLong 性能好？**
> `AtomicLong` 所有线程竞争同一个 `value` 变量，高并发下 CAS 失败率高，大量自旋。
> `LongAdder` 将计数分散到多个 `Cell` 数组（分段），不同线程更新不同的 Cell，减少竞争；最终 `sum()` 汇总所有 Cell。代价是 `sum()` 结果不是强一致的实时值，适合统计场景（不适合要求精确实时的场景如 AtomicLong 做序列号）。

**Q8：什么是自旋锁？它和乐观锁有什么关系？**
> 自旋锁是指线程在获取锁失败后，不进入阻塞（不放弃 CPU），而是持续循环检测锁是否释放（"空转等待"）。CAS 的重试循环就是一种自旋，所以基于 CAS 的乐观锁本质上是自旋锁。自旋适合锁持有时间短的场景，否则白白浪费 CPU。
