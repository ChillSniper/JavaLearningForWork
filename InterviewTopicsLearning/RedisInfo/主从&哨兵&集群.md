# Redis 主从 & 哨兵 & 集群

## 一、主从复制（Master-Slave）

### 核心原理

- Master 负责写，Slave 同步 Master 数据负责读（读写分离）
- 写请求只能打到 Master，读请求可分发到任意 Slave

### 复制流程

**全量同步（首次连接）：**

1. Slave 发送 `PSYNC` 命令给 Master
2. Master `fork` 子进程生成 RDB 快照，发送给 Slave
3. Slave 载入 RDB
4. Master 将生成 RDB 期间的写命令（replication buffer）补发给 Slave

**增量同步（断线重连）：**

1. Master 维护 `repl_backlog`（环形缓冲区）记录近期写命令
2. Slave 携带自身 `offset` 重新连接
3. Master 判断 offset 是否还在 backlog 范围内：
   - 在：只发送 offset 之后的命令（增量）
   - 不在（backlog 已被覆盖）：重新全量同步

### 主从的缺点

- Master 宕机需**手动切换**，无法自动故障转移 → 引出哨兵模式

## 二、哨兵模式（Sentinel）

### 解决的问题

在主从基础上，实现 **Master 宕机后自动选主、自动切换**。

### 故障转移完整流程

```java
1. 主观下线（SDOWN）
   Sentinel 对 Master 发送 PING，超时未响应
   → 该 Sentinel 单独标记 Master 为「主观下线」

2. 客观下线（ODOWN）
   该 Sentinel 向其他 Sentinel 询问
   → 超过 quorum 数量认为 Master 下线
   → 标记为「客观下线」，触发故障转移

3. Sentinel Leader 选举
   Sentinel 之间通过 Raft 协议选出 Leader
   → 由 Leader 负责执行切换

4. 选新 Master（优先级依次）
   slave-priority 最高 → 复制 offset 最大 → run_id 最小

5. 切换完成
   → 通知所有 Slave 更换 Master
   → 更新客户端连接（客户端通过 Sentinel 获取新 Master 地址）
   → 原 Master 恢复后降级为 Slave
```

### 哨兵的缺点

- 只解决**高可用**，Master 仍是单节点
- 写能力和存储容量有上限 → 引出 Cluster 模式

## 三、Cluster 模式

### 解决的问题 Cluster

**水平扩展**：将数据分散到多个 Master，突破单机内存和写入瓶颈。

### 核心：哈希槽（Hash Slot）

- 总共 **16384** 个槽
- 数据路由：`CRC16(key) % 16384` → 计算出 slot → 路由到对应 Master
- 每个 Master 负责一段连续 slot，自带若干 Slave 保证局部高可用
- 节点间通过 **Gossip 协议**互相感知状态，支持动态扩缩容（slot 迁移）

### 为什么是 16384 个槽？

- 心跳包中用 bitmap 表示负责的 slot，16384 个 slot 只需 2KB
- 若用 65536 个 slot 则需 8KB，心跳包过大
- 且 Redis Cluster 节点数一般不超过 1000，16384 个槽已经足够分配

## 四、三种模式对比

| 维度     | 主从              | 哨兵           | Cluster           |
| -------- | ----------------- | -------------- | ----------------- |
| 高可用   | ✗（手动切换）     | ✓（自动切换）  | ✓                 |
| 水平扩展 | ✗                 | ✗              | ✓                 |
| 读写分离 | ✓                 | ✓              | 有限支持          |
| 复杂度   | 低                | 中             | 高                |
| 适用场景 | 数据备份/读多写少 | 中小规模高可用 | 大数据量/高并发写 |

## 五、高频面试题

### Q1：主从复制全量同步和增量同步的区别？

全量同步在首次连接时触发，Master fork 子进程生成 RDB 发给 Slave；增量同步在断线重连时，Slave 携带 offset，Master 从 repl_backlog 中补发缺失命令。若 offset 已超出 backlog 范围则退化为全量同步。

### Q2：哨兵如何判断 Master 宕机？

分两阶段：先「主观下线」（单个 Sentinel 认为宕机），再「客观下线」（超过 quorum 数量的 Sentinel 认同）。两阶段设计是为了避免网络抖动导致的误判。

### Q3：哨兵如何选新 Master？

依次按：slave-priority（优先级）最高 → 复制 offset 最大（数据最新）→ run_id 字典序最小。

### Q4：Cluster 的哈希槽为什么是 16384 个？

心跳包用 bitmap 表示 slot 归属，16384 个 slot 只需 2KB；若用 65536 个则需 8KB，网络开销过大。且实际集群节点数通常不超过 1000，16384 足够分配。

### Q5：Cluster 和哨兵怎么选型？

- 数据量在单机可承受范围内，只需高可用 → **哨兵**（运维简单）
- 数据量大或写吞吐高，需水平扩展 → **Cluster**

### Q6：脑裂问题是什么？怎么解决？

网络分区时，旧 Master 和新 Master 同时接受写请求，网络恢复后旧 Master 降为 Slave 导致数据丢失。缓解方案：配置 `min-replicas-to-write`（至少 N 个 Slave 正常同步才允许写入），降低脑裂期间的数据写入量。
