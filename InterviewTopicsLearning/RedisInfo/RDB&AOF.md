# RDB & AOF

> 这边问的 Gemini 3.1 Pro，复习八股的确是有必要的，我甚至一开始MySQL和Redis的内容都搞混了。

##

没错，你的记忆非常准确！**RDB 和 AOF 是 Redis 的数据持久化机制**，而不是 MySQL 的（MySQL 用的是 Redo Log、Undo Log 和 Binlog）。

因为 Redis 是一个**基于内存**的数据库，读写速度极快，但如果不把数据保存到硬盘上，一旦服务器宕机或重启，内存里的数据就会瞬间清空。为了解决这个问题，Redis 提供了两种主要的持久化方式：**RDB** 和 **AOF**。

为了让你更好地理解和记忆，我们可以打个比方：
**RDB 就像是“拍快照”**（定期给全盘数据拍个照）。
**AOF 就像是“写日记”**（把你做过的每一次修改动作都记录下来）。

下面为你详细拆解这两个机制：

---

### 一、 RDB (Redis Database) —— 内存快照

**1. 什么是 RDB？**
RDB 是 Redis 默认的持久化方式。它会在指定的时间间隔内，将内存中的**所有数据集**作为一个快照（Snapshot）写入到磁盘中。生成的文件通常叫 `dump.rdb`，这是一个经过压缩的二进制文件。

**2. 它是怎么工作的？**
当触发 RDB 持久化时（比如满足了配置项“5分钟内有100次修改”，或者手动执行了 `bgsave` 命令）：
Redis 主进程会 **fork（派生）** 出一个子进程。
主进程继续处理客户端的请求，子进程负责将内存中的数据写入一个临时的 RDB 文件中。
写入完成后，临时文件会替换掉旧的 RDB 文件。

**3. RDB 的优缺点**
**优点：**
    **恢复速度快**：因为它存的是二进制的数据块，重启 Redis 时直接把数据加载进内存就行，非常适合灾难恢复。
    **文件体积小**：经过了压缩，占用磁盘空间少。
    **对性能影响小**：由子进程在后台完成，主进程不执行任何磁盘 I/O 操作。
**缺点：**
    **容易丢数据**：因为它是定时保存的（比如每 5 分钟保存一次），如果在这个间隔内 Redis 宕机了，那最后这几分钟的数据就永远丢失了。
    **Fork 子进程的开销**：如果内存数据非常大，fork 子进程的瞬间会比较消耗 CPU，可能导致 Redis 稍微卡顿一下。

---

### 二、 AOF (Append Only File) —— 追加日志

**1. 什么是 AOF？**

AOF 是以日志的形式，把 Redis 执行过的**每一条写命令**（比如 SET、DEL，读命令不记录）追加保存到一个文件中（通常叫 `appendonly.aof`）。

**2. 它是怎么工作的？**

当 Redis 执行一条写命令后，它会把这条命令以 Redis 通信协议的文本格式写入 AOF 缓冲区，然后根据配置的策略同步到磁盘。

AOF 有三种刷盘策略（同步频率）：
**Always**：每次写操作都立刻存入磁盘（最安全，但最慢，严重拖慢 Redis 性能）。
**Everysec（默认设置）**：每秒钟保存一次（折中方案，性能很好，最多只会丢失 1 秒的数据）。
**No**：交由操作系统决定什么时候刷盘（最快，但不安全）。

**3. AOF 重写机制 (Rewrite)**
如果你一直给 Redis 写数据，AOF 文件会越来越大，怎么办？
Redis 提供了一个 AOF 重写机制。它会自动在后台把 AOF 文件“瘦身”。
*比如你对同一个变量执行了 100 次 `INCR` 操作，AOF 原本记录了 100 条命令，重写后就会直接变成一条 `SET 变量 100`。*

**4. AOF 的优缺点**
**优点：**
    **数据极其安全**：最多只丢 1 秒的数据（使用 Everysec 策略）。
       **文件可读性强**：AOF 里面存的是纯文本的 Redis 命令，如果你不小心执行了 `FLUSHALL` 清空了数据库，只要还没发生重写，你可以马上打开 AOF 文件把最后那条命令删掉，就能恢复数据。
   **缺点：**
       **文件体积大**：即使有重写机制，AOF 文件通常也比 RDB 文件大。
       **恢复速度慢**：重启 Redis 时，系统需要把 AOF 文件里的命令从头到尾重新执行一遍来恢复数据，数据量大时会比较慢。

---

### 三、 总结对比与怎么选？

| 特性 | RDB (拍快照) | AOF (写日记) |
| :--- | :--- | :--- |
| **保存内容** | 某一时刻的完整数据（二进制） | 所有的写操作命令（文本） |
| **数据安全性** | 较低（会丢失最后一次快照后的数据） | 高（最多丢1秒数据） |
| **文件大小** | 小（压缩二进制） | 大（记录了所有操作） |
| **恢复速度** | **极快** | 慢 |
| **适用场景** | 数据备份、对丢失少量数据不敏感的缓存 | 对数据安全性要求高的核心业务 |

**企业里通常怎么用？（混合模式）**
在早期的 Redis 中，开发者通常要在这两者之间纠结。但是从 **Redis 4.0** 开始，官方推出了**RDB-AOF 混合持久化**：

   在 AOF 重写的时候，它会把当前的内存全量数据以 RDB 的（二进制）格式写到 AOF 文件的开头。
   之后的增量修改，依然以 AOF 的（文本命令）格式追加到文件末尾。
   **结果就是**：既保证了重启时恢复速度飞快（前半部分是 RDB），又保证了数据不丢失（后半部分是 AOF 日志），完美结合了两者的优点！这也是目前生产环境的标配。

**顺便与 MySQL 关联一下帮你记忆：**
   Redis 的 **RDB** 类似于 MySQL 的 **mysqldump 导出的全量数据文件**。
   Redis 的 **AOF** 类似于 MySQL 的 **Binlog (归档日志) 或 Redo log**。
