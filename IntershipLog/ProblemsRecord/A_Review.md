# 实习经历复盘 - 面试准备

---

## 实习经历第一点：支付风控黑名单管理模块

### 简历原文

> 为提升微小提现场景下的风险控制能力，开发了支付风控黑名单管理模块。基于 Redis ZSet 实现定时黑名单解封任务，通过 Score 存储解封时间戳，配合 ZRANGEBYSCORE 定时扫描 + SetNX 分布式锁实现高可用的任务调度，保障多实例环境下的幂等性。

---

## 一、核心问题框架

### 1. 你做了什么？

在微小提现场景中，部分用户行为触发风控规则后会被临时拉入黑名单，禁止提现。黑名单有时效性，到期后需要自动解封。核心设计如下：

- 用 Redis ZSet 存储黑名单，`member = userId`，`score = 解封时间戳`
- 定时任务周期性执行 `ZRANGEBYSCORE key 0 currentTimestamp`，查出所有到期用户
- 用 SetNX 分布式锁保证多实例下只有一个实例执行任务
- 执行完解封后用 `ZREM` 从 ZSet 移除该用户

### 2. 为什么这样做？（技术选型思路）

**为什么选 Redis ZSet，而不是其他方案？**

| 方案                    | 问题                                                                                          |
| ----------------------- | --------------------------------------------------------------------------------------------- |
| 定时扫描数据库          | 给 DB 造成压力，慢，不适合高频任务                                                            |
| Redis 普通 String + TTL | TTL 到期自动删除，但无法主动查出"哪些 key 刚刚过期"，需要 keyspace notification，复杂且不可靠 |
| Redis List / Set        | 没有排序能力，无法按解封时间高效筛选                                                          |
| **Redis ZSet**          | **Score 存时间戳，ZRANGEBYSCORE 可以 O(log N + M) 精确捞出所有到期用户**                      |

> ZSet 的核心价值：把"时间"变成可范围查询的维度。

**为什么用 SetNX 做分布式锁，而不是其他锁？**

- SetNX = SET if Not eXists，原子操作，天然避免多个实例同时抢锁的竞态条件
- 配合 `EXPIRE` 设置锁超时，防止实例崩溃后死锁
- 轻量，无需引入 ZooKeeper / etcd 等重型组件

### 3. 带来的收益是什么？

- **解放人工**：解封操作全自动，不需要运营手动介入
- **多实例安全**：服务水平扩容后，任务不会重复执行，保证幂等性
- **低延迟**：Redis 内存操作，扫描速度远快于 DB 查询
- **高可用**：锁有过期时间，即使某实例崩溃，锁自动释放，其他实例下一轮可接管

## 二、面试高频问题 & 标准答案

### Q1：ZSet 的 ZRANGEBYSCORE 是怎么用的？时间复杂度？

```go
ZRANGEBYSCORE blacklist 0 <当前Unix时间戳>
```

- 查出所有 score（解封时间）≤ 当前时间的用户，即"应该解封的人"
- 时间复杂度：**O(log N + M)**，N 是 ZSet 总元素数，M 是返回结果数

### Q2：定时任务是怎么实现的？

Go 中常见两种方式：

```go
// 方式1：time.Ticker
ticker := time.NewTcker(1 * time.Minute)
for range ticker.C {
    runUnblockTask()
}

// 方式2：cron 库（如 robfig/cron）
c := cron.New()
c.AddFunc("@every 1m", runUnblockTask)
c.Start()
```

定时间隔一般设为 1 分钟，根据业务对解封时效的要求调整。

### Q3：为什么需要分布式锁？不加锁会怎样？

多实例问题：服务部署了 3 个实例，每个实例都有定时任务，同一时刻 3 个实例同时执行：

```go
实例A: ZRANGEBYSCORE → [user1, user2] → 开始解封 user1
实例B: ZRANGEBYSCORE → [user1, user2] → 开始解封 user1  ← 重复！
实例C: ZRANGEBYSCORE → [user1, user2] → 开始解封 user1  ← 重复！
```

可能导致：重复写 DB、重复发通知、数据状态错乱。

加锁后：只有一个实例能拿到锁并执行，其他实例直接跳过本轮。

### Q4：SetNX 分布式锁的具体实现？

```go
// 推荐用原子命令：SET key value NX EX 30
ok, err := rdb.SetNX(ctx, "blacklist:unlock:lock", instanceID, 30*time.Second).Result()
if !ok {
    return // 没抢到锁，本轮跳过
}
defer rdb.Del(ctx, "blacklist:unlock:lock") // 任务完成后主动释放

// 执行解封逻辑...
```

关键点：

- `NX`：不存在才设置（原子抢锁）
- `EX 30`：30秒超时，防死锁
- 用 `instanceID` 作为 value，释放时验证是自己的锁（防误删他人锁）

### Q5：锁的过期时间怎么定？如果任务执行时间超过锁的过期时间怎么办？

- 过期时间 = 预估任务执行时间的 3~5 倍，留足余量
- 如果担心任务超时，可以用**看门狗机制**（watchdog）：开一个协程定期续期锁，任务完成后停止续期
- 小批量解封任务通常毫秒级完成，30s 的锁完全够用

### Q6：什么是幂等性？你是怎么保证幂等性的？为什么要保证？

**幂等性定义：** 同一操作执行一次和执行多次，结果完全相同，不产生副作用。

**为什么要保证：** 分布式系统中网络抖动、重试、多实例并发都可能导致同一逻辑被触发多次。

**这个场景里如何保证：**

1. **分布式锁**：同一时刻只有一个实例在执行 → 避免并发重复处理
2. **ZREM 的原子性**：解封后立即从 ZSet 移除该用户，下次扫描就不会再扫到他
3. **DB 层幂等**：解封操作是 `UPDATE status = 'normal' WHERE status = 'blocked'`，多次执行结果一样

### Q7：高可用的任务调度体现在哪里？

| 场景           | 没有分布式锁         | 有分布式锁                       |
| -------------- | -------------------- | -------------------------------- |
| 实例1崩溃      | 任务中断，等实例恢复 | 锁超时后，实例2/3 下一轮自动接管 |
| 多实例同时运行 | 重复执行，数据错乱   | 只有一个实例执行，其他跳过       |
| 实例扩容       | 执行次数倍增         | 仍然只有一个实例执行             |

### Q8：如果要解封的用户非常多怎么处理？

- 用 `ZRANGEBYSCORE key 0 ts LIMIT 0 1000` 分批处理，每批 1000 条
- 避免一次性把大量数据加载到内存
- 结合 DB 批量更新（`UPDATE ... WHERE id IN (...)` 批次执行）

### Q9：为什么不用消息队列（MQ）来做解封？

|                  | Redis ZSet 方案      | MQ 延迟消息方案            |
| ---------------- | -------------------- | -------------------------- |
| 查看当前黑名单   | 直接 ZRANGE，O(N)    | 困难，消息在队列里不可见   |
| 中途修改解封时间 | ZADD 更新 score 即可 | 需要撤回并重发消息，复杂   |
| 依赖             | 只需 Redis           | 需要引入 MQ 组件           |
| 适用场景         | 数据量可控           | 超大规模、解封时间精确到秒 |

## 三、追问：分布式锁为什么不用 synchronized？

### 核心区别：锁的作用范围不同

`synchronized` 是进程内的锁，只锁同一个 JVM/进程里的线程：

```go
实例A (进程1)          实例B (进程2)          实例C (进程3)
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│  线程1       │      │  线程1       │      │  线程1       │
│  线程2  sync │      │  线程2  sync │      │  线程2  sync │
│  线程3       │      │  线程3       │      │  线程3       │
└──────────────┘      └──────────────┘      └──────────────┘
   各自的内存              各自的内存              各自的内存
```

`synchronized` 只能让实例A 内部的线程互斥，完全感知不到实例B、实例C 的存在。

**Redis SETNX 是跨进程的锁：**

```go
实例A ──┐
实例B ──┼──→ Redis（共享）← SETNX blacklist:lock
实例C ──┘
```

实例A 在 Redis 里写入锁之后，实例B 去 Redis 查，发现锁已经存在就跳过。

> **"分布式锁"里"分布式"指的是应用实例分布式，不是 Redis 分布式。**

### 单节点 Redis 的隐患

Redis 挂了，锁消失或无法写锁，可能所有实例都抢着执行。

应对方案：

- **可接受**：解封任务幂等性保证了重复执行无害，短暂的 Redis 故障影响有限
- **更高要求**：用 Redis Sentinel / Cluster 保证 Redis 本身高可用
- **极致要求**：用 Redlock 算法（多个独立 Redis 节点投票）

## 四、追问：NX 是什么意思？Redis Cluster 下怎么办？

### NX = Not eXists

| 命令               | 含义                                  |
| ------------------ | ------------------------------------- |
| `SET key value NX` | 只有 key **不存在**时才设置（抢锁用） |
| `SET key value XX` | 只有 key **已存在**时才设置           |

**老写法（有问题）：**

```go
SETNX lock "instance-A"   # 步骤1
EXPIRE lock 30             # 步骤2（不原子！崩溃后死锁）
```

**现代写法（推荐）：**

```go
SET lock "instance-A" NX EX 30   # 一条命令，原子操作
```

### Redis Cluster 下 SETNX 的问题

单个 key 的 SETNX 在 Cluster 里操作上没问题（key 被 hash 到某个 shard）。

真正的问题是**主从切换的竞态**：

```go
1. 实例A 向 Master 写入锁成功
2. Master 还没来得及同步给 Slave → Master 宕机
3. Slave 晋升为新 Master（锁数据丢失）
4. 实例B 来写锁，发现锁不存在，成功拿到锁
结果：实例A 和 实例B 同时持有锁 → 锁失效
```

### Redlock 和 Redisson RLock

**Redlock 算法（Redis 作者 antirez 提出）：** 向 N 个完全独立的 Redis Master 同时抢锁，超过半数（N/2+1）成功才算拿到锁：

```go
Redis节点1 ──┐
Redis节点2 ──┤
Redis节点3 ──┼→ 实例A 向5个节点都执行 SET NX，≥3个成功 → 锁成立
Redis节点4 ──┤
Redis节点5 ──┘
```

**Redisson RLock 特性对比：**

| 特性   | 原始 SETNX     | Redisson RLock       |
| ------ | -------------- | -------------------- |
| 原子性 | 需要手动用 Lua | 内置 Lua 脚本        |
| 锁续期 | 手动 watchdog  | 自动续期（看门狗）   |
| 可重入 | 不支持         | 支持                 |
| 等待锁 | 需要轮询       | Pub/Sub 通知，不轮询 |

**选型总结：**

```go
单节点 Redis        → SET NX EX 足够
Redis 主从/Sentinel → SET NX EX 有主从切换风险，可接受或用 Redisson RLock
Redis Cluster       → 同上
多个独立 Redis 节点  → Redlock 算法（Redisson 有封装）
```

## 五、追问：多实例是什么？HTTP 请求是线程还是进程？

### 多实例的概念

**实例 = 这套代码跑起来的一个 OS 进程。**

线上多实例部署示意：

```go
用户请求
    ↓
  负载均衡器 (Nginx / K8s Service)
    ↓          ↓          ↓
  实例A      实例B      实例C
(进程1)    (进程2)    (进程3)
    ↓          ↓          ↓
         同一个 Redis
         同一个 MySQL
```

多实例的原因：

| 原因         | 解释                                             |
| ------------ | ------------------------------------------------ |
| **高可用**   | 实例A 崩溃了，B 和 C 还在服务，用户无感知        |
| **水平扩容** | 流量大了，加几个实例分摊请求，比升级单机配置便宜 |

在 Kubernetes 里就是 `replicas: 3`，直接起 3 个相同的 Pod，每个 Pod 是一个独立进程，内存完全隔离，互相不知道对方的存在。

### Go 语言中 HTTP 请求是什么？

**既不是线程，也不是进程，是 Goroutine（协程）。**

Go 的 HTTP Server 每来一个请求，就启动一个新的 goroutine 来处理：

```go
// Go 标准库 net/http 内部大概是这样的
for {
    conn, _ := listener.Accept()
    go handleRequest(conn)  // 每个请求一个 goroutine
}
```

三者的区别：

```go
OS 进程 (Process)
└── OS 线程 (Thread) × N        ← Java/C++ 通常在这层
    └── Goroutine × 成千上万   ← Go 在这层
```

|          | 进程     | OS线程       | Goroutine    |
| -------- | -------- | ------------ | ------------ |
| 内存     | 完全隔离 | 共享进程内存 | 共享进程内存 |
| 初始栈   | MB 级    | 1~8 MB       | **2 KB**     |
| 切换开销 | 极大     | 较大         | **极小**     |
| 创建数量 | 几个     | 数百         | **数十万**   |

Go 的调度模型（GMP）：成千上万个 goroutine 被 Go runtime 复用到少量 OS 线程上，这是 Go 高并发的核心原因。

### 串起来理解锁的完整层次

```go
跨实例（跨进程）         → Redis SETNX          ← 简历里的这个
单实例内跨请求（跨goroutine）→ sync.Mutex / sync.RWMutex
单个请求内               → 不需要锁（天然串行）
```

> 面试回答："sync.Mutex 只能保护同一个进程内的 goroutine 并发，但定时任务在多个实例（多个 OS 进程）上都会跑，进程间内存完全隔离，sync.Mutex 对其他进程没有任何约束力，必须用 Redis 这种外部共享存储来做跨进程协调。"

## 六、可能被追问的深层问题

- **Redis 挂了怎么办？** → 持久化（RDB/AOF）+ 哨兵/集群保证 Redis HA；紧急情况 fallback 到 DB 查询
- **ZSet 存了多少数据？有没有内存压力？** → 黑名单用户数通常有限，ZSet 内存占用极低
- **加黑和解封的并发安全怎么保证？** → 加黑用 ZADD，解封用 ZREM，Redis 命令本身是原子的
- **怎么监控这个任务是否正常运行？** → 打点（任务执行次数、解封用户数、耗时），接入告警
- **ZSet 里 Score 存时间戳，是秒还是毫秒？** → 统一用秒级 Unix 时间戳即可，ZRANGEBYSCORE 对应用 `time.Now().Unix()`

---

## 七、一句话总结

> 用 ZSet 的 Score 把"时间"变成可范围查询的索引，用 SetNX 把"分布式互斥"变成一行原子命令，两者结合实现了轻量、高可用、幂等的定时解封调度。
